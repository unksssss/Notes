# 可靠 UDP 与 KCP 原理

## 先纠正认知

**UDP 本身不保证任何可靠性。** 所谓「可靠 UDP」是**在 UDP 之上、由应用层自己实现**的一套机制。

| | 可靠性实现在哪 | 可配置性 |
| --- | --- | --- |
| **TCP** | **内核** | 几乎改不动 |
| **可靠 UDP** | **用户态**（你的代码 / KCP 库） | 参数全部可调 |

→ 自研的意义不是「更可靠」，而是**能按业务需要取舍**。

## 为什么不用现成的 TCP

TCP 的可靠性是「**全有或全无**」，五个致命点：

1. **队头阻塞**：一个包丢了，后面已到达的包必须等它重传才能交付
2. **无法放弃**：3 秒前的位置数据重传回来毫无价值，但 TCP 照样重传
3. **重传时机不可控**：RTO 算法面向吞吐而非延迟
4. **拥塞控制不可控**：一次丢包就猛烈降速，对实时对战是灾难
5. **建连开销**：三次握手，短连接场景不划算

→ 游戏要的语义是：**「大概率会收到、而且很及时、实在来不及就不要」**
→ TCP 给的语义是：**「你一定会收到，但可能很晚」**

## 四个核心机制

| 机制 | 作用 | 关键细节 |
| --- | --- | --- |
| **序列号** | 检测丢包 / 乱序 / 重复 | 每个包递增编号；收到 1、2、4 就知道 3 丢了 |
| **ACK 确认** | 告知发送方接收情况 | **累积确认**（ACK 4 = 4 之前都收到）；**位图确认**（精确到单个包，弱网下更有效） |
| **重传** | 补发丢失数据 | 超时重传 / 快速重传；RTO 系数与重传阈值都可调 |
| **滑动窗口** | 控制发送速率 | 限制同时在途的包数；可关闭拥塞控制（KCP 支持） |

**这四个零件 TCP 全都有**——区别只在于它们在用户态，参数由你定。

### 分片与重组

一个逻辑消息超过 MTU 时切成多个 UDP 包，**每个分片单独编号**：

- 丢哪个分片，只重传那一个，而不是整个报文
- TCP 在内核里做同样的事，但你控制不了它的重传时机

## KCP 比 TCP 快在哪

| 维度 | TCP | KCP |
| --- | --- | --- |
| RTO 系数 | 超时后 **×2** 递增 | **×1.5**，重传更早 |
| 快速重传阈值 | 3 个重复 ACK（约等于跳过 2 个后续包） | **`fastresend` 可设为 1**，跳过 1 个就重传 |
| 拥塞控制 | 强制开启 | **可开关**（`ikcp_nodelay` 参数） |
| 实现位置 | 内核 | 用户态，需自行配合 UDP socket |

**本质是「用带宽换延迟」**：更激进的重传意味着更多冗余流量，在弱网下换来更低的延迟。

⚠️ 代价：KCP 的冗余流量不小，不适合大流量传输（如下载、大文件同步）。

## 主要方案对比

| 方案 | 特点 | 典型场景 |
| --- | --- | --- |
| **KCP** | 纯算法库，无连接管理，需自行配合 UDP socket；重传激进 | 国内游戏最常用 |
| **ENet** | 自带连接管理与多通道（channel） | 开源引擎常见 |
| **UTP**（Unity Transport） | Unity 官方，提供 Reliable / Unreliable 两种 pipeline | Netcode for GameObjects、Mirror 的底层 |
| **QUIC** | 用户态完整传输层，0-RTT、多流复用、解决队头阻塞 | HTTP/3，部分新项目 |

## 关键设计：选择性可靠

**不是所有数据都值得重传**——这才是自研最核心的价值所在。

| 通道 | 数据 | 理由 |
| --- | --- | --- |
| **可靠通道** | 技能释放、开火指令、道具使用、交易结算、聊天、登录匹配 | 丢一次就是逻辑 bug |
| **不可靠通道** | 位置与朝向、移动输入采样、非关键特效、动画状态 | 新的会覆盖旧的，重传反而有害 |

同一连接上可以并存多条通道，按消息类型分流——UTP 里叫 `pipeline`，ENet 里叫 `channel`。

### 冗余发送：不靠重传也能抗丢包

对关键输入（如 FPS 的射击指令），可以把**最近几帧的输入一起打包发送**：丢一包不影响，收到的包自带历史。

这是「多发几次」代替「重传等待」的思路，弱网下比等 ACK 更快。

## 面试答题模板

> "UDP 本身不保证可靠，「可靠 UDP」其实是把 TCP 那套机制搬到应用层重做一遍——序列号检测丢包乱序，ACK 做确认，超时或跳过确认就重传，再用滑动窗口控制发送速率。之所以不直接用 TCP，是因为 TCP 的可靠性是全有或全无：队头阻塞会让后面的包一起等，而且你没法告诉它「这条消息不重要，别重传了」。
>
> KCP 就是这类方案的典型，它比 TCP 快的核心是用带宽换延迟——RTO 只乘 1.5 倍而不是 2 倍，快速重传阈值可以设成跳过 1 个包就重传，而且拥塞控制可以关掉。
>
> 但真正的设计重点不是快，是**选择性可靠**：技能释放、交易这类丢一次就是 bug 的消息走可靠通道，位置、朝向这类「新的会覆盖旧的」走不可靠通道，两条通道在同一个连接上并存。"
