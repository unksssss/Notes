# 大整数哈希

## 一、题意

维护一个映射 `f: [0, 2⁶⁴) → [0, 2⁶⁴)`，初始 `f(x) = 0`（对所有 x）。共 n 次操作，每次给定 `(x, y)`：

1. 记下 `aᵢ = f(x)`（**当前值**，不是更新后的）
2. 更新 `f(x) ← y`

求 `Σ(i × aᵢ) mod 2⁶⁴`，`n ≤ 5×10⁶`。

> 一句话：**「先读后写」的 n 次映射操作，按操作序号加权重求和。**

## 二、五处错（按致命度）

灯皇的循环体：

```cpp
while (q--) {
    long long x, y;
    cin >> x >> y;
    map[x] = y;                       // ← 只有「写」，没有「读」
}
long long result = 0;
for (auto it : map)
    result += (it.first * it.second) % (2 ^ 64);
```

### ① 漏了整个「读」的动作（主错）

题目要的 `aᵢ = f(x)` **是在赋值之前读一次**。他一步都没读，反而在最后遍历哈希表：

- 遍历得到的是「每个 x **最后一次**被赋的 y」，中间的 9 次赋值全丢了
- 加权的系数用成了 `x`（`it.first`），而不是操作序号 `i`
- 表里的顺序还是哈希序（`unordered_map` 不保序），根本不是操作顺序

**这不是「差一点」，是换了另一道题在做。** 4 步小样例：

```
输入            正确推演                              灯皇输出
4               i=1  x=1  a=f(1)=0   → 1×0  = 0
1 10            i=2  x=1  a=f(1)=10  → 2×10 = 20        40
1 20            i=3  x=1  a=f(1)=20  → 3×20 = 60
1 30            i=4  x=2  a=f(2)=0   → 4×0  = 0         正确 80
2 5             总和 = 80
```

### ② 加权系数用成了 `x`

```cpp
result += it.first * it.second;   // ❌ it.first 是 x
sum    += (ull)i  * ans;          // ✅ i 是操作序号（从 1 开始）
```

题目公式是 `Σ i × aᵢ`，`i` 和 `x` 毫无关系。

### ③ `2 ^ 64` 是 `66`，不是 2 的 64 次方

```cpp
% (2 ^ 64)      // ❌ ^ 是「按位异或」
```

实测输出：

```
2 ^ 64 = 66        （10 XOR 1000000 = 1000010 = 66）
```

所以他那句其实是 `% 66`。

> C++ 里没有幂运算符。`^` 是**按位异或**，`pow(2, 64)` 是浮点且会溢出。**`2⁶⁴` 在整数世界里没法写成一个字面量** —— 这正是本题的核心命题。

### ④ `long long` 装不下 2⁶⁴−1

题目明确 `0 ≤ x, y < 2⁶⁴`，而 `long long` 最大只有 `2⁶³−1`。实测：

```
读 "18446744073709551615" 到 long long:
    a = 9223372036854775807   fail = 1   b = -1（根本没读进来）
读 "18446744073709551615" 到 unsigned long long:
    a = 18446744073709551615  fail = 0   b = 7
```

`cin >> long long` 溢出时**不会崩、不会抛异常**，而是：赋 `LLONG_MAX` + **置 failbit** → 之后**所有**读取立刻返回、变量保持原值。

**只要数据里有一个 x ≥ 2⁶³，后面全废。** 这是最典型的静默失效：程序正常退出，输出一个看似合理的数。

### ⑤ `long long × long long` 溢出是 UB

```cpp
result += (it.first * it.second);
```

有符号整数溢出在 C++ 是 **未定义行为**（不是「回绕成负数」），编译器可以把它优化成任何值。这题乘出来必然爆表。

换成 `unsigned long long` 之后，溢出变成**定义良好**的 `mod 2⁶⁴` —— 也就是题目要的答案。

### 附带

| 小问题 | 说明 |
|---|---|
| 变量名 `map` | 又是它，遮蔽 `std::map`（上一题刚说过） |
| 没 `reserve` | 5e6 节点反复 rehash |
| `cin` 读 200 MB | 5e6 行 × 2 个 20 位数 ≈ 2×10⁸ 字节 |
| `cout << result` | 没换行（多数 OJ 宽容，但别学） |

## 三、正解：三档，按需选

### 档 1：`unordered_map`（代码最短，n ≤ 5e5 够用）

```cpp
#include <cstdio>
#include <unordered_map>
using namespace std;
using ull = unsigned long long;

int main() {
    int n;
    if (scanf("%d", &n) != 1) return 0;

    unordered_map<ull, ull> f;
    f.reserve(n * 2);

    ull sum = 0;
    for (int i = 1; i <= n; ++i) {
        ull x, y;
        scanf("%llu %llu", &x, &y);
        auto it = f.find(x);
        ull ans = (it == f.end() ? 0ULL : it->second);   // 默认 0
        sum += (ull)i * ans;                             // 自然溢出 ≡ mod 2^64
        f[x] = y;
    }
    printf("%llu\n", sum);
}
```

**三个关键点**：
- `f.find(x)` 而不是 `f[x]` —— `operator[]` 会**插入**一个默认值，虽然本题恰好无害，但养成用 `find` 读的习惯
- `sum` 是 `unsigned long long` —— 溢出自动等于 `mod 2⁶⁴`
- 类型全用 `ull`

### 档 2：手写开放地址法（快 5 倍）

```cpp
static const int CAP  = 1 << 23;    // 8388608 槽位，n ≤ 5e6 → 负载 ≤ 0.6
static const int MASK = CAP - 1;
static ull  HK[CAP], HV[CAP];
static bool HU[CAP];

int p = (int)(mix(x) & MASK);
while (HU[p] && HK[p] != x) p = (p + 1) & MASK;   // 线性探测

ull ans = HU[p] ? HV[p] : 0ULL;
sum += (ull)i * ans;
HU[p] = true; HK[p] = x; HV[p] = y;
```

| 为什么快 | 说明 |
|---|---|
| 无堆分配 | `unordered_map` 每个节点一次 `new`（5e6 次） |
| 无指针跳转 | 数组连续，cache 友好 |
| 容量 2 的幂 | `& MASK` 代替 `%`（取模是除法指令，20+ 周期） |

**负载因子的取舍**：线性探测在负载 0.6 时平均探测约 2~3 次，可接受；到 0.9 就退化成近似顺序扫描。所以 `CAP` 要开成 `n` 的 1.5~2 倍。

### 档 3：再加 fread 快读（200 MB 输入不再是瓶颈）

```cpp
static char IBUF[1 << 25];
static int ILEN = 0, IPOS = 0;
inline char gc() {
    if (IPOS == ILEN) {
        ILEN = (int)fread(IBUF, 1, sizeof(IBUF), stdin);
        IPOS = 0;
        if (ILEN <= 0) return 0;
    }
    return IBUF[IPOS++];
}
inline ull readU() {
    char c = gc();
    while (c < '0' || c > '9') { if (!c) return 0; c = gc(); }
    ull r = 0;
    while (c >= '0' && c <= '9') { r = r * 10 + (ull)(c - '0'); c = gc(); }
    return r;
}
```

**为什么值得写**：`cin` 即使关了同步，每个 `>>` 仍要走 `num_get` 的 locale 处理、异常标志、格式化；`fread` 一次拿 32 MB 进内存，解析只剩「跳空白 + 累加」。

## 四、核心认知一：`mod 2⁶⁴` 不用写

```cpp
sum = (sum + (ull)i * ans) % (1ULL << 64);   // ❌ 1ULL << 64 是 UB
sum = sum + (ull)i * ans;                     // ✅ 什么都不用做
```

`unsigned long long` 是 64 位，**任何算术溢出都是对 2⁶⁴ 取模**，这是 C++ 标准明确保证的定义良好的行为（有符号则相反，是 UB）。

> 题面反复强调 `(mod 2⁶⁴)`，实际是在提示：**「选对类型，模运算自动完成」**。
> 这也是为什么这题 `x, y` 必须用无符号 —— 用 `long long` 不仅装不下，溢出还是 UB。

⚠️ `1ULL << 64` 是 UB（移位数 == 位宽）。想显式写可以用 `% (1ULL << 63) % (1ULL << 63)` 之类，但没必要 —— 交给类型。

## 五、核心认知二：`x & MASK` 会被卡

如果直接用 `x` 的低位当坐标：

```cpp
int p = x & MASK;      // 危险
```

构造 `x` 全是 2¹⁶ 的倍数（低 16 位恒为 0）时，**所有 key 落在同一个桶**，线性探测退化成顺序扫描 → `O(n²)`。实测：

```
【退化】20000 个 x 全是 2^16 的倍数
  直接 x & MASK            131.4 ms
  splitmix64(x) & MASK       1.0 ms      ← 131 倍
```

### 修法：先混一次再取低位

```cpp
static inline ull mix(ull x) {
    x += 0x9e3779b97f4a7c15ULL;
    x = (x ^ (x >> 30)) * 0xbf58476d1ce4e5b9ULL;
    x = (x ^ (x >> 27)) * 0x94d049bb133111ebULL;
    return x ^ (x >> 31);
}
```

`splitmix64` 是「雪崩（avalanche）」构造：输入的**任意一个 bit** 变化都会让输出的**约一半 bit** 翻转。所以低位的规律性被彻底打散。

> 同理，`unordered_map<ull, ...>` 的 `std::hash<unsigned long long>` 是**恒等映射**，桶下标 = `x % 桶数`。这题上限 5e6 且数据随机时不会出事，但要知道**默认哈希对整数没有防御力**（Codeforces 上的 anti-hash 就是打这个）。

## 六、性能实测（本机 g++ 8.1.0 `-O2`）

### 算法部分：5×10⁶ 次操作（30% 的 x 与之前重复）

| 方案 | 耗时 |
|---|---|
| `unordered_map` + `reserve` | **801 ms** |
| 手写开放地址 `x & MASK` | **152 ms** |
| 手写开放地址 `splitmix64(x) & MASK` | **160 ms** |

混一次只多 8 ms（5%），换来免疫退化 —— 值。

### IO 部分：200 MB / 5×10⁶ 行 / 10⁷ 个数

| 读法 | 耗时 |
|---|---|
| `cin`（关同步 + untie） | **2723 ms** |
| `scanf("%llu")` | **5641 ms** |
| `fread` + 手写解析 | **463 ms** |

（本机 MinGW 的 `scanf` 走 msvcrt，偏慢；Linux/glibc 上会比 `cin` 快，但和 `fread` 仍差一个数量级。）

### 完整最优解

```
读 200 MB + 5×10⁶ 次哈希操作  →  1.19 s
```

单看算法 152 ms，单看 IO 463 ms，合起来 1.19 s —— 说明表变满后探测链变长，两者互相拖累（不是简单相加）。

## 七、输出格式：`%lld` 是陷阱

题面末尾那句 **「64 位输出请用 printf("%lld")」** 是牛客模板的通用提示，但**这题的答案是 `unsigned`**。

```cpp
unsigned long long s = 18446744073709551615ULL;   // 2^64 - 1

printf("%llu", s);              →  18446744073709551615   ✅
printf("%lld", (long long)s);   →  -1                    ❌
cout << s;                      →  18446744073709551615   ✅（按类型选无符号）
```

`%lld` 会把最高位当符号位 → 只要 `sum ≥ 2⁶³`（约一半的随机数据）就输出**负数**。用 `%llu`，或者干脆 `cout`（它按变量类型推断，不会错）。

## 八、必须记住的点

1. **`2 ^ 64` 是异或，等于 66。** C++ 没有幂运算符。
2. **`mod 2⁶⁴` = 用 `unsigned long long`，什么都不用写。** 溢出是定义良好的。
3. **有符号溢出是 UB，无符号溢出是回绕。** 这一个差别决定了这题能不能做。
4. **`x < 2⁶⁴` 必须用 `unsigned long long`。** `long long` 溢出时置 failbit，后续读取全部失效（静默）。
5. **`2⁶⁴` 在整数域不可表示**，`1ULL << 64` 是 UB。
6. **`x & MASK` 要加 `splitmix64`**，否则规律数据把哈希打成链表。
7. **`f.find(x)` 读，`f[x] = y` 写**，别用 `[]` 读（会插入）。
8. **`%llu` 不是 `%lld`。**

## 九、易错点

| 坑 | 后果 | 正确做法 |
|---|---|---|
| `2 ^ 64` | 对 66 取模，答案全错 | 不写，靠类型溢出 |
| `long long` 存 x | 读大值 failbit，后续全废 | `unsigned long long` |
| `long long` 累加 | 有符号溢出 UB | `ull sum` |
| 漏掉「先读后写」 | 换了另一道题 | 先 `find` 取 ans，再赋值 |
| 加权用成 `x` | 与公式无关 | 用操作序号 `i`（1 起） |
| `map[x]` 读 | 静默插入默认值 | `find` |
| `x & MASK` 不混淆 | 规律数据退化 O(n²) | `splitmix64` |
| `%lld` 输出 | 高位为 1 时是负数 | `%llu` / `cout` |
| `cin` 读 2×10⁸ 字节 | 2.7 s，多半 TLE | `fread` 手写解析 |
| 5e6 节点 `unordered_map` | 约 200 MB，可能 MLE | 开放地址法 142 MB |

## 十、复杂度

| 方案 | 时间（期望） | 空间 | 实测（5e6） |
|---|---|---|---|
| `unordered_map` | `O(n)` | `O(n)`，约 200 MB | 801 ms（不含 IO） |
| 开放地址法 | `O(n)` | `O(n)`，142 MB | 152 ms |
| + `fread` | `O(n)` | 同上 | **1.19 s 总计** |

（`CAP = 2²³` 时：`HK` 67 MB + `HV` 67 MB + `HU` 8 MB ≈ **142 MB**。）

最坏情况：哈希退化 → 单次 `O(n)`，总 `O(n²)`。加 `splitmix64` 后在实际数据上不会发生。

## 十一、面试延伸

**Q：为什么 `2⁶⁴` 这种模数正好适合计算机？**

`2⁶⁴` 是「无符号整数的自然溢出点」，不需要任何显式取模运算 —— 加法、乘法、移位全都在 `mod 2⁶⁴` 的环里。代价是 `2⁶⁴` 不是质数，除法/求逆不成立，所以**做哈希时它比 1e9+7 弱**（详见 [[字符串哈希]] 的碰撞实测）。

**Q：这题能不能用「排序 + 扫描」做？**

不能。每次操作的 `aᵢ = f(x)` 依赖**操作顺序**（同一个 x 第 2 次出现时要读第 1 次写的值，第 3 次读第 2 次的……），排序会打乱因果关系。必须在线处理。

**Q：为什么 `f` 的初始值是 0 而不是「不存在」？**

这是题目给的约定，好处是**不需要判「有没有出现过」**：表里查不到时直接当 0 用，省一个分支。代价是 0 和「没设置过」不可区分 —— 如果题目要求「区分」，就得额外一个 `used` 标记。

**Q：n 再大一个数量级（5×10⁷）怎么办？**

- 计数排序 / 离散化把 x 压到 32 位（但要先读完全部 x，与在线冲突）
- 块状处理 + 外部排序
- 通常不会这么出，因为 IO 本身就要 2 GB

**Q：`x` 是 64 位但只有 5e6 个，怎么压内存？**

存 `splitmix64(x)` 的 32 位截断 + 32 位 value？会碰撞。稳妥做法是把 key 换成 `(mix(x) >> 32)` 做「指纹」，碰撞时再回表验证原 key —— 就是「开放地址 + 指纹」的思路（RocksDB 的 Bloom filter 也是这样）。

## 十二、一句话总结

> **看到 `mod 2⁶⁴` 就选 `unsigned long long`，然后忘掉取模这件事。**
> 看到 `2 ^ 64` 就想起：`^` 是异或，幂在整数世界里不存在。
