# C++ 虚函数机制与空指针调用 — vptr、成员偏移与崩溃点

## 一、题目

```cpp
struct unio
{
    char* c;
public:
    void FuncA()        { /* 操作 c */ }
    virtual void FuncB() { /* 操作 c */ }
    virtual void FuncC() { /* 操作 c */ }
};

int main()
{
    unio* unio1 = NULL;
    unio1->FuncA();

    unio* unio2 = NULL;
    unio2->FuncB();

    unio unio3;
    unio3.FuncC();
}
```

---

## 二、结论：三个都崩，但崩的位置不同

| 调用 | 崩点 | 本质 |
| --- | --- | --- |
| `unio2->FuncB()` | **取 vptr**（读地址 0） | 虚函数机制第一层，**还没进函数体** |
| `unio1->FuncA()` | **取成员偏移**（读/写地址 8） | `this` 解引用 |
| `unio3.FuncC()` | **解引用 `c`** | 二级指针的第二次解引用，**可能不崩** |

**崩得越早越好查** —— 第二种连函数体都没进，栈回溯一眼能看出是空指针调用。

### 前提很重要

如果函数体**完全不碰成员**，结论会变：

- `unio1->FuncA()` 会"正常"输出（非虚函数静态绑定，地址编译期确定，`this` 从未被解引用）
- 但从标准角度**仍然是 UB**（见第六节）

---

## 三、为什么非虚函数这次也会崩：成员偏移

对象布局（64 位）：

```
offset 0 : vptr        8 字节   ← 因为类有虚函数才存在
offset 8 : char* c     8 字节
```

`this->c` 展开成：

```asm
mov rax, [rbp-8]        ; rax = this = 0
mov rdx, [rax+8]        ; 读 this->c  →  读地址 8
```

地址 8 位于**空指针保护页**（Linux 前 4KB / Windows 前 64KB 不可访问），必崩。

> **重要推论：虚函数的存在改变了非虚函数的成员偏移。**
> 这就是跨模块 C 接口绝不能用带虚函数的类的原因——布局随编译器和选项变化，一旦不一致就错位。

---

## 四、vptr 与 vtable 机制

```
对象                          虚表（只读数据段，全类共享）
┌──────────────┐
│ vptr ────────┼──────────→  ┌──────────┐
├──────────────┤             │ &FuncB   │
│ c（未初始化） │             ├──────────┤
└──────────────┘             │ &FuncC   │
                             └──────────┘
```

- **每个「有虚函数的类」一张 vtable**，编译期生成，存在只读数据段
- **每个「对象」一个 vptr**，占 8 字节
- 同一类的所有对象共享同一张 vtable
- 虚表里还包括 RTTI 指针（用于 `typeid` / `dynamic_cast`）

**虚函数调用序列**（`unio2->FuncB()`，`unio2 = nullptr`）：

```asm
① mov rax, [nullptr]    ; 取 vptr → 读地址 0 → 这里就崩
② mov rcx, [rax + 0]    ; 取函数地址
③ call rcx              ; 调用
```

**非虚函数没有第 ① 步**，地址直接写进指令（`call FuncA`）。

## 五、`unio3` 的信号：vptr 对、成员错

```cpp
unio unio3;      // 默认初始化
```

- **类有虚函数 → 编译器生成的默认构造函数是"非平凡"的**，必须写入 vptr → `unio3.__vptr` 正确
- **但 `char* c` 是 POD 成员，默认初始化不处理** → 值不确定（栈上残留）

这就是"`FuncC()` 能正常进入、但 `c` 是野指针"这个看似矛盾现象的成因。

### 修法

```cpp
unio unio3{};                              // 值初始化 → 所有成员零初始化
// 或
struct unio { char* c = nullptr; ... };    // 类内默认成员初始化
```

---

## 六、野指针的不确定崩溃（最危险）

`unio3.c` 的值可能是：

| 残留值 | 后果 |
| --- | --- |
| `0` | 空指针解引用 → 崩在函数里 |
| 合法堆地址 | **不崩**，读写别人的数据 → 内存踩踏，问题延后爆发 |
| 非法地址 | 崩，但栈回溯指向 `c` 的目标，与 `unio3` 看不出关系 |

**「确定崩溃」只是麻烦，「不确定崩溃」才是灾难**——它可能表现为「跑一小时后在不相干的地方算错数值」。

---

## 七、对 `c` 做不同操作，后果不同

| 操作 | `unio1`（this = 0） | `unio3`（this 有效，`c` 是野指针） |
| --- | --- | --- |
| `c = p`（只写） | 崩（写地址 8） | **正常执行**，野指针值被覆盖（若原值指向堆 → 泄漏） |
| `cout << c` / `strlen(c)` | 崩（读地址 8） | **可能崩**，取决于垃圾值；也可能读出乱码 |
| `*c = 'x'` | 崩 | 可能崩，可能改坏别人的内存 |
| `delete[] c` / `free(c)` | 崩 | **堆管理器崩溃 / 双重释放** |

> 第一行值得注意：纯写场景下 `unio3` 反而"能跑通"，把未初始化的坑掩盖住了；等某天有人加一句 `if (c)` 才炸出来。

## 八、UB 的严肃性：同一段代码，优化级别改变行为

`unio1->FuncA()` 即使函数体不碰成员，**标准上也属于 UB**（通过空指针调用成员函数）。

| 环境 | 表现 |
| --- | --- |
| GCC `-O0` | 正常输出，看起来没问题 |
| GCC `-O2` | 可能把整个调用当死代码删掉（编译器假设 `this` 永远非空） |
| `-fsanitize=undefined` | 报 `member call on null pointer` |

**UB 不是「崩溃或正常二选一」，而是「编译器拥有解释权」。**

## 九、延伸考点

### ① 虚析构函数

有虚函数的类如果可能被继承，析构必须是 `virtual`，否则 `Base* p = new Derived; delete p;` 不会执行派生类析构 → UB。

### ② 构造/析构期间 vptr 会被改写

构造基类时 vptr 指向基类虚表，构造派生类时改成派生类的。**这就是「构造函数里调用虚函数不会多态」的底层原因。**

### ③ 去虚化（devirtualization）

编译器能确定动态类型时可绕过虚表直接调用（甚至内联）。例如 `unio3.FuncC()` 中 `unio3` 是栈上具体类型对象，可能根本不查表。

**所以「虚函数一定查表」要打折扣**——真正的开销往往来自「无法内联」，而非查表本身。

### ④ `sizeof` 计算

64 位下 `sizeof(unio) == 16`（vptr 8 + `char*` 8）。若没有虚函数则是 8。

## 十、面试话术

> 「三个调用都会崩，但崩的位置不一样。
>
> `unio2->FuncB()` 崩得最早——虚函数走 `this → vptr → vtable`，第一条指令就是读 `this` 处的 vptr，`this` 是空指针等于读地址 0，直接访问违例，**它连函数体都没进去**。
>
> `unio1->FuncA()` 是非虚函数，静态绑定，能进入函数体；但函数里操作了成员 `c`，要算 `this + offset`。因为类有虚函数，`c` 的偏移是 8 不是 0，所以读写地址 8，同样在空指针保护页里，也会崩。
>
> `unio3.FuncC()` 最麻烦：对象有效、vptr 由编译器生成的默认构造函数正确初始化了，但 `char* c` 是 POD 成员、默认初始化不处理，所以是野指针。这时崩不崩取决于那个垃圾值——可能崩，也可能踩到别人的内存，在不相关的地方才出问题。如果函数里是 `delete[] c`，直接堆破坏。
>
> 修法是 `unio unio3{}` 做值初始化，或者给成员写 `char* c = nullptr;`。」

**主动反问一句「函数里对 c 是读、写还是释放」**，说明你意识到「访问成员」和「解引用成员」是两件事——这是这题最容易拉开差距的地方。
