# TCP 与 UDP 的区别与游戏选型

## 一句话区别

TCP 是**面向连接的可靠字节流**；UDP 是**无连接、不保证可靠的数据报**。

## 对比表

| 维度   | TCP                | UDP             |
| ---- | ------------------ | --------------- |
| 连接   | 面向连接（三次握手）         | 无连接             |
| 可靠性  | 可靠：确认应答、超时重传、去重、排序 | 不可靠：不保证送达与顺序    |
| 传输单位 | **字节流（无边界）**       | **数据报（保留边界）**   |
| 首部开销 | 20 字节起             | 8 字节            |
| 拥塞控制 | 有                  | 无               |
| 流量控制 | 有（滑动窗口）            | 无               |
| 传输顺序 | 保证                 | 不保证             |
| 通信模式 | 仅一对一               | 一对一 / 一对多 / 多对多 |
| 延迟   | 较高                 | 较低              |
| 典型应用 | HTTP、文件传输、回合制      | 实时对战、音视频、DNS    |

## 字节流 vs 数据报：边界的意义

对比表里「传输单位」那一行是最本质的差异，值得单独展开。

### 有边界 vs 无边界

- **TCP 是字节流**：应用层看到的是一条**连续的字节序列**，传输层里根本不存在「消息」这个概念。收发次数**没有对应关系**——两次 `Send` 可能被一次读到（N:1），一次 `Send` 也可能被拆成多次读到（1:N）。
- **UDP 是数据报**：每次 `sendto` 就是一个**独立报文**，收发**严格一对一**。要么完整收到，要么完全没收到，两个报文绝不会粘在一起。

`SOCK_STREAM` / `SOCK_DGRAM` 描述的是「**应用层与传输层之间怎么交付数据**」，不是链路层的物理特性。所以更准确的表述是：**TCP 向应用层提供字节流接口，UDP 提供报文接口。**

### 读不完的时候，行为完全相反

| 场景 | TCP `recv(buf, n)` | UDP `recvfrom(buf, n)` |
| --- | --- | --- |
| 缓冲区装得下 | 读走 n 字节 | 读走整个报文 |
| **缓冲区装不下** | **未读部分留在内核缓冲区，下次继续读** | **超出部分直接丢弃，无法补读** |

→ 所以 UDP 的接收缓冲区必须按**最大报文长度**预留（一般 ≥ 1500 字节，即 MTU），否则会静默丢数据——这个坑比粘包更容易被忽略。

### 由此推出：粘包是 TCP 独有的问题

**它不是 bug，是字节流的必然结果**——流里没有边界信息，所以「消息从哪切开」必须由应用层自己划定。

| 划界方案 | 做法 | 适用 |
| --- | --- | --- |
| **长度前缀** | 消息头固定字节写长度，先读头再读体 | 最常用，通用性强 |
| 定长消息 | 每条消息固定长度 | 结构简单的协议 |
| 分隔符 | 用 `\n` 等特殊字符分隔 | 文本协议（如 Redis 协议） |

## 游戏为什么选 UDP（面试核心）

### 队头阻塞（Head-of-Line Blocking）

TCP 保证**顺序**，所以一个包丢了，后面的包必须**等它重传**才能交付——即使后面的数据早就到了。

对实时对战来说，**过期的位置数据毫无价值**：宁可丢掉，也不要为了等一个旧包而卡住后续所有数据。

### TCP 的可靠性在这个场景反而是负担

- **重传机制**引入不可控延迟
- **拥塞控制**会在网络波动时主动降速，对游戏是灾难

### Nagle 算法的坑

TCP 默认开启 Nagle 算法：把小包攒起来一起发，以减少网络开销。这对游戏是灾难（凭空增加延迟）。

→ 若必须用 TCP 做实时通信，要设 `socket.NoDelay = true` 关闭 Nagle。

### 业界方案：UDP + 自研可靠性

纯 UDP 完全不可靠也不行，所以主流做法是**在 UDP 之上自己做可靠性**：

- **只对关键消息做可靠传输**：如「开火」「购买装备」「技能释放」——丢了必须重发
- **状态同步类消息允许丢包**：下一个包会带更新的状态，无需重传

代表实现：**KCP**、**ENet**、Unity 官方的 **UTP**——四个零件的完整拆解见 [[可靠 UDP 与 KCP 原理]]。

## 两个易错点

### 1.「UDP 会粘包吗」→ 不会，但会截断

- **粘包是 TCP 独有的**：字节流没有消息边界，两次 `Send` 可能被一次 `Receive` 收到（Nagle + 内核缓冲合并）
- **UDP 的对应坑是截断**：接收缓冲区小于报文长度时，超出部分被**静默丢弃**，不发任何错误——所以 UDP 的 buf 要按最大报文预留

（机制详见上文「字节流 vs 数据报」一节。）

### 2. 三次握手 / 四次挥手（了解即可）

- **三次握手**：确认双方的收发能力都正常
- **四次挥手**：TCP 是全双工，两个方向要各自关闭
- **TIME_WAIT**：主动关闭方等待 2MSL，确保最后的 ACK 能到达

客户端岗极少深问，知道结论即可。

## 面试答题模板

> "TCP 面向连接、可靠、是字节流，有确认重传、拥塞控制和流量控制，首部 20 字节；UDP 无连接、不可靠、是数据报，首部 8 字节，没有这些机制。
>
> 对游戏来说关键是 **TCP 的队头阻塞**——一个包丢了，后面的包必须等重传，而游戏的位置数据是有时效的，过期就没有价值了，所以宁可丢包也不等。这就是实时对战用 UDP 的原因。
>
> 但 UDP 完全不可靠也不行，所以业界做法是**自研可靠 UDP**——把 TCP 那套序列号、ACK、重传、滑动窗口搬到用户态重写一遍，因为放在内核里就改不动了。比如 KCP：对关键消息做可靠传输，对状态同步允许丢包。
>
> 另外要注意，**粘包是 TCP 独有的问题**——TCP 是字节流没有消息边界，两次 Send 可能被一次 Receive 读到，所以必须由应用层自己用长度前缀划界；而 UDP 是数据报，天然保留边界，它的坑是另一头：缓冲区小于报文长度时超出的部分会被静默丢弃。"
