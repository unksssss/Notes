# 可靠 UDP 与 KCP 原理

## 先纠正认知

**UDP 本身不保证任何可靠性。** 所谓「可靠 UDP」是**在 UDP 之上、由应用层自己实现**的一套机制。

| | 可靠性实现在哪 | 可配置性 |
| --- | --- | --- |
| **TCP** | **内核** | 几乎改不动 |
| **可靠 UDP** | **用户态**（你的代码 / KCP 库） | 参数全部可调 |

→ 自研的意义不是「更可靠」，而是**能按业务需要取舍**。

## 为什么不用现成的 TCP

TCP 的可靠性是「**全有或全无**」，五个致命点：

1. **队头阻塞**：一个包丢了，后面已到达的包必须等它重传才能交付
2. **无法放弃**：3 秒前的位置数据重传回来毫无价值，但 TCP 照样重传
3. **重传时机不可控**：RTO 算法面向吞吐而非延迟
4. **拥塞控制不可控**：一次丢包就猛烈降速，对实时对战是灾难
5. **建连开销**：三次握手，短连接场景不划算

→ 游戏要的语义是：**「大概率会收到、而且很及时、实在来不及就不要」**
→ TCP 给的语义是：**「你一定会收到，但可能很晚」**

## 四个核心机制

| 机制 | 作用 | 关键细节 |
| --- | --- | --- |
| **序列号** | 检测丢包 / 乱序 / 重复 | 每个包递增编号；收到 1、2、4 就知道 3 丢了 |
| **ACK 确认** | 告知发送方接收情况 | **累积确认**（ACK 4 = 4 之前都收到）；**位图确认**（精确到单个包，弱网下更有效） |
| **重传** | 补发丢失数据 | 超时重传 / 快速重传；RTO 系数与重传阈值都可调 |
| **滑动窗口** | 控制发送速率 | 限制同时在途的包数；可关闭拥塞控制（KCP 支持） |

**这四个零件 TCP 全都有**——区别只在于它们在用户态，参数由你定。

### 一次丢包的完整走查

发送 `Seq = 1~5`，其中 3 在链路丢失：

| 步骤 | 发生了什么 |
| --- | --- |
| ① | 接收方收到 1、2 → 交付应用 |
| ② | **3 在链路丢失** |
| ③ | 4、5 到达，但**不能交付**（顺序未满足），暂存在接收缓冲区 |
| ④ | 接收方回 `ACK = 3`（累积确认：我还在等 3）+ 位图（4、5 已到） |
| ⑤ | 发送方据此重传 3 |
| ⑥ | 3 到达 → 3、4、5 **一起**交付应用 |

→ 第 ③ 步就是**队头阻塞**的现场：4、5 早就到了，却因为 3 没来而卡住。

### 1. 序列号：给每个包定位

三个用途：**检测丢包**（收到 1、2、4 → 3 没了）、**检测重复**（连续两个 2 → 丢弃后一个）、**乱序重排**（4 比 3 先到 → 缓冲等 3）。

⚠️ **TCP 的序号是「字节序号」，不是「包序号」**——这是最容易答错的点：

- **TCP**：面向字节流，序号按**字节**累加。起始字节 `Seq = 1`，若该包携带 1000 字节，下一个包就是 `Seq = 1001`。所以 TCP 的序号表示**「本包第一个字节在整个流中的位置」**
- **可靠 UDP**：面向数据报，按**包**编号（1、2、3…）——因为边界本来就存在

### 2. ACK：把接收情况回报给发送方

| 方式 | 含义 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **累积确认** | `ACK = 4` 表示「4 之前全部收到」 | 丢一个 ACK 不影响，后续能覆盖 | **说不清 4 之后哪些已到** |
| **位图确认** | 明确列出已收到的序号（如 `1011`） | 精确，弱网下能精准重传 | 包体略大 |

- **TCP 默认只用累积确认**（SACK 是扩展选项）
- **KCP 两者都用**：收到包后把序号记进列表，下次发送时打包成 ACK 列表回传 → 弱网下不瞎重传

### 3. 重传：把丢失的补上

| 方式 | 触发条件 | 速度 |
| --- | --- | --- |
| **超时重传** | `RTO` 计时器到期仍未收到 ACK | 慢——RTO 通常几百毫秒 |
| **快速重传** | 收到 **3 个重复 ACK**（对方一直在说「我在等 3」） | 快，不用等超时 |

**为什么阈值是 3 而不是 1**：只等 1 个容易被偶发乱序误导——包可能只是晚了，并没丢，重传纯属浪费带宽。3 是个平衡点。

→ **KCP 敢用 1**（`fastresend = 1`），因为游戏场景能容忍少量无效重传，换来更低的延迟。

### 4. 滑动窗口：决定在途包数

**为什么需要它**：停等协议（发一个 → 等 ACK → 再发下一个）的吞吐被 RTT 卡死——RTT 100ms 时一秒最多发 10 个包，链路再宽也没用。窗口允许**多个包同时在途**，把等待摊薄到多个包上。

窗口能开多大，由两个值**取小**决定：

| 来源 | 谁在管 | 保护谁 |
| --- | --- | --- |
| **接收窗口 `rwnd`** | 接收方在 ACK 里告知缓冲区余量 | 保护**接收方**不被打爆 |
| **拥塞窗口 `cwnd`** | 发送方按丢包情况自己推算网络容量 | 保护**网络**不被堵死 |

→ **实际发送窗口 = `min(rwnd, cwnd)`**

**窗口为 0** 表示接收方缓冲区已满，发送方停发并定期发窗口探测包。

### 流量控制 vs 拥塞控制（别混）

| | 怕什么 | 谁推算 | 对应窗口 |
| --- | --- | --- | --- |
| **流量控制** | 把**对面**撑死 | 接收方（点对点，有发言权） | `rwnd` |
| **拥塞控制** | 把**中间的网络**堵死 | 发送方（系统性，自己估算） | `cwnd` |

→ KCP 可以**关闭拥塞控制、改用固定窗口**：游戏流量通常只有几十 KB/s，从来不是网络拥堵的元凶，没道理为了照顾别人牺牲自己的延迟。这又回到「可配置」的价值。

### 分片与重组

一个逻辑消息超过 MTU 时切成多个 UDP 包，**每个分片单独编号**：

- 丢哪个分片，只重传那一个，而不是整个报文
- TCP 在内核里做同样的事，但你控制不了它的重传时机

## KCP 比 TCP 快在哪

| 维度 | TCP | KCP |
| --- | --- | --- |
| RTO 系数 | 超时后 **×2** 递增 | **×1.5**，重传更早 |
| 快速重传阈值 | 3 个重复 ACK（约等于跳过 2 个后续包） | **`fastresend` 可设为 1**，跳过 1 个就重传 |
| 拥塞控制 | 强制开启 | **可开关**（`ikcp_nodelay` 参数） |
| 实现位置 | 内核 | 用户态，需自行配合 UDP socket |

**本质是「用带宽换延迟」**：更激进的重传意味着更多冗余流量，在弱网下换来更低的延迟。

⚠️ 代价：KCP 的冗余流量不小，不适合大流量传输（如下载、大文件同步）。

## 主要方案对比

| 方案 | 特点 | 典型场景 |
| --- | --- | --- |
| **KCP** | 纯算法库，无连接管理，需自行配合 UDP socket；重传激进 | 国内游戏最常用 |
| **ENet** | 自带连接管理与多通道（channel） | 开源引擎常见 |
| **UTP**（Unity Transport） | Unity 官方，提供 Reliable / Unreliable 两种 pipeline | Netcode for GameObjects、Mirror 的底层 |
| **QUIC** | 用户态完整传输层，0-RTT、多流复用、解决队头阻塞 | HTTP/3，部分新项目 |

## 关键设计：选择性可靠

**不是所有数据都值得重传**——这才是自研最核心的价值所在。

| 通道 | 数据 | 理由 |
| --- | --- | --- |
| **可靠通道** | 技能释放、开火指令、道具使用、交易结算、聊天、登录匹配 | 丢一次就是逻辑 bug |
| **不可靠通道** | 位置与朝向、移动输入采样、非关键特效、动画状态 | 新的会覆盖旧的，重传反而有害 |

同一连接上可以并存多条通道，按消息类型分流——UTP 里叫 `pipeline`，ENet 里叫 `channel`。

### 冗余发送：不靠重传也能抗丢包

对关键输入（如 FPS 的射击指令），可以把**最近几帧的输入一起打包发送**：丢一包不影响，收到的包自带历史。

这是「多发几次」代替「重传等待」的思路，弱网下比等 ACK 更快。

## 面试答题模板

> "UDP 本身不保证可靠，「可靠 UDP」其实是把 TCP 那套机制搬到应用层重做一遍——序列号检测丢包乱序，ACK 做确认，超时或跳过确认就重传，再用滑动窗口控制发送速率，窗口大小取接收窗口和拥塞窗口的较小值。之所以不直接用 TCP，是因为 TCP 的可靠性是全有或全无：队头阻塞会让后面的包一起等，而且你没法告诉它「这条消息不重要，别重传了」。
>
> KCP 就是这类方案的典型，它比 TCP 快的核心是用带宽换延迟——RTO 只乘 1.5 倍而不是 2 倍，快速重传阈值可以设成跳过 1 个包就重传，而且拥塞控制可以关掉。
>
> 但真正的设计重点不是快，是**选择性可靠**：技能释放、交易这类丢一次就是 bug 的消息走可靠通道，位置、朝向这类「新的会覆盖旧的」走不可靠通道，两条通道在同一个连接上并存。"

## 自测四问

1. TCP 的序号为什么不是 1、2、3，而是按字节累加？
2. 累积确认和位图确认，各自的盲区是什么？
3. 快速重传为什么需要「3 个重复 ACK」才触发？等超时不是更简单？
4. `min(rwnd, cwnd)` 里，哪个是流量控制、哪个是拥塞控制？

> 第 3 题最关键：**等超时太慢**（RTO 几百毫秒），而只等 1 个重复 ACK 又容易被偶发乱序误导——3 是平衡点；KCP 敢用 1，是因为游戏场景能容忍少量无效重传。
