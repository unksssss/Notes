题目：给 4 个数，用 `+ - * /` 和括号、每数恰好一次，判断能否得 24（牛客 BM64 / LC 679）。

#### 2. 根因一：`int` 存中间结果 = 凭空造出一种假运算

```cpp
// ❌ 灯皇原版
if (num[i] != 0) { temp.push_back(num[j] / num[i]); ... }   // int / int → 向零截断
```

`int / int` 不是数学除法：`12/8 = 1`（真 1.5）、`1/5 = 0`（真 0.2）。后果是**双向**的 —— 既漏判（`1 5 5 5` 的 `5*(5-1/5)` 需要 0.2）又误判。

实测 `1..13` 随机四数 **20000 组**（与分数精确解对比）：

| 类别 | 组数 | 占比 |
| --- | --- | --- |
| 误判（应 false 却 true） | **2868** | 14.3% |
| 漏判（应 true 却 false） | 38 | 0.19% |
| 合计 | 2906 | **14.5%** |

而 12 个手选用例**只错 1 个**（`1 5 5 5`）→ 手挑选例几乎测不出精度 bug。

完整假路径（实测追出，输入 `8 12 13 1`，真实无解）：

```text
int  版：12/8 = 1      → 13-1 = 12    → 12+12 = 24    → true  ❌
double：12/8 = 1.5     → 13-1.5 = 11.5 → 11.5+12 = 23.5 → false ✅
```

**修复**：换 `double`，比较与判零都用 eps。

```diff
- bool dfs(vector<int>& num) { ... if (num[i] != 0) cand = num[j] / num[i]; ... }
+ bool dfs(vector<double>& a) {
+     if (a.size() == 1) return fabs(a[0] - 24.0) < 1e-6;      // ★ 不能用 ==
+     ...
+     if (fabs(y) > 1e-9) cand[m++] = x / y;                    // ★ 判零用 eps
+     if (fabs(x) > 1e-9) cand[m++] = y / x;
+ }
```

实测 `double` 版与分数精确版在 2 万组上 **0 差异**。要绝对精确则上分数类（`long long p/q` 约分）。

#### 3. 根因二：`num.size() - 1` 无符号下溢 → 死循环

```cpp
for (int i = 0; i < num.size() - 1; i++)   // size() 返回 size_t
```

`size() == 0` 时 `0-1` 下溢成 `18446744073709551615`，`int i` 被提升为 `size_t` 后比较恒真 → **实测 2 秒不返回**。修法三选：`i + 1 < num.size()` / `(int)num.size()` 强转 / 开头 `if (num.size() < 2) return ...` 提前挡。

> 这是「无符号减法下溢」的通病，凡是 `xxx.size() - k` 出现在循环条件里都该警惕。

#### 4. 方法论沉淀：随机对拍（本次已补强进笔记）

今天真正的收获不是这道题，而是**「怎么证明自己写对了」**。手选用例 12 个只错 1 个，随机 2 万组错 14.5% —— 说明精度类 bug 的验证只有一条路：

1. **三件套**：精确基准（分数版）+ 待测实现 + 随机生成器（值域覆盖题目真实范围 1~13）；
2. **固定种子**并打印，出差异能原地复现；
3. **第一个反例就 break**，一次修一个；
4. **差异用例手动缩到最小**（本题缩到 `12 8 13 1` 才看清丢的是 0.5）；
5. **别只比 bool**，把两版中间结果一起打出来，才知道错在哪一步。

## Ideas

- **「数值类型体检」清单**：只要代码里出现 `/`、`sqrt`、大数、取模，先问三句 —— 需要小数吗？比较需要 eps 吗？边界会下溢吗？今天的两个坑全在这三句里。
- **精度 vs 确定性是一对**：`int` 截断是「精度不够」，Day 63 的 Q2（帧同步禁用 float）是「精度不可复现」。前者害自己，后者害队友。
- 把「随机对拍」做成刷题固定收尾动作：每道数值/边界题跑 1e4 组，比反复读代码有效得多。
- 手挑选例的心理陷阱：**挑用例时会下意识避开自己不确定的输入**，所以手选用例永远覆盖不到 bug —— 这跟「自己 review 自己的代码」是同一个问题。
