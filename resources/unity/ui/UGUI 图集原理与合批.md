# UGUI 图集原理与合批

> 来源：牛客零跑 U3D 面经真题"用过图集吗？图集为什么能优化？"；CSDN《Unity GUI优化》《uGUI性能优化全解析》（Day 37 面经，首学）

## 图集为什么能优化

**GPU 痛点**：每张图都是独立纹理 → GPU 画完一张要**切换纹理**才能画下一张。切换纹理 = 渲染状态切换 = 批次被拆开，各自一个 DrawCall。

**图集魔法**：几十张小图**预先拼进一张大纹理**（2048×2048 之类），每个 UI 元素只引用大图上的**一小块区域（UV）**。所有元素**共享同一张纹理** → 满足 UGUI 合批条件（同 Canvas + 同材质实例 + 同纹理）→ 相邻同深度的元素合并成一个 DrawCall。

- 类比：每张小图 = 一支笔（换笔=切纹理=状态切换）；图集 = 多色圆珠笔，按一下换色，手不换笔 → 写字（DrawCall）连贯
- 相关：[[UGUI多级UI性能优化与Canvas重建]]

## 图集的代价（面试追问）

1. **尺寸上限**：移动端单张纹理通常限 **2048/4096**。图多了必须拆多张 → **不同图集之间又不能合批**
2. **内存占用**：图集纹理 = 宽×高×字节数，**整张常驻显存**；拼不满有**空白浪费区**；同屏用不到的图也一起占内存
3. **加载粒度**：A/B 界面图全塞一张 → A 加载时 B 的图也被拽进内存 → **按界面/功能分组打包**（配合 Addressables/AB 按需加载卸载）

**打包黄金法则**：同屏同组的图放一起、按界面分组、超大图（全屏背景）单独留、需要热更的小图单独成集。

## Mask vs RectMask2D（真实面经高频）

| | Mask | RectMask2D |
|---|---|---|
| 裁剪原理 | **模板缓冲（Stencil Buffer）** | **shader 矩形裁剪**（计算裁剪矩形范围） |
| 合批影响 | **强制打断合批**，子物体及后续同层 UI 无法与之前元素合批 | 只要子物体材质支持就**不打断合批** |
| 额外 DrawCall | 有 | 无 |
| 形状 | 任意形状（需配图） | 仅矩形 |
| 选型 | 需要圆形/异形遮罩时才用 | **矩形遮罩（滚动列表/头像框）无脑优先** |

> RectMask2D 性能远优于 Mask；旧 Mask 是移动端 UI 合批的最大杀手之一。

## 附：UI 动静分离（姊妹篇，面试连招）

- 做法：静态元素一个 Canvas、动态元素另一个 Canvas
- **为什么**：同一 Canvas 下任意元素"脏"了，整个 Canvas 的批次要**整体重算**——静态元素即使自己没变也被迫跟着重建（"一损俱损"）。动静分离让静态 Canvas **永不脏、永不重建**
- **权衡**：分 Canvas 会打断合批增加 DrawCall，但换来了动态元素不污染静态元素；**脏的频率**越高，独立 Canvas 越值
- **分三档**：纯静态（背景框）一档 / 低频动态（偶尔跳的血条数字）一档 / 每帧高频（摇杆、跟随名字）独立一档

## 面试表达框架

1. 图集 = 多小图拼一张大纹理，共享纹理免切换 → 满足合批条件 → DrawCall 减少
2. 代价：尺寸上限、整张常驻内存、空白浪费 → 按界面分组打包
3. 补充：Mask 打断合批用 RectMask2D；动静分离控制 Canvas 重建范围
