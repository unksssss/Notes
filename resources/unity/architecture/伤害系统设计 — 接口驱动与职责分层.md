# 伤害系统设计 — 接口驱动与职责分层

## 一、问题的形状

一颗子弹飞出枪口，撞到东西了。它需要回答三个问题：

1. **打到的是什么？**（石头 / 木箱 / 敌人 / 队友）
2. **该不该扣血？**（石头扣不了，队友不该扣）
3. **扣多少、扣完怎么表现？**（掉血飘字、受击动画、死亡倒地）

如果子弹自己 `if (hit.collider.CompareTag("Enemy"))` 然后 `hit.collider.GetComponent<EnemyAI>().TakeDamage(10)`，那它就**同时知道了「谁在受伤」和「受伤是什么」**。加一个可破坏的木箱，就得回来改子弹；加一个护盾机制，又得改子弹。子弹是**投递者**，不该持有**受体的知识**。

正确的切法是三层：

```
投递层（Bullet）        →  只认 IDamageable，不知道对面是谁
协议层（IDamageable + DamageInfo）→  定义「受伤」这件事长什么样
受体层（Health + EnemyAI/Player）→  数值归 Health，表现归角色
```

## 二、协议层：`readonly struct` 当消息

```csharp
public readonly struct DamageInfo
{
    public readonly int attackDamage;
    public readonly Vector3 hitPoint;    // 击中点（飘字位置 / 特效朝向）
    public readonly Vector3 hitNormal;   // 击中点法线（弹孔贴合法线方向）
    public readonly GameObject source;   // 谁打的（仇恨、击杀归属、反击）
    public readonly int teamID;          // 阵营

    public DamageInfo(int attackDamage, Vector3 hitPoint, Vector3 hitNormal,
                      GameObject source, int teamID)
    {
        this.attackDamage = attackDamage;
        this.hitPoint = hitPoint;
        this.hitNormal = hitNormal;
        this.source = source;
        this.teamID = teamID;
    }
}

public interface IDamageable
{
    void OnDamage(DamageInfo damage);
}
```

### 为什么是 struct 而不是 class

| | `struct` | `class` |
| --- | --- | --- |
| 每次命中分配 | **0**（栈/寄存器，按值传） | 一次堆分配 + 后续 GC |
| 全自动步枪 10 发/秒 × 100 敌人 | 每秒 1000 次分配 | 每秒 1000 个垃圾对象 |
| 可变性 | `readonly struct` + `readonly` 字段 → **物理不可改** | 任意改，容易被下游篡改 |

连发武器 + 大量单位是这类消息的典型场景，堆分配会直接把 GC 压力顶上来。`readonly struct` 还有个隐性收益：**字段全 readonly 后，传参不会产生防御性拷贝**（非 readonly struct 当 `in` 参数或调成员时，编译器要拷一份防你改原件）。

### 为什么不用参数列表 `OnDamage(int dmg, Vector3 point, ...)`

今天多一个「暴击倍率」，明天多一个「元素类型」，后天多一个「是否穿透」——**每次加字段都要改接口、改所有实现类、改所有调用点**。打包成一个 struct 后，新增字段只动 struct 和真正用到它的那一两个实现。这是「**参数对象**（Parameter Object）」重构手法的直接应用。

### 为什么不用 `SendMessage("OnDamage", ...)`

`SendMessage` 靠**字符串**反射查找方法：无编译期检查（方法改名静默失效）、有反射开销、只能传单个 `object`（装箱）、且会广播给该物体的**所有**组件（包括不该收到的那几个）。接口是编译期契约，`GetComponent<IDamageable>()` 是精确查找。

## 三、受体层：数值与表现分家

```csharp
public class Health : MonoBehaviour, IDamageable
{
    private int currentHealth;
    private bool isDead = false;
    private int TeamID = -1;
    public Action<DamageInfo> OnDamaged;
    public Action<DamageInfo> OnDied;

    public void Init(int maxHealth) { currentHealth = maxHealth; }

    public void OnDamage(DamageInfo damage)
    {
        if (isDead) return;
        if (TeamID == damage.teamID) return;
        currentHealth = Mathf.Max(0, currentHealth - damage.attackDamage);
        OnDamaged?.Invoke(damage);
        if (currentHealth == 0) OnDied?.Invoke(damage);
    }
}
```

**分工**：`Health` 只做「算术 + 生死判定」，一行表现代码都没有；受击僵直、死亡倒地、飘字全在订阅方：

```csharp
// EnemyAI.Start()
health.OnDamaged += OnDamaged;
health.OnDied    += OnDied;

private void OnDamaged(DamageInfo info)
{
    isTakingDamage = true;                 // 受击僵直：Move() 里直接 return
    StartCoroutine(WaitTakingDamage());
}

private IEnumerator WaitTakingDamage()
{
    yield return new WaitForSeconds(0.3f);
    isTakingDamage = false;
}
```

好处是**同一个 `Health` 能挂给玩家、敌人、可破坏木箱**，表现各写各的；坏处是**订阅必须在 `OnDisable` 里退订**（今天的代码做到了，值得肯定——`Health` 被销毁后仍持有 `EnemyAI` 的委托会让它无法被回收）。

> `Health` 用 `GetOrAddComponent<Health>()` 挂在角色**根物体**上，因为 `Bullet` 拿到的是 `hit.collider`，而 `CharacterController` 正好是根物体上的 Collider——这一步是自洽的。

## 四、六个真实漏洞（2026-11-22 代码）

### ① `TeamID` 私有且从未赋值 → 友伤判定**恒不成立**

```csharp
private int TeamID = -1;              // 默认 -1，全项目没有任何地方赋值
if (TeamID == damage.teamID) return;  // -1 == 0 → 永远 false
```

判定写对了，但**输入是死的**。结果：敌人打敌人照样扣血。这类 bug 的特征是「**代码看起来完全正确，跑起来毫无效果**」——因为判据的一侧是常量。

修复方向：`Init(int maxHealth, int teamID)` 一起初始化，或让 `RoleBase.SetRoleInfo` 里按 `RoleType` 推出阵营：

```csharp
public void Init(int maxHealth, int teamID)
{
    currentHealth = maxHealth;
    TeamID = teamID;
}
```

### ② `Bullet` 硬编码 `teamID = 0` → 所有子弹同一阵营

```csharp
damageable?.OnDamage(new DamageInfo(attackValue, hit.point, hit.normal,
                                    this.gameObject, 0));  // 0 是写死的
```

配合 ①，即使 `TeamID` 修好了，**敌人和玩家射出的子弹仍然都算 0 号阵营**。阵营必须从**发射者**继承，而不是子弹自己决定：

```csharp
// StartMove 时把发射者的 teamID 一起带进来
public void StartMove(..., int teamID) { shooterTeamID = teamID; }
```

### ③ `isDead` 从不置 `true` → `OnDied` 会**重复触发**

```csharp
if (isDead) return;      // isDead 永远是 false，这道闸门是空的
...
if (currentHealth == 0) OnDied?.Invoke(damage);
```

血量到 0 之后，**每一发后续子弹**都会让 `Mathf.Max(0, 0 - dmg) == 0` 成立，于是 `OnDied` 再发一次。今天 `OnDied` 是空实现所以没炸；一旦填上「播放死亡动画 + 入池 + 从敌人列表移除」，就会变成**重复入池**（同一个 GO 在池里存两份 → 下次 `GetInPool` 两次拿到同一个对象，两把枪共用一个子弹）。

```csharp
if (currentHealth == 0)
{
    isDead = true;          // ← 缺这一行
    OnDied?.Invoke(damage);
}
```

**死亡的幂等性**是这类系统的必答项：`OnDied` 必须**至多执行一次**，无论之后收到多少伤害。

### ④ `currentHealth` 默认 0，且 `Player` 从未 `Init`

`Health.Init` 只在 `RoleBase.SetRoleInfo` 里被调用，而 `SetRoleInfo` 只有 `EnemyAI` 走得到（`FightingManager.OnSceneCreateEnemy` 里显式调用）。`Player` 是场景里摆好的预制体，**没人调 `SetRoleInfo`** → 玩家根本没有 `Health` 组件，`hit.collider.GetComponent<IDamageable>()` 返回 null，敌人射击玩家时 `damageable?.OnDamage` 静默跳过。

即使给玩家挂上 `Health`，`currentHealth` 默认 0 → **一枪就死**。`Init` 的调用点必须与组件生命周期绑定（`Awake` 里从配表读，或 `Start` 里兜底）。

### ⑤ `GetComponent<IDamageable>()` 只查本物体

```csharp
IDamageable damageable = hit.collider.GetComponent<IDamageable>();
```

碰撞体挂在**子物体**上时（很常见：模型子物体带 `BoxCollider`，`Health` 在根上）会返回 null。安全写法：

```csharp
IDamageable damageable = hit.collider.GetComponentInParent<IDamageable>();
```

代价是 `GetComponentInParent` 会向上遍历整条父链——但命中事件频率远低于 `Update`，可以接受。今天的代码「恰好能用」是因为 `CharacterController` 就在根物体上，属于**依赖了实现细节的正确**。

### ⑥ `Debug.LogError` 当伤害日志用

```csharp
Debug.LogError($"currentHealth: {currentHealth}, damage: {damage.attackDamage}");
```

`LogError` 会进错误统计、在很多 CI/打包配置里被当成失败、且**每次调用都带堆栈抓取**（比 `Log` 贵一个数量级）。调试期用 `Debug.Log`，正式版走条件编译或直接删。

## 五、设计取舍清单

| 决策点 | 今天的选择 | 更好的做法 |
| --- | --- | --- |
| 受体识别 | 接口 `IDamageable` | ✅ 对。可加 `IDamageable` 之外再拆 `IKnockbackable` / `IHealable`，避免接口膨胀 |
| 消息载体 | `readonly struct` | ✅ 对。字段多了可换 `in DamageInfo` 传参省拷贝 |
| 数值与表现 | `Health` 纯数值 + 事件外抛 | ✅ 对。**别让 `Health` 引用 `Animator`** |
| 阵营判定 | `TeamID` 存 `Health` 里 | 阵营属于**角色身份**，更适合放 `RoleBase` 或独立的 `TeamMember` 组件；`Health` 只读它 |
| 伤害计算 | 子弹直接算好 `attackValue` | 抗性/暴击/减伤属于**伤害管线**，应该在 `Health.OnDamage` 入口统一结算，否则每个武器都要自己算一遍 |
| 死亡处理 | 空实现 | 需要「置 `isDead` → 停 AI → 播动画 → 延时入池」，且**幂等** |

## 六、面试延伸

- **ECS 里怎么表达？** `IDamageable` 换成组件标记（`Health` 是纯数据组件），`OnDamage` 换成 System 遍历 `Health` + `DamageEvent` 缓冲。接口在这里消失，因为「谁有这个组件」本身就是查询条件。
- **为什么不用继承 `DamageableBase`？** C# 单继承，一个类既要能受伤又要能拾取，继承会打架；接口可以多实现。且继承要求「is-a」，木箱 is-a 伤害受体并不自然。
- **伤害飘字的位置从哪来？** 就是 `DamageInfo.hitPoint`——这也是把 `hitPoint`/`hitNormal` 塞进消息而不是让订阅方自己算的原因。
- **如何防止「友伤判定」这类常量 bug？** 判据两侧都不能是写死的常量；`TeamID` 应该在 `Init` 时断言 `>= 0`，未初始化直接抛异常而不是静默放行。

## 七、实战补记（2026-11-23）：组件重复创建 + `Init` 缺失

上文的六个漏洞还没修完，`Empty` 里又长出三个**更隐蔽**的，共同特征是「代码看起来都在做正确的事，但对象身上出现了两份状态」。

### ⑦ 物体上挂了两个 `Health`，子弹打到的是没 `Init` 的那个

```csharp
// RoleBase.cs —— OnEnable 里兜底创建
protected virtual void OnEnable()
{
    if (health == null) health = gameObject.GetOrAddComponent<Health>();   // ← 加了 Health #1
    if (!healthSubscribed) { health.OnDamaged += OnDamaged; health.OnDied += OnDied; }
}

// FightingManager.cs —— 装配敌人时又加了一个
var health = enemy.AddComponent<Health>();   // ← Health #2
enemyAI.health = health;                     // 字段被指向 #2
health.Init(roleInfo.Health);                // 只有 #2 有真血量
```

时序是致命的：`AddComponent<EnemyAI>()` 会在**当场**触发 `Awake`/`OnEnable`（GameObject 已激活），所以 `Health #1` 在 `AddComponent<Health>()` 之前就存在了。结果：

- 物体上有 **两个 `IDamageable`**；
- `hit.collider.GetComponent<IDamageable>()` 返回**先添加的 `#1`**（`currentHealth = 0`）；
- `#1` 收到伤害 → `Mathf.Max(0, 0 - dmg) = 0` → 立刻 `OnDied`；
- 带真血量的 `#2` 永远收不到任何伤害。

表现就是「敌人一枪死」，而且 `Debug.LogError` 打印的 `currentHealth` 一直是 0，看起来像「血量没初始化」，实际是**初始化给了另一个对象**。

**判据**：打印 `GetComponents<Health>().Length` 就知道。**修法**：`Health` 只允许一个创建点——要么 `RoleBase` 全用 `GetOrAddComponent` 兜底、外部不再 `AddComponent`；要么外部统一 `AddComponent` 且 `RoleBase` 不再兜底。二者混用必炸。

### ⑧ `healthSubscribed` 从未置 `true`

```csharp
private bool healthSubscribed = false;
// 订阅
if (!healthSubscribed) { health.OnDamaged += OnDamaged; health.OnDied += OnDied; }
// 退订
if (healthSubscribed)  { health.OnDamaged -= OnDamaged; health.OnDied -= OnDied; }
```

标志位只在声明处赋过 `false`，**没有任何一处置 `true`** → 订阅判断恒真、退订判断恒假：

- 每次 `OnEnable` 都再订阅一遍（对象池复用一次，一次伤害触发两遍回调）；
- `OnDisable` 从不退订 → 组件销毁后 `Health` 仍持有已销毁对象的委托 → 下次 `OnDamaged` 抛 `MissingReferenceException`。

`+=` 对同一个方法重复添加**不会去重**（`Delegate.Combine` 只是串链表）。修法：订阅后立刻 `healthSubscribed = true;`，退订后置回 `false`。

### ⑨ `Init` 只给敌人调，玩家血量恒为 0

`RoleBase.SetRoleInfo` 现在只存 `roleInfo`，不再 `Init`：

```csharp
internal virtual void SetRoleInfo(RoleInfo _roleInfo) { roleInfo = _roleInfo; }   // 没有 health.Init
```

而 `FightingManager` 里 `player.SetRoleInfo(roleInfos[0])` 之后**没有** `player.health.Init(...)` → 玩家 `currentHealth = 0`，被敌人打第一枪就走 `OnDied`（日志「Player Die」），之后每发子弹都重复触发。

**结论：`Init` 是生命周期的必经步骤，不能散落在装配方**。把它收进 `RoleBase.SetRoleInfo`（`health = GetOrAddComponent<Health>(); health.Init(roleInfo.Health);`）一处完成，装配方只负责「给配置」，不负责「给血」。

### ⑩ 显式 `enemyAI.health = health` 不是修复，是把坑埋深了（2026-11-24）

双 `Health` 的坑第二天被「修」成了这样：

```csharp
var health = enemy.AddComponent<Health>();   // 第二个 Health
enemyAI.health = health;                     // 把字段指向第二个
health.Init(roleInfo.Health);                // 只给第二个 Init
```

看着很合理——字段指对了、血也 Init 了。但**订阅早就绑在第一个上了**：

| | 第一个 `Health`（`RoleBase.OnEnable` 的 `GetOrAddComponent` 创建） | 第二个 `Health`（`FightingManager.AddComponent` 创建） |
| --- | --- | --- |
| `currentHealth` | **0**（从未 `Init`） | 正确血量 |
| `OnDamaged` / `OnDied` 订阅 | ✅ 有（`OnEnable` 里 `+=`） | ❌ 无 |
| `GetComponent<IDamageable>()` 命中谁 | ✅ **命中它**（返回第一个匹配） | 永远不会被命中 |

`Bullet` 走 `hit.collider.GetComponent<IDamageable>()`，`CharacterController` 挂在根节点，于是永远打到第一个 → `currentHealth = Mathf.Max(0, 0 - damage) = 0` → 立刻 `OnDied` → **一枪死，和没修一样**。

三条可迁移的判断：

1. **`AddComponent` 之后再赋字段，改不了「谁被 `GetComponent` 命中」**。`GetComponent` 按组件在 GameObject 上的挂载顺序返回第一个，跟字段指向谁毫无关系。
2. **订阅关系是不可迁移的状态**。改字段不会把委托搬过去；要么在订阅前就把引用定好，要么用 `-=` / `+=` 显式重绑。
3. **「看起来修了」比「明显没修」更危险**。这行 `enemyAI.health = health` 会让下一个人（包括三天后的自己）直接跳过这块代码。

真正的修法是**只保留一个创建入口**：删掉 `FightingManager` 里的 `AddComponent<Health>()`，把 `health.Init(roleInfo.Health)` 收进 `RoleBase.SetRoleInfo`（此时 `OnEnable` 已经用 `GetOrAddComponent` 建好并订阅了那唯一一个）。

### 由此提炼的两条通用规则

1. **一个组件只能有一个创建入口**。`GetOrAddComponent` 这种「兜底创建」写进基类生命周期后，外部任何 `AddComponent<同一组件>` 都是 bug 源——包括「我明确知道它没有所以加一个」。
2. **状态初始化必须跟着生命周期走**。`Init` 写在装配方（`FightingManager`）意味着「谁忘调谁出事」；写进 `SetRoleInfo`/`Start` 才是「漏不掉」。

### ⑪ 溢出伤害统计：`self` 字段是破抽象，正解是「用 `this`」（2026-11-25）

**症状**：目标 100 血，一发 30 伤害打在只剩 10 血时，`TotalDamage` 记的是 **30** 而不是 10 —— 溢出伤害也被算进战绩。

**第一版**（灯皇自己先改的）：给协议加受伤者字段，让 `Health` 自己去做统计。

```cs
public readonly struct DamageInfo
{
    public readonly RoleBase source;
    public readonly RoleBase self;      // ← 新增：受伤者
    // ...
}

// Bullet.Move
IDamageable damageable = hit.collider.GetComponent<IDamageable>();
RoleBase hitRole = hit.collider.GetComponent<RoleBase>();   // ← 第二次 GetComponent
damageable?.OnDamage(new DamageInfo(attackValue, hit.point, hit.normal, source, 0, hitRole));

// Health.OnDamage（此时 RoleBase.OnDamaged 里的累加被注释掉了）
damage.source.AddTotalDamageNum(trueDamageValue);
damage.self.AddTakeDamageNum(trueDamageValue);
```

**三处硬伤**：

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | 同一 Collider 查两次 `GetComponent` | 每发子弹多一次组件查找，射击高频时是实打实的开销 |
| 2 | `IDamageable` 的实现者不一定是 `RoleBase` | 可破坏物 / 炸药桶（项目里已有 `P_EXP_Barrel`）→ `GetComponent<RoleBase>()` 返回 null → `damage.self.AddTakeDamageNum()` **NRE** |
| 3 | `Health` 越权 | `Health` 只管血量，不该知道 `RoleData` 战绩统计；统计的归属是 `RoleBase`（它才持有 `roleData`） |

**关键洞察**：`RoleBase.OnDamaged(DamageInfo)` 是**实例方法**，`this` 天然就是受伤者。`self` 字段描述的信息，接收方本来就知道 —— 典型的「把接收方信息塞进消息里」。

**落地改法（4 步）**：

```cs
// 1. 协议删字段，回到 5 参数
public readonly struct DamageInfo
{
    public readonly int attackDamage;
    public readonly Vector3 hitPoint;
    public readonly Vector3 hitNormal;
    public readonly RoleBase source;
    public readonly int teamID;
}
```

```cs
// 2. Health 算完真伤后【重建】一条消息再广播
int prevHeath = currentHealth;
currentHealth = Mathf.Max(0, currentHealth - damage.attackDamage);
int trueDamageValue = prevHeath - currentHealth;

// readonly struct 在 Unity 2022.3（C# 9）没有 with 表达式，只能 new
DamageInfo trueDamageInfo = new DamageInfo(trueDamageValue, damage.hitPoint, damage.hitNormal,
                                           damage.source, damage.teamID);
OnDamaged?.Invoke(trueDamageInfo);
if (currentHealth == 0) { isDead = true; OnDied?.Invoke(trueDamageInfo); }
```

```cs
// 3. Bullet 只查一次，只依赖接口
IDamageable damageable = hit.collider.GetComponent<IDamageable>();
damageable?.OnDamage(new DamageInfo(attackValue, hit.point, hit.normal, source, 0));
```

```cs
// 4. RoleBase 恢复累加，this 就是受伤者
protected virtual void OnDamaged(DamageInfo damageInfo)
{
    this.AddTakeDamageNum(damageInfo.attackDamage);
    damageInfo.source?.AddTotalDamageNum(damageInfo.attackDamage);
}
```

**为什么是「重建消息」而不是「改字段」**：`DamageInfo` 是 `readonly struct`、按值传递，`Health` 拿到的是副本 —— 想在广播前修正伤害值只能**造一个新的**。这也正好把「原始伤害」与「真伤」两个语义分开：`Health` 内部用原始值扣血，对外只广播真伤。

> **与 ⑩ 的关系**：⑩ 给出的修法是「删掉 `FightingManager` 的 `AddComponent<Health>()`，`Init` 收进 `SetRoleInfo`」。11-25 实际落地走的是另一条路 —— **`SetActive(false)` 装配窗口**（`SetActive(false)` → `AddComponent` / 赋字段 → `SetActive(true)`）。两条路都能消除「两个 Health」，选后者的原因是：玩家场景里根本没挂 `Health`，必须保留 `OnEnable` 的 `GetOrAddComponent` 兜底，那就只能在装配期保证「兜底不会兜出第二份」。

**同日连带发现**：`RoleBase.OnEnable` 的幂等订阅写成了

```cs
health.OnDamaged -= OnDamaged;
health.OnDied    -= OnDamaged;   // ← 应该是 OnDied
```

`-=` 删一个不存在的委托**不报错、不打警告**，静默无效；而 `+= OnDied` 每次 `OnEnable` 都加一遍 → 一次击杀加 N 次击杀数。幂等订阅的正确姿势是「同一个方法名成对出现」，最好收进一对 `Subscribe()/Unsubscribe()`，肉眼 diff 就能对齐。
