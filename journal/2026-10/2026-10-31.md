### 其他技术产出（Part D）

#### 1. 手撕事件总线 → 归档成笔记（`18f6cc4`，15:15）

**产出**：`resources/csharp/事件总线实现 — 订阅令牌与发布期快照.md`（279 行），同步 `resources/_index.md` / `_tags.md` / `_graph.md`，4 files / +291 −4。

**接口**：

```csharp
SubscriptionToken Subscribe<T>(Action<T> callback);
bool Unsubscribe(SubscriptionToken token);
void Publish<T>(T data);
```

**四个关键决策（这题的骨架）**：

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 新订阅不参与本次发布 | 发布前锁定 `count`，只遍历 `[0, count)` | 新订阅追加到末尾，天然落在边界外；比 `ToArray()` 快照省掉每次分配 |
| 发布中取消 | 只标记 `IsActive = false`，**不 `RemoveAt`** | `RemoveAt` 让后面元素前移，正在遍历的索引直接错位 |
| 墓碑清理 | 只在 `_publishDepth == 0` 且 `Dead >= 8` 时压缩 | 压缩会移动元素，遍历中做必炸；倒序删避免索引前移 |
| 订阅者抛异常 | 捕获后继续，并上抛 `OnSubscriberException` | 广播不能因一个模块的 bug 全线瘫痪，也不能静默吞掉 |

**三个易被追问的实现细节**：

1. `count` 必须在进入循环前取 —— 写成 `i < entries.Count` 时，新增订阅当次就会被执行，直接违反需求。
2. 用 `Entry<T>` 而不是裸 `Delegate` —— 按 `typeof(T)` 分桶后桶内元素必然是 `Entry<T>`，强转安全；`Action<T>` 存储不装箱。
3. 嵌套发布（回调里再 `Publish` 同一 topic）—— `_publishDepth` 变 2，内层各取新的 `count` 互不影响；内层结束回 1 时不压缩，压缩只由最外层触发。

**token 设计**：`readonly struct SubscriptionToken`（`Type` + `int Id`），每次订阅零堆分配；**必须实现 `IEquatable<T>`**，否则默认 `Equals(object)` 会装箱。

**遗留/可延伸**：`Unsubscribe` 是 O(n)（要 O(1) 需再维护 `Dictionary<(Type,int), Entry>`）；当前只支持主线程发布（多线程要么整体 `lock`，要么每次 `ToArray()` 真快照，代价是分配）；订阅不取消 → 委托持有目标对象引用 → 对象无法 GC，典型泄漏，token 必须存下来在 `OnDestroy` 退订。
