# 字体与文本合批

面试题原声：「字体可以进行合批吗？」

## 结论先行

**能合批，但字体从来不是决定因素。** 决定因素仍然是 UGUI 的合批五条件：

> **同一 Canvas 下 · 同材质 · 同贴图 · 深度连续（不与其他材质元素交错）· 同裁剪矩形**

字体（或字号、样式）只要**落在同一张贴图上、共用同一个材质**，它就和同材质的其他 UI 元素一样参与合批。真正的断批元凶是**字体资产不统一**、**fallback 混用**、**材质实例化**、**和 Image 交错排布**。

## 一、Legacy `Text` 的情况

- **每个 `Font` 资产对应一张动态字体图集纹理**（运行时把用到的字形栅格化进去），同一 Font 的 Text 共享这张纹理 + 同一材质 → **能合批**。
- 同一 Font 的**不同字号**也写在**同一张**动态图集纹理里 → 所以字号不同**不影响**合批。
- 但是：
  - **换了 Font 资产** → 换了纹理 → **断批**；
  - **动态图集扩容 / 重建纹理**（新字符首次出现、图集满了要重排）→ 那一帧纹理变化，合批被打断并触发文本重建 → 表现为**偶发卡顿 + DrawCall 抖动**。

## 二、TextMeshPro 的情况

TMP 用的是 **SDF 字体资产 `TMP_FontAsset`**，每个 FontAsset 带自己的 atlas（可能多张，可以设为 Dynamic 模式运行时填充）。

| 情况 | 能否合批 |
| --- | --- |
| 同一 `TMP_FontAsset` 的多个 `TextMeshProUGUI` | ✅ 共享材质，可合批 |
| 不同 `TMP_FontAsset`（如常规体 vs 粗体、中文字体 vs 英文字体） | ❌ 不同 atlas + 不同材质 → 断批 |
| 同一段文本里**有字符来自 fallback 字体** | ⚠️ **部分断批**（见下） |
| 改了材质属性（材质实例化，如动态调 Outline/Underlay 颜色） | ❌ 破坏合批 |

### 关键机制：TMP 按 FontAsset 拆 submesh

TMP 生成网格时，会把同一段文本**按所用到的 FontAsset 切成多个 submesh**，每个 submesh 对应一个材质 → 表现为**额外的 DrawCall**。

所以：如果正文用字体 A，而其中某些生僻字走了 fallback 字体 B，那段文本就会**拆成 2 个 submesh → 2 次绘制**。这比"每个字一个 DC"好得多，但仍然是一次实打实的额外绘制。

**实践含义**：给 `TMP_FontAsset` 配好 fallback 链是必要的（否则汉字显示成方块），但要**尽量让同一个界面里的字符落在同一个 FontAsset 上**，别让 fallback 频繁接管。

## 三、为什么「字体」经常被当成破批元凶

因为最常见的断批场景是这一种：

```
[Image 背景] → [Text 文本] → [Image 图标] → [Text 文本] → ...
```

`Image` 用的是 `UI/Default` 材质，TMP 用的是 SDF shader 材质（Legacy Text 也是不同材质）→ **材质不同导致深度不连续** → 每个交错点都要切一次 → DrawCall 直线飙升。

**看起来"是字体破的批"，其实是「文本与图片交错排布」破的批。** 判断方法：看 Frame Debugger 里断批的原因是不是 "Objects have different materials"。

## 四、对比表

| | Legacy `Text` | `TextMeshPro` |
| --- | --- | --- |
| 字体资产 | `Font` + 动态字体图集 | `TMP_FontAsset` + SDF atlas |
| 同字体多字号 | ✅ 同一张图集，可合批 | ✅（同 FontAsset 内） |
| 不同字体 | ❌ 断批 | ❌ 断批 |
| 跨字体 fallback | ✅ 不适用 | ⚠️ 拆 submesh，产生额外 DC |
| 缩放/放大 | 位图放大发虚，可能触发重新栅格化 | SDF 任意缩放锐利，不重新栅格化 |
| 材质实例化风险 | 中（改 `font.material` 等） | 高（TMP 材质预设极易被实例化） |

## 五、优化清单

1. **一个界面统一字体**：别混用 2~3 个 FontAsset，这是最省事的降 DrawCall 手段。
2. **分级检查 fallback**：主字体尽量覆盖常用字，减少运行时 fallback 接管。
3. **文本与图片按层分组**：同层元素尽量同材质、连续排布，避免「图-字-图-字」交错。
4. **别改 TMP 材质属性**：需要不同外观就用**不同的材质预设**（而不是运行时改属性），或者用顶点色 / `fontSharedMaterial` 而非 `fontMaterial`。
5. **图集要预热**：把常用字符提前写进字体图集（`FontAsset.TryAddCharacters` / 编辑器预热），避免运行时扩容打断合批。
6. **验证手段**：`Stats` 看 DrawCall 总数 → `Frame Debugger` 看具体断批原因 → `Profiler` 看是否是图集扩容导致的重建。

## 六、面试答题框架

① 先纠正前提：**字体不决定合批，合批只看「同材质同贴图 + 深度连续」** → ② Legacy Text：同 Font 共一张动态图集，可合批，但扩容会打断 → ③ TMP：同 FontAsset 共享材质可合批，**fallback 会拆 submesh 产生额外 DC**，材质实例化必破批 → ④ 最常见的破批其实是「文本与图片交错」（材质不同） → ⑤ 优化：统一字体、控制 fallback、按材质分层排布、预热图集。
