# 进程与线程 — 基本概念与关系

## 一、两句话定义

> **进程 = 资源分配的基本单位**（一份独立的地址空间）
> **线程 = CPU 调度的基本单位**（进程里的一条执行流）

「资源」这个抽象词，具体指：**地址空间、页表、打开的文件句柄、信号处理器、环境变量**。

由此推出两个直接结论：

- 进程之间**天然隔离**——A 进程的指针拿不到 B 进程的内存，想通信必须走 IPC
- 线程之间**共享同一份地址空间**——传数据几乎零成本，代价是数据竞争

---

## 二、一个进程里到底装了什么

```
┌─────────── 进程（独立地址空间）───────────┐
│  代码段        数据段           堆          │  ← 全进程共享一份
│  只读指令      全局/静态变量    new/malloc  │
│ ────────────────────────────────────────── │
│  线程1        线程2          线程3         │  ← 每个线程各一份
│  栈/寄存器    栈/寄存器      栈/寄存器      │
└────────────────────────────────────────────┘
```

| 共享（进程级，一份） | 独享（线程级，各一份） |
| --- | --- |
| 代码段（指令） | **栈**（局部变量、调用链） |
| 数据段（全局变量、静态变量） | **寄存器**（含 PC 程序计数器、SP 栈指针） |
| **堆**（`new` / `malloc` 的对象） | 线程 ID（TID） |
| 打开的文件 / Socket 句柄 | 线程优先级、调度策略 |
| 信号处理器、当前工作目录 | `errno`、信号掩码 |

**面试就考这张表。** 一句话记：**「栈是私有的，堆是大家的」**——这是理解后面所有并发 bug 的地基。

## 三、四个关系要点

### ① 线程是「轻量级进程」——创建它不用复制地址空间

创建进程要做的事：分配 PCB、建立页表、复制/加载代码数据、打开标准流……很重。
创建线程只要：分配一个栈 + 一套寄存器上下文 + 一个 TID。

所以同一份数据上的并发，用线程而不是多进程。

### ② 一个线程崩了，整个进程会死

因为共享地址空间。一个线程野指针写到别的线程的数据上，或者抛出未捕获异常 → 操作系统终止的是**整个进程**，不是单个线程。

- **Chrome 每个标签页一个进程**：用进程隔离换稳定性，一个页面崩了不带走浏览器
- **Unity 是单进程多线程**：任何子线程的未捕获异常都可能带走整个游戏

### ③ 共享内存 = 通信免费，但要自己加锁

进程间传数据要序列化 + 系统调用；线程间直接读写同一个变量。代价是**数据竞争**：

```csharp
// 两个线程各执行 10 万次，最终结果可能小于 20 万
for (int i = 0; i < 100000; i++) count++;
```

`count++` 编译成「读 → 加 → 写」三步，不是原子操作。两个线程同时读到旧值、各自加完再写回，**丢一次更新**。

```csharp
// 三种修法
lock (gate) { count++; }
Interlocked.Increment(ref count);        // 硬件 CAS，无锁
Parallel.For(0, 200000, _ => Interlocked.Increment(ref count));
```

### ④ 切换开销的差别，在于「换不换地址空间」

| | 同进程内切线程 | 切到另一个进程 |
| --- | --- | --- |
| 保存/恢复寄存器、栈指针 | 要 | 要 |
| 换页表 | **不用** | 要 |
| TLB（地址翻译缓存） | 保留 | **可能失效**，后续访存要重新查页表 |
| 缓存局部性 | 较好 | 差，数据全换了一批 |

**一个反直觉的事实**：Linux 里线程和进程都是 `task_struct`，内核调度逻辑几乎一样，差别只在于是否共享 `mm_struct`（地址空间）。

所以「线程切换一定比进程切换快」这个说法，准确表述是：**同进程的线程切换省掉了地址空间切换和 TLB 失效那部分开销**。

## 四、进程间通信 vs 线程间通信

| | 进程间（IPC） | 线程间 |
| --- | --- | --- |
| 手段 | 管道、消息队列、**共享内存**、Socket、信号 | **共享变量** + 锁 / 信号量 / 条件变量 / 原子操作 |
| 数据传递 | 序列化 + 内核拷贝（共享内存除外） | 直接读写 |
| 隔离性 | 强 | 无 |
| 开销 | 高 | 低 |
| 出错后果 | 单个进程崩 | 整个进程崩 |

**共享内存是最快的 IPC**——省掉了内核拷贝，但同步要自己写。本质上是「用线程的方式在进程之间通信」。

## 五、三层对比：进程 / 线程 / 协程

| | 进程 | 线程 | 协程 |
| --- | --- | --- | --- |
| 由谁调度 | 操作系统 | 操作系统 | **你自己的代码**（Unity 主循环） |
| 是否真并行 | ✅ | ✅ | ❌ 单线程分帧 |
| 地址空间 | 独立 | 共享 | 共享 |
| 切换成本 | 高（换页表 + 可能 TLB 失效） | 中（换寄存器 + 栈） | **极低**（一次函数调用） |
| 数据竞争 | 无 | 有，必须加锁 | 无（本来就串行） |
| 适合 | 隔离、崩溃不影响他人 | 真并行计算、阻塞 IO | 等待类逻辑、分帧执行 |

一句话：**进程解决「隔离」，线程解决「并行」，协程解决「等待」。**

## 六、Unity 里的实际映射

| 场景 | 用什么 |
| --- | --- |
| 逻辑、渲染、UI、物理 | **主线程**（Unity API 只在这里安全） |
| 文件下载、解压、大量 IO、寻路计算 | 子线程 / `Task.Run` |
| 子线程算完要改 UI / Transform | **回主线程**（入队 + 主循环消费） |
| 大量同质计算（粒子、蒙皮） | Job System（受控并行，保证数据安全） |

**项目实例**：DarkGod 的 `NetSvc` 就是这条链路的教科书——

1. 网络库的收包回调跑在**线程池线程**（不是 Unity 主线程）
2. 回调里只做一件事：加锁把消息塞进队列（**不碰任何 Unity API**）
3. 主线程 `Update` 出队，按 CMD 分发到业务层

→ 这样业务逻辑天然单线程，共享数据只有队列一个，锁的范围极小。

## 七、线程不是越多越好

三个限制：

| 限制 | 说明 |
| --- | --- |
| **栈占地址空间** | Windows 默认保留 1MB / Linux 默认 8MB 虚拟内存每线程，上千线程就是 GB 级 |
| **切换有成本** | 线程数远超核心数时，CPU 大量时间花在切换而不是干活 |
| **竞争加剧** | 锁争抢、缓存行伪共享（false sharing） |

所以有**线程池**：复用线程，避免频繁创建销毁。创建线程要分配栈 + 内核对象，是微秒到毫秒级操作；从池里取一个几乎是零成本。

> 经验值：**CPU 密集型任务的线程数 ≈ 核心数**（多了纯浪费切换）；**IO 密集型**可以多几倍（线程大部分时间在等）。

## 八、面试答题模板

> 「进程是资源分配的基本单位，有独立的地址空间；线程是 CPU 调度的基本单位，是进程里的执行流，共享进程的地址空间，但各自有独立的栈和寄存器。
>
> 关系上：一个进程至少有一个线程，创建线程不用复制地址空间，所以比创建进程便宜；线程共享代码段、全局变量和堆，独享栈、寄存器和线程 ID；因为共享地址空间，一个线程抛未捕获异常会让整个进程退出——Chrome 每个标签页一个进程就是为了这个隔离性。
>
> 这也决定了两者的取舍：进程隔离性好但通信贵、要走 IPC；线程通信靠共享内存几乎免费，但要自己加锁处理竞争，比如 `count++` 就不是原子的。切换开销上，切进程要换页表、可能让 TLB 失效，同进程内切线程就不用。」

## 九、自测三问

1. 一个进程里的线程，哪些内存区域是共享的、哪些是私有的？
2. 为什么一个线程崩溃会导致整个进程退出？Chrome 怎么规避这个问题？
3. `count++` 在两个线程里各跑十万次，结果为什么可能小于二十万？三种修法分别是什么？

> 第 3 题的关键词是「**不是原子操作**」——编译成读、加、写三步，中间可能被切走。能说出 `Interlocked` 用硬件 CAS 实现、无锁，是加分项。
