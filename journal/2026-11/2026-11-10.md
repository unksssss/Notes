**2 · 真 bug：`Random.Range(-1, 1)` 走了 int 重载 → 弹道永远单边偏**

- 目标文件：`Assets/Scripts/Fightings/Bullet.cs` → `MainPlayerShoot()`
- 问题：每次开枪子弹都往**左下**偏，右侧从不偏；偏移量只有 0 或 −2.5 两种。
- 根因：`Random.Range` 有 `int` / `float` 两个重载，**`int` 版上界不包含**。`Random.Range(-1, 1)` 落在 int 重载上 → 只可能返回 `-1` 或 `0`，再乘 `accuracy = 2.5f` 得到 `{-2.5, 0}`。要连续区间必须给浮点字面量。

```diff
- float offSetX = Random.Range(-1, 1) * accuracy;
- float offSetY = Random.Range(-1, 1) * accuracy;
+ float offSetX = Random.Range(-1f, 1f) * accuracy;
+ float offSetY = Random.Range(-1f, 1f) * accuracy;
```

- 附带一处：`accuracy` 硬编码 `2.5f`，应随武器配置（`WeaponConfig`）下发，否则每把枪手感一样。
- 判断口诀：**`Random.Range(a, b)` 只要两个参数都是整数，就是「含头不含尾」的整数随机**。

**3 · 真 bug：`distance > range` 分支缺 `return` → 同一个子弹二次回池**

- 目标文件：`Assets/Scripts/Fightings/Bullet.cs` → `Move()`
- 问题：子弹超距后偶发「原地多飞一帧」甚至同一帧既超距又命中。
- 根因：超距分支里已经 `ReturnPool` 并置 `isMove = false`，但**没有 `return`**，代码继续往下走 `Physics.Raycast`；若这一帧恰好命中，就再执行一次 `ReturnPool` —— 同一个 GameObject 在池的 `List` 里出现**两份引用**，之后被两个子弹逻辑同时取用，表现是「一颗子弹打两下」或特效错位。

```diff
  if (distance > range)
  {
      isMove = false;
      ResourcesMgr.Instance.ReturnPool(bulletName, this.gameObject);
+     return;                       // ★ 回收即终态，不要再判命中
  }
```

- 同类隐患：`ReturnPool` 是「终态操作」，凡调用它的分支都应 `return` 或 `else` 掉后续逻辑。更稳的做法是池内加 `HashSet` 去重 / 给子弹加 `isReturned` 幂等标记。
- 顺带：`Debug.DrawLine(ray.origin, ray.direction * distance, ...)` 第二参传的是**方向×距离**而不是「起点 + 方向×距离」，画出来是条错误的线，调试时会误导自己。

## Ideas

- **重载陷阱是一类题，不是一道题**：`Random.Range` 的 int/float 分叉、`Mathf.Clamp` vs `Clamp01`、`Vector3.Lerp` 的 t 是否自动截断 —— 凡是「同名函数靠参数类型分派」的 API，都要问一句「我这次走的是哪个重载」。
- **「回收」必须是幂等操作**：今天这个二次回池的根因不是少写 `return`，而是 `ReturnPool` 本身允许同一对象进池两次。设计池时该把幂等性做进 API，而不是指望每个调用点都记得 return。
- **兜底特判是 bug 的遮羞布**（正则那题）和**手挑选例避开不确定输入**（11-07）是同一个心理机制：都在「绕开自己没把握的路径」，于是验证信号被系统性削弱。以后凡是想加特判，先把它当 bug 线索。
- **一处改动能多过一批用例 ≠ 改对了**：47→42→26→2→0 这条链说明多个独立 bug 会互相掩盖，逐个修时每步都"像"修好了。判断标准只能是**全量对拍归零**，不是"感觉差不多了"。
- 战斗模块的池化对象已经跨了三个文件（子弹/枪口/命中），但生命周期全靠调用方自觉。这块迟早要收口成一个 `PooledObject` 基类 + 统一回收协议。
