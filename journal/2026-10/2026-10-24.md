#### 二、平面反射：从零到「镜面没问题」

Built-in 管线没有现成的平面反射。Reflection Probe 只能反射环境（照不出角色），所以必须走 **镜像相机 + 斜投影 + RT + 屏幕空间采样**。完整原理已单独成篇 → 📎 [[平面反射 — 镜像相机、斜投影裁剪与反射贴图采样]]

**核心五步**：

```cs
// ① 镜像矩阵（关于平面 n·p + d = 0 做反射）
Matrix4x4 reflectionMat = CalculateReflectionMatrix(plane);
// ② 乘在 view 矩阵左边 = 让镜像相机看到镜像世界
reflectionCamera.worldToCameraMatrix = cam.worldToCameraMatrix * reflectionMat;
// ③ 斜投影：近裁剪面扭到镜面，只渲镜面以上
reflectionCamera.projectionMatrix = cam.CalculateObliqueMatrix(clipPlane);
// ④ 绕序翻转（镜像行列式为负，不翻则里外颠倒）
GL.invertCulling = true;
reflectionCamera.Render();
GL.invertCulling = false;
```

**Shader 侧**只有一句关键：`float2 reflUV = i.screenPos.xy / i.screenPos.w;` —— `ComputeScreenPos` 给的是齐次坐标，**必须除 w**，否则全屏一个色。因为镜像相机与主相机共用一套投影参数，屏幕像素与 RT 像素天然一一对应，不需要任何世界坐标变换。

**踩的两个坑**：

1. `clipPlaneOffset = 0` 会让镜面自身被渲进倒影（递归噪点）→ 抬 0.07，并把镜面单独一层从 `cullingMask` 剔除
2. `OnWillRenderObject` 会被 **Scene 视图相机**触发，而 Scene 视图是**正交**投影 → `CalculateObliqueMatrix` 在正交下算出退化近裁剪面（w ≈ 1.8e6）→ Console 每帧刷 `Screen position out of view frustum (screen pos 0,0,1835012)`。Game 视图倒影其实是好的，纯噪音。修法是按 `cameraType` 过滤 `SceneView / Preview / Reflection`，主相机 `orthographic` 也直接跳过

#### 三、天花板穿透：检测和推进不在同一个时钟上

**现象**：跳跃上升时头直接穿出薄天花板，`TrackSensor` 完全来不及反应。

**根因**：`TrackSensor` 在 **Update** 采样，物理在 **FixedUpdate** 推进。上升速度 `8.5 m/s`，一个物理帧位移 `8.5 × 0.02 = 0.17 m`——比天花板厚度还大，整段跨过去，中间没有一帧处于「相交」状态。

**修法**：把「归零速度」交给**碰撞回调**，而不是 Update 里的检测。

```cs
// PlayerMotor
public void StopRise()
{
    Vector3 v = rb.velocity;
    if (v.y <= 0f) return;      // 下落中不干扰
    v.y = 0f;
    rb.velocity = v;
}

// PlayerRoot：Enter 管首次接触，Stay 防止贴住后被再顶
private void OnCollisionEnter(Collision c) => HandleCeilingContact(c);
private void OnCollisionStay(Collision c)  => HandleCeilingContact(c);
```

碰撞回调由物理系统在**求解碰撞的同一时刻**给出，此时速度还没积分到下一帧，在这里清零才掐得住。详见 📎 [[Update-FixedUpdate-LateUpdate执行时机]]

> ⚠️ 前提：`Layer Collision Matrix` 里天花板层与玩家层必须勾选碰撞，否则物理根本不接触，回调也不会触发。

#### 四、per-actor 重力倍率：Unity 没有 Gravity Scale

灯皇原话：「gravity 有点小了，怎么调大一点」。

`Rigidbody.useGravity` 只有开关，大小只能改全局 `Physics.gravity`。做法是每物理帧补一份**差额加速度**：

```cs
// extra = |g| × (scale - 1)；scale < 1 时 extra 为负，down × 负 = 向上
float extra = Physics.gravity.magnitude * (config.gravityScale - 1f);
if (Mathf.Abs(extra) < 0.001f) return;
rb.AddForce(Vector3.down * extra, ForceMode.Acceleration);
```

用 `ForceMode.Acceleration` 忽略质量，和真实重力表现一致；`useGravity == false`（吸附中）直接跳过。

**调参公式**（`T = 2v/(g·k)`、`H = v²/(2g·k)`）：

| 想保持 | 初速怎么改 | `k=1.5` | `k=2.0` | `k=2.5` |
| --- | --- | --- | --- | --- |
| 跳高不变 | `v' = v × √k` | 7.35 | 8.49 | 9.49 |
| 滞空不变 | `v' = v × k` | 9.0 | 12.0 | 15.0 |

（`normalJumpForce` 原为 6）**只改 k 不改 v，手感会变成「跳得又快又矮」**，两个必须一起动。

#### 五、TrackSensor 的两次迭代：多段取舍 → 水平投影 → 被否决

**迭代一（14:05）：循环覆盖 → 多段取舍**

探测球有半径，站接缝上会同时罩住两段跑道。原来在循环里直接覆盖 `probe`，最终留下哪段取决于碰撞体返回顺序——**随机的**，表现为接缝处颜色判定忽对忽错、极难复现。

```cs
bool found = false;
float bestEdge = 0f;

for (int i = 0; i < n; i++)
{
    if (!buffer[i].TryGetComponent<TrackPiece>(out var piece)) continue;
    Bounds bounds = buffer[i].bounds;

    float edge = isCeiling ? bounds.min.y : bounds.max.y;   // 地面看顶面，天花板看底面
    bool isBetter = !found || (isCeiling ? edge < bestEdge : edge > bestEdge);
    if (!isBetter) continue;                                 // 地面取最高，天花板取最低

    found = true; bestEdge = edge; colorIndex = piece.ColorIndex;
}
```

**迭代二（14:52）：加水平投影判断**

`OverlapSphere` 是球体探测，**分不清「从下面顶上去」和「撞在侧面」**。撞方块前壁时头点在方块的 Y 厚度内、球也罩得到，但身体在方块外侧 → 被判成吸附 → 人被拉到方块底面下方，水平位置还在外面 → 视觉上「吸在侧面上」。

修法是加 `IsHorizontallyOver()`：探测点 XZ 必须落在碰撞体 bounds 的 XZ 范围内（容差 0.1m）。

**迭代三（14:58）：被灯皇否决，改成只对地面生效**

灯皇原话：「我觉得你这个方法还是不行，**直接设置玩家的 Y 值就行了**」。

他的思路更对：撞到天花板（不管底面还是侧面）→ 直接把 Y 压到方块下方 → 从底下钻过去，这才是跑酷该有的手感。于是：

- `IsHorizontallyOver` **只对地面生效**（防贴侧壁误判落地），天花板不判
- `PlayerMotor.HoldAtY` 改为**当帧立即落位**（`rb.position.y = holdY`），不再等下一个 FixedUpdate——否则撞侧面那一帧还有「贴壁」观感，物理仍在挡前进

> 经验：**涉及手感的判断，先按灯皇的直觉走**。「直接设 Y」本质是「撞到就钻到下面」，比抽象的判定条件更贴近玩家体验。

#### 六、相机侧视角：不只是换 offset

灯皇原话：「这个 cameraFollow 有问题，应该是在角色的侧面，而不是正后方」。

**根因**（不只是 offset 方向）：原脚本只做位置 `SmoothDamp`，**从不旋转**。offset 在正后方时朝向碰巧能看住角色；一挪到侧面，位置变了朝向没变，角色直接跑出画面。

改动三处：

```cs
// ① 默认侧后 3/4 视角
private Vector3 offset = new Vector3(7f, 4f, -3f);

// ② 每帧朝向角色（焦点抬高，让角色居中而非贴上边缘）
Vector3 focus = target.position + Vector3.up * lookAtHeight;
transform.rotation = Quaternion.LookRotation(focus - transform.position, Vector3.up);

// ③ 转向用指数插值，帧率无关
float t = 1f - Mathf.Exp(-Time.deltaTime / rotationSmoothTime);
transform.rotation = Quaternion.Slerp(transform.rotation, desiredRot, t);
```

`1 - exp(-dt/t)` 替代 `Slerp(a, b, dt * speed)`：后者在 60fps 与 144fps 下**每秒实际转向量不同**，手感不一致。另加 `OnDrawGizmosSelected` 画相机→焦点连线，方便调 offset。

##### ③ `HandleJump` 改了状态却不发 `StateChanged` —— Animator 的 `Grounded` 卡在 true

```cs
private void HandleJump(PlayerInput input)
{
    if (!input.JumpPressed) return;
    if (state == PlayerState.Grounded)
    {
        motor.Jump(config.normalJumpForce);

```

**连锁反应**：`PlayerAnimator` 只在 `StateChanged` 里 `SetBool(Grounded, false)`。这里跳过了广播 → Animator 里 `Grounded` 一直是 `true`。下一帧 `EvaluateSurfaces` 又因为 `state` 已经是 `Airborne` 而跳过广播（`if (state != Airborne)` 不成立）→ **`run --Grounded==false--> jump_over` 这条转移永远不触发**，只能靠 `jump_start --Has Exit Time--> jump_over` 兜底。

```cs
// ✅ 修法：状态变更统一走一个私有方法，避免「改了忘了广播」
private void SetState(PlayerState next)
{
    if (state == next) return;
    state = next;
    StateChanged?.Invoke(next);
}
```

> `EvaluateSurfaces` 里那三条分支已经写成「只在真变化时发事件」了（否则 `OnLanded` 每帧累加、`landingStreak` 秒满、rush 失效），但 `HandleJump` 这条旁路漏了。**状态机只要允许「直接给 state 赋值」，就一定会漏**。

#### 八、关卡流水线：从手搭到一键生成

**架构选择**：同一场景里**换关卡 Prefab**，而不是切 Scene。

- 不用处理 `SceneManager` 异步加载、`GameManager` 跨场景存活
- 循环关卡只是索引取模：`currentIndex = ((index % len) + len) % len`
- 计时器（`GameTime`）不会因为切场景被销毁

**两个顺序坑（都已修）**：

1. `PlayerRoot` 的初始定位从 `Start()` 移到 **`Awake()` 末尾** —— `LevelManager` 也在 `Start` 里 `ResetPlayer`，两个 `Start` 顺序不确定，玩家的 `Start` 若后执行会把出生点覆盖回自己身上
2. `ResetPlayer` 里**先 `Teleport` 后 `ResetTo`** —— `ResetTo` 会广播 `StateChanged` + `ColorChanged`，表现层立刻同步；顺序反过来会在**旧位置**先闪一帧再被传送，看起来像瞬移+抽搐

**Editor 生成器**：16:33 新增 `LevelBuilder`（菜单 `Tools/Parkour/Build Two Levels`），生成 `Level_01`（5 段纯地面，缝隙 6~7m，普通跳可过）/ `Level_02`（5 段地面 + 1 段 3.2m 高天花板，第三段缝隙 9m，需二段跳），前置检查 Ground / Ceiling 层，private 字段用 `SerializedObject` 写入。

### 其他技术产出（Part D）

#### 一、`ZeroFriction.physicMaterial`：撞墙卡死的物理层解法

`dynamicFriction = 0` / `staticFriction = 0` / `frictionCombine = Minimum`。

Unity 的摩擦是**双方合成**的：玩家材质与墙材质的摩擦值按 `frictionCombine` 规则合成，默认 `Average`，所以只把自己调到 0 还是会被墙的 0.6 拉高。改成 `Minimum` 取两者较小值 → 玩家侧为 0 就一定是 0，撞墙后能沿墙滑落。

**更彻底的关卡侧修法**（建议但未做）：天花板段的碰撞体只包「底面薄板」，侧面不设碰撞体。因为吸附靠 `TrackSensor` 的 `OverlapSphere` 检测、**不依赖物理碰撞体**，碰撞体可以做得比视觉模型小。

**为什么没做代码层「受阻检测」**：用 `velocity.z ≈ 0` 判受阻会误伤起步与落地瞬间（那时 z 速度本来就是 0），要做得引入 `SphereCast` + `obstacleMask` 配置，成本不划算。

#### 二、统一取色：`GamePalette` + `MaterialPropertyBlock`

玩家与跑道共用 `TrackColor` 枚举（Red/Blue/Green）与 `GamePalette.Colors`，保证「同一索引 = 同一颜色」。刷色统一走 `MaterialPropertyBlock`：

```cs
block ??= new MaterialPropertyBlock();
renderer.GetPropertyBlock(block);
var shared = renderer.sharedMaterial;
if (shared != null && shared.HasProperty("_BaseColor")) block.SetColor("_BaseColor", c);  // URP/HDRP
else block.SetColor("_Color", c);                                                         // Built-in
renderer.SetPropertyBlock(block);
```

**为什么不用 `renderer.material`**：会给每个 Renderer 生成材质实例（多 DrawCall、易泄漏）；MPB 直接写属性块，不产生实例。细节见 📎 [[Unity 渲染批处理体系]]

`TrackPiece` 还挂了 `OnValidate()` 刷色 —— 编辑器里改完 Inspector 立刻能看到颜色，搭关卡不用反复点运行。MPB 在编辑态是安全的（不会实例化材质）。

## Ideas

- **「事件有定义、有广播、无订阅」是最隐蔽的一类断链**：编译过、不报错、日志干净，只是功能静默失效。今天 `PlayerBrain.Died` 就挂在这——过关链路是通的，死亡链路断了，现象「过关能进下一关、死了不动」很难联想到「少了一行 `+=`」。自检手段应该是 grep **订阅点**，不是读广播端
- **`using UnityEditor` 混进运行时程序集，10-23 行为树刚踩过，今天 `PlayerBrain` 又踩一次**。说明「记住别写」根本不管用——只有 asmdef 能管：Runtime 程序集不允许引用 UnityEditor，写错就是编译期红字。这条比任何笔记都值得落成工程约束
- 状态机只要允许「直接给 `state` 赋值」，就一定会漏广播（今天 `HandleJump` 就是）。`EvaluateSurfaces` 那三条分支已经老老实实只在变化时发事件了，旁路一开就破功 → **私有 `SetState()` 收口**
- 灯皇三次推翻我的方案里，最值钱的是 #6「直接设置玩家的 Y 值就行了」：我的 XZ 投影判断在几何上更「正确」，但跑酷要的是「撞到就钻过去」的手感。**手感问题里，「正确」要让位给「可玩」**
- `OverlapSphere` 的球体探测天然分不清「上下顶」和「侧面撞」。所有用球/胶囊做接触判定的地方都会遇到这个——补一句「接触法线方向和探测轴夹角」可能比 XZ 投影更通用
