# 字符串哈希

## 一、题意

> 给定 N 个字符串（1 ≤ N ≤ 10⁴，1 ≤ |sᵢ| ≤ 1500，仅由数字和大小写字母组成，**区分大小写**），求其中不同字符串的个数。

样例：

```
输入          输出
6             5
Hello
World
hello
HELLO
Code
Hello
```

（`Hello` 出现两次算 1 个；`Hello` / `hello` / `HELLO` 是三个不同的串 —— **区分大小写**是本题最容易忽略的一句。）

## 二、唯一的致命错误：把结果写进了 `return`

```cpp
int main() {
    ...
    return map.size();      // ❌ 结果去了退出码，stdout 一个字都没有
}
```

灯皇的思路、数据结构、去重逻辑**全部正确** —— `unordered_map<string,int> map` 计数后，`map.size()` 确实就是不同字符串的个数。错的只是**把它交给了谁**。

### `return` 和 `cout` 是两条完全不相干的通道

| 通道 | 谁看 | 谁判题 |
|---|---|---|
| `cout` / `printf` → **stdout** | 用户、判题机 | ✅ **OJ 只比对这里** |
| `return` → **进程退出码** | 操作系统、shell、CI | ❌ 0~255 的小整数，且 0 = 成功 |

`main` 的返回值传统上只表示「程序正常结束（0）还是异常（非 0）」。**它不是输出通道**，OJ 也从来不去读它。

### 实测三重证据

拿 5 个串 `abc abd abc xyz abd`（3 个不同）跑灯皇的原版：

```
stdout 字节数 = 0          ← 一个字都没输出
内容 = []
退出码 = 3                 ← 答案在这里，但没人看
```

再拿 **300 个不同串**跑：

```
退出码 = 44                ← 300 & 255 = 44
```

退出码只有 8 位有效（POSIX 只保证低 8 位），**300 被截成 44**。就算有哪个系统想读它，也读不到原值。

> 有些 OJ 还会把「非 0 退出码」判成 **RE（运行时错误）**。所以这行代码在最好的情况下是 0% WA，最坏的情况是 RE。

### 修法

```cpp
cout << distinct.size() << '\n';   // ★ 走 stdout
return 0;                          // ★ 0 = 正常结束
```

顺带：`size()` 返回 `size_t`（无符号 64 位），直接 `return` 到 `int` 是窄化转换，`-Wconversion` 会响。而 `cout << size_t` 没有任何问题。

## 三、另外三处（不影响正确性，但该改）

### ① `unordered_map` 换成 `unordered_set`

```cpp
unordered_map<string, int> map;    // 存了「每个串出现几次」
map[s]++;                          // 但你从没读过这个次数
```

题目只要「有哪些」，不要「各几次」。`unordered_set::insert` 自带去重，`size()` 直接就是答案：

```cpp
unordered_set<string> distinct;
distinct.insert(s);                // 已存在就什么都不做
```

省一半内存（不用给每个 key 配一个 `int`），也少一次 `operator[]` 查找。

> ⚠️ 顺带记住 `map[s]` 的语义：**key 不存在会静默插入一个默认值 0**。这里 `map[s]++` 恰好是想要的，但如果是「只读查询」，`operator[]` 会悄悄改大你的 map —— 要读用 `.at()` 或先 `find`。

### ② 变量名 `map` 阴影了 `std::map`

```cpp
using namespace std;
unordered_map<string, int> map;    // 这行本身合法
map<int, int> m2;                  // ❌ 编译失败：map 现在是个变量，不是模板
```

局部变量名会**遮蔽**同名的模板类。这行能编过，但之后任何 `map<K,V>` 都用不了了。命名成 `mp`、`cnt`、`distinct` 之类。

### ③ `endl` + 没开 IO 加速

本题只有一行输出，`endl` 无所谓。但 N = 10⁴、每串 1500 字符 → 输入共 **1.5×10⁷ 字节**，加上 `sync_with_stdio(false)` 更稳。

```cpp
ios::sync_with_stdio(false);
cin.tie(nullptr);
```

## 四、正解

```cpp
#include <iostream>
#include <string>
#include <unordered_set>
using namespace std;

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    int n;
    if (!(cin >> n)) return 0;

    unordered_set<string> distinct;
    distinct.reserve(n * 2);          // 预留桶数，避免反复 rehash

    while (n--) {
        string s;
        cin >> s;
        distinct.insert(s);
    }

    cout << distinct.size() << '\n';  // ★ stdout
    return 0;                         // ★ 0
}
```

官方样例实测输出 `5` ✅

### `reserve(n * 2)` 为什么值得加

`unordered_set` 插入时若「元素数 / 桶数 > max_load_factor（GCC 默认 1.0）」就触发 **rehash**：重新分配桶数组 + 把已有元素全部重新落桶。N = 1e4 时会经历约 14 次翻倍（1→2→4→…→16384），总搬迁量约 2N。`reserve(n*2)` 一次把桶数顶到 ≥ 2n，负载因子 ≈ 0.5，**一次都不 rehash**，且桶更空 → 查找更快。

## 五、题名为什么叫「字符串哈希」

哈希表（`unordered_map` / `unordered_set`）的桶下标是**整数**：`bucket = hash(key) % 桶数`。

`int`、`char` 本身就是整数，`std::hash<int>` 几乎是恒等映射。但**字符串不是整数**，没法直接取模 —— 必须先把它压成一个整数：

```
"Hello"  →  某个 64 位整数  →  % 桶数  →  落在第 k 个桶
```

这一步就是**字符串哈希**。`unordered_set<string>` 只是让标准库替你做了它（`std::hash<std::string>`，GCC 里是 `_Hash_bytes`，MurmurHash 的变体，**不是**多项式滚动哈希）。

> 所以这题的本质是：**你当然可以直接用 `unordered_set<string>`。但题目考的知识点是「字符串怎么变成整数」。**

## 六、手写字符串哈希

### 核心式子

```cpp
unsigned long long hashStr(const string& s) {
    unsigned long long h = 0;
    for (unsigned char c : s) h = h * 13331ULL + c;   // 自然溢出 ≡ mod 2^64
    return h;
}
```

这就是**把字符串当成 base 进制的数**：

```
"abc"  →  'a'*base² + 'b'*base + 'c'
```

和十进制 `"123" → 1*100 + 2*10 + 3` 是同一个式子，只是基数从 10 换成 13331。

| 参数 | 常见取值 | 说明 |
|---|---|---|
| `base` | 131 / 13331 | **必须大于字符集大小**（62），且取质数让各位贡献分散 |
| 模数 | 2⁶⁴（自然溢出）/ 1e9+7 / 1e9+7 与 1e9+9 | 见下节 |

### 为什么必须转 `unsigned char`

```cpp
for (char c : s) h = h * base + c;              // ❌ c 可能是负数
for (unsigned char c : s) h = h * base + c;     // ✅
```

`char` 在 x86 上是有符号的，UTF-8 高位字节（≥ 0x80）读出来是**负数**，加进哈希里就是负数 —— 同样的字节在不同平台/编译器下可能算出不同的哈希值。

### 三种取模方式的风险

| 方式 | 碰撞概率（n = 10⁴） | 备注 |
|---|---|---|
| `unsigned long long` 自然溢出 | 极低 | 但 **mod 2⁶⁴ 不是质数**，存在 Thue-Morse 序列的确定性碰撞构造，可被恶意卡 |
| 单模数 1e9+7 | **≈ 5%** | 生日悖论：`n² / (2m)` = 10⁸ / 2×10⁹ |
| 双模数 1e9+7 + 1e9+9 | ≈ 5×10⁻¹¹ | 最稳，多一次取模的常数 |

**实测**（100 轮 × 每轮 1e4 个随机串，与 `unordered_set<string>` 的真值对比）：

```
单模数 1e9+7       碰撞出错 3 轮
双模数 1e9+7+1e9+9 碰撞出错 0 轮
```

3% 和理论值 5% 同量级 —— **单模数在这题是有真实 WA 风险的，不是理论洁癖**。

### 用哈希值存表

```cpp
unordered_set<unsigned long long> seen;
seen.insert(hashStr(s));
```

内存从「每个串存完整内容」降到「每个串 8 字节」。N = 10⁴、串长 1500 时，`set<string>` 要存 **15 MB**，存哈希值只要 **80 KB**。

> 这正是「字符串哈希」在工程上的意义：**把「逐字符比较」降级成「比较一个整数」**。
> 但代价是**概率正确**：理论上存在两个不同串哈希值相同的情况（碰撞），必须靠双模数把概率压到可忽略。

### 完整手写版

```cpp
#include <iostream>
#include <string>
#include <unordered_set>
using namespace std;

const unsigned long long B = 13331;

unsigned long long h1(const string& s) {
    unsigned long long h = 0;
    for (unsigned char c : s) h = h * B + c;
    return h;
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);
    int n;
    if (!(cin >> n)) return 0;

    unordered_set<unsigned long long> seen;
    seen.reserve(n * 2);
    while (n--) {
        string s;
        cin >> s;
        seen.insert(h1(s));
    }
    cout << seen.size() << '\n';
    return 0;
}
```

对拍结果：200 轮 × 每轮 1e3~1e4 个串，**与 `unordered_set<string>` 答案 0 轮不一致**。

## 七、必须记住的点

1. **`main` 的 `return` 是退出码，不是输出。** 想输出就只有 `cout` / `printf`。退出码还会被截成低 8 位（300 → 44）。
2. **`return 0` 表示「正常结束」**，非 0 在有些 OJ 上直接判 RE。
3. **题目要「不同个数」时优先 `unordered_set`**，不要 `unordered_map` 记次数再取 `size()`。
4. **`unordered_set<string>` 内部就在做字符串哈希**，`std::hash<std::string>` 是 MurmurHash。
5. **手写哈希三件套**：`h = h * base + c`、`base` 取质数且 > 字符集、`unsigned char` 防负数。
6. **单模数 1e9+7 在 n = 1e4 时约 5% 碰撞**，要稳就上双模数。
7. **`size()` 是 `size_t`**，`cout` 没事，赋给 `int` 要显式转。

## 八、易错点

| 坑 | 后果 | 正确做法 |
|---|---|---|
| `return 答案;` | stdout 空，0% / RE | `cout << ans << '\n'; return 0;` |
| 忽略「区分大小写」 | `Hello` 与 `hello` 被当成一个 | `unordered_set` 本身区分，别自己 `tolower` |
| `map[s]` 只读 | key 不存在时静默插入 0 | 只读用 `.at()` 或 `find` |
| 变量名 `map` / `set` / `string` | 遮蔽同名模板，后续用不了 | 换名 |
| `unordered_map` 无 `reserve` | 14 次 rehash | `reserve(n * 2)` |
| `for (char c : s)` 累加 | 高位字节为负 → 哈希值随平台变 | `unsigned char c` |
| 单模数当万能 | 约 5% 概率 WA | 双模数或 `unsigned long long` |
| `endl` | 每次都 flush | `'\n'` |

## 九、复杂度

| 方案 | 时间 | 空间 |
|---|---|---|
| `unordered_set<string>` | `O(Σ|s|)` 平均（每串一次哈希 + 一次比较） | `O(Σ|s|)` ≈ 15 MB |
| 手写哈希 + `unordered_set<ull>` | `O(Σ|s|)` | `O(N)` ≈ 80 KB |
| `set<string>`（红黑树） | `O(Σ|s| · log N)`，每次比较还要 `O(|s|)` | `O(Σ|s|)` |

`Σ|s|` 最大 1e4 × 1500 = **1.5×10⁷**，三种都能过；差距在常数和内存。

> **`unordered_set` 的「平均 O(1)」有前提**：哈希函数把 key 均匀撒进桶里。如果哈希被卡成全部落同一个桶，退化成链表 → `O(N)` 单次。这就是「反哈希攻击」。

## 十、面试延伸

**Q：`unordered_map` 会不会被人卡成 O(n²)？怎么办？**

会。Codeforces 上经典的 anti-hash test 就是构造一堆哈希值（对 `% 桶数` 后）相同的 key。对策：

```cpp
struct custom_hash {
    static uint64_t splitmix64(uint64_t x) {
        x += 0x9e3779b97f4a7c15ULL;
        x = (x ^ (x >> 30)) * 0xbf58476d1ce4e5b9ULL;
        x = (x ^ (x >> 27)) * 0x94d049bb133111ebULL;
        return x ^ (x >> 31);
    }
    size_t operator()(uint64_t x) const {
        static const uint64_t FIXED_RANDOM =
            chrono::steady_clock::now().time_since_epoch().count();
        return splitmix64(x + FIXED_RANDOM);
    }
};
unordered_map<long long, int, custom_hash> mp;
```

关键是 **`FIXED_RANDOM`**：种子在运行期才确定，攻击者没法离线构造碰撞。

**Q：字符串哈希能做什么，`unordered_set` 做不到的？**

- **子串哈希 / 滚动哈希**：预处理前缀哈希 `pre[i]`，`O(1)` 取任意子串的哈希 → 字符串匹配、最长重复子串、回文判断都能做到 `O(n log n)` 甚至 `O(n)`
- **判重但不想存原串**：内存敏感场景（如 1e6 个长串）
- **配合二分**：`O(log n)` 找最长公共前缀

**Q：为什么 `base` 要取质数？**

`h = Σ cᵢ · baseⁱ`。如果 base 与模数不互质（比如 base 是模数的因子），不同位置的字符贡献会「塌缩」到少数几个值上，碰撞率飙升。取质数且大于字符集大小，能让 `base⁰, base¹, …, baseᵏ` 在模意义下尽量分散。

**Q：`X*` 那种通配符能不能用哈希做？**

不能，正则匹配需要逐字符回溯/DP，哈希只能判「两个串是否相等」。

## 十一、一句话总结

> **输出走 `cout`，`return 0` 只表示「我没崩」。** 想清楚「结果交给谁」再动手，比想清楚算法更早一步。
