#### 二、架构变化：从「UI 直接抓 Player」到「四层拆分」

今天的主线是把昨天（10-28）那个什么都往 `Player` 里塞的结构拆开：

```text

    ├── Player（输入 + CharacterController 位移）
    │     └── AnimatorManager（纯 C# 类，只管 SetBool/SetFloat）
    └── UIFightingView（视图层，只发指令，不碰输入不碰物理）
```

```cs
public class FightingManager : MonoBehaviour
{

    private void Awake()
    {

            Instance = this;

    internal Player player;

        player = FindAnyObjectByType<Player>();
    }

```

**意图很明确**：`UIFightingView` 里不再 `FindAnyObjectByType<Player>()`，改成 `FightingManager.Instance.player.OnPlayRun(true)` —— UI 只认一个全局入口，不认场景里谁是谁。这是向 [[UI-逻辑-数据分层与事件驱动]] 迈的第一步（虽然还差事件层）。

`AnimatorManager` 抽出来的价值在**去掉 MonoBehaviour 依赖**：

```cs
public class AnimatorManager
{
   private static readonly int crouch = Animator.StringToHash("Crouch");
   private static readonly int run = Animator.StringToHash("Run");
   private Animator animator;

   public AnimatorManager(Animator _animator) { animator = _animator; }

   public void OnPlayRun(bool _isRun)
   {
      animator.SetBool(run, _isRun);
      animator.SetBool(crouch, !_isRun);
   }
}
```

`StringToHash` 提成 `static readonly` 是正确的（省掉每帧字符串哈希，见 [[Animator参数与性能优化]]），构造注入 `Animator` 也符合「非 MonoBehaviour 逻辑类」的写法（同 [[行为树工程实现 — 黑板、RUNNING 中断与节点生命周期]] 里 Node 靠构造注入依赖的路子）。

#### 三、配表链路：Excel → 中间格式 → StreamingAssets → 运行时

今天花时间最多的其实是这条链路，`游戏配表/` 目录是新出现的：

```text
游戏配表/WeaponsGun.xlsx              ← 策划表（含三行表头）
  ├── WeaponsGun - 副本.csv           ← 逗号分隔
  ├── WeaponsGun - 副本.xml           ← Excel「XML 表格 2003」导出（SpreadsheetML）
  └── Assets/StreamingAssets/WeaponGun.json   ← 实际喂给运行时的
```

三行表头结构（第 4 行才是数据）：

| 行 | ID | WeaponName | FireRate | WeaponType | AnimatorType |
| --- | --- | --- | --- | --- | --- |
| 1（字段名） | `ID` | `WeaponName` | `FireRate` | `WeaponType` | `AnimatorType` |
| 2（类型） | `int` | `string` | `int` | `int` | `string` |
| 3（注释） | `武器ID` | `武器名称` | `射速` | `武器类型` | `动画类型` |
| 4（数据） | `1001` | `AK47` | `300` | `RF` | `RfsAnimator` |

导出的 JSON 把三行都塞进数组：

```json
{"Sheet1":[
  {"ID":"int","WeaponName":"string","FireRate":"int", ...},
  {"ID":"武器ID","WeaponName":"武器名称","FireRate":"射速", ...},
  {"ID":1001,"WeaponName":"AK47","FireRate":300,"WeaponType":"RF","AnimatorType":"RfsAnimator", ...}
]}
```

**表本身已经自相矛盾**：表头类型行写 `WeaponType: int`，数据行给的是 `"RF"`（字符串）。这类矛盾在强类型反序列化时会直接炸，必须先把表改对。

`XMLReader` 走的是「泛型 + 反射」路线：

```cs
public List<T> Read<T>(string path) where T : new()
{
    xd.Load(path);
    Type type = typeof(T);
    var fields = type.GetFields();
    XmlNode rootNode = xd.FirstChild;
    XmlNodeList childNodes = rootNode.ChildNodes;

    List<T> TList = new List<T>();
    foreach (XmlNode node in childNodes)
    {
        T obj = new T();
        foreach (XmlNode content in node.ChildNodes)
        {
            foreach (var fieldInfo in fields)
                if (fieldInfo.Name == content.Name)
                    fieldInfo.SetValue(obj, content.InnerText.ToString());
            TList.Add(obj);
        }
    }
    return TList;
}
```

思路（反射按字段名自动映射，配置类加字段不用改读表代码）是对的，但**五个地方会静默失效**，逐条见下。

### 其他技术产出（Part D）

#### 1. 读表格式选型的实际判断

三条路都试了一遍，结论：

| 格式 | 优点 | 今天踩到的硬伤 |
| --- | --- | --- |
| **Excel 直存 XML** | 一键导出、带类型标注 | SpreadsheetML 结构复杂（`Worksheet/Table/Row/Cell/Data` 四层），字段名在 `Data` 文本里而非元素名 → 通用 XML 解析器全部失效 |
| **CSV** | 最简单、最通用 | 无法表达嵌套/数组；中文逗号与转义要自己处理；类型全靠约定 |
| **JSON** | 生态好、Unity 有 `JsonUtility` | 表头三行混在数据里；`JsonUtility` 顶层不能是数组、不吃 Dictionary、类型必须严格匹配（`"RF"` 进 `int` 直接失败） |

最终选 JSON（`StreamingAssets/WeaponGun.json`）是合理的——比 SpreadsheetML 好解析一个量级。代价是要先解决三行表头与混合类型两个问题。

#### 3. `FightingManager` 单例的两处隐患

```cs
internal static FightingManager Instance;
private void Awake() { if (Instance == null) Instance = this; }
```

- **没有 `DontDestroyOnLoad`**：切场景后 `Instance` 变成「假空」（Unity 的 `==` 重载会把已销毁对象判为 null），但静态字段本身还指着那块已释放的壳 → 需要在 `Awake` 里判 `Instance != null && Instance != this` 时销毁自身，或者干脆不跨场景
- **`player` 无判空**：`UIFightingView.OnBtnRun` 里 `FightingManager.Instance.player.OnPlayRun(true)`，只要 `FightingManager.Start` 没跑完（或场景里没 `Player`），就是 `NullReferenceException`。`Start` 的执行顺序在 `Awake` 之后但跨对象无序，UI 按钮的点击至少晚于第一帧所以现在不会炸，但**依赖「用户点得比 Start 晚」不是设计**

## Ideas

- **表头三行 = 代码生成器的输入**：既然表里已经写了类型（`int`/`string`），导表工具就该顺手生成 `WeaponConfig.cs` 或 `WeaponTable` 常量类，运行时零反射。反射读表只适合原型期，正式管线一定走生成代码
- **动画状态别用布尔组合编码**：`Run` / `Crouch` 两个 bool 能表示 4 种组合，但业务只有 3 个状态 → 第 4 个组合是非法状态，迟早被某个 `!` 撞上。用 enum + 单一入口
- **移动速度与动画混合是两层数据**：逻辑层用米/秒，动画层用 0~1 归一化，中间隔一层换算。混在一起改一个坏一个
- 战斗 UI 现在还是「按钮直调 Player 方法」，下一步该抽事件层：UI 发 `OnRunRequested`，`Player` 订阅。否则每加一个按钮就要改一次 UI 脚本的引用链
- `FightingManager` 现在只是「全局变量容器」，真正的价值应该是**战斗流程状态机**（准备/进行/结算），现在还没到那一步
