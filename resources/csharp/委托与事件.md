# 委托与事件

面试题原声：「讲一下委托和事件」。**核心一句话**：`event` 就是加了一层访问限制的 `delegate` 字段。把这句话说透，这题就答完大半了。

## 一、委托 delegate 是什么

**本质：类型安全的函数指针 + 一个目标对象（target）。**

```csharp
public delegate int Calc(int a, int b);   // 声明一种"函数签名类型"
Calc add = (a, b) => a + b;               // 实例：绑定具体方法
int r = add(1, 2);                        // 调用 → 实际调用被绑定的方法
```

两个关键点：

1. **它是类型**，不是普通对象 —— 只接受**签名匹配**的方法，所以叫"类型安全"，比 C 的函数指针安全。
2. **它成对携带「方法地址 + target 实例」** → 用实例方法创建的委托**隐式持有 `this`**。这一条是后面所有内存泄漏问题的根源。

### 多播委托 = 委托链

`+=` / `-=` 把多个方法串成一条链（`MulticastDelegate`），调用时**按加入顺序依次执行**。

```csharp
Action onDone = null;
onDone += A;      // 链：A
onDone += B;      // 链：A → B
onDone.Invoke();  // 依次执行 A、B
```

⚠️ **两个坑**：

- **中途抛异常会截断**：A 抛异常 → B 根本不执行。要让每个都跑到，得手动遍历 `GetInvocationList()` 逐个 try/catch。
- **`-=` 只移除一个匹配项**，重复订阅 N 次要 `-=` N 次才干净；`+=` 同一个方法多次会执行多次。

### 内置委托类型（日常首选）

| 类型 | 用途 |
| --- | --- |
| `Action` / `Action<T...>` | 无返回值，最多 16 个参数 |
| `Func<T..., TResult>` | **有**返回值，最后一个泛型参数是返回类型 |
| `Predicate<T>` | 返回 `bool`，常用于筛选 |

自 2026 视角：能用 `Action`/`Func` 就别自定义 delegate，省得处处 `new` 一个类型。

## 二、事件 event 是什么（本题重点）

**`event` = 对 `delegate` 字段的一层「访问权限封装」。**

```csharp
public class Publisher
{
    public event Action OnFire;          // 声明事件

    public void Trigger() => OnFire?.Invoke();   // 类内可调用
}

// 类外：
pub.OnFire += Handler;      // ✅ 允许：订阅
pub.OnFire -= Handler;      // ✅ 允许：退订
pub.OnFire = null;          // ❌ 编译错误：不能赋值覆盖
pub.OnFire();               // ❌ 编译错误：不能直接调用
```

### 编译后发生了什么（答到这一层是加分项）

`event Action OnFire;` 会被编译成：

- 一个 **`private` 的 delegate 字段**；
- 一对 **`add_OnFire` / `remove_OnFire` 访问器方法**（类似属性的 get/set）；
- 外部代码对 `+=` / `-=` 的调用被编译成**对这两个访问器的调用**。

所以 `event` **不是新类型**，是**编译器层面的语法 + 访问控制**。

### 那为什么还需要 event？只暴露一个 public delegate 不行吗？

不行，public delegate 字段会带来两个致命问题：

1. **外部可以 `= null` 把别人的订阅全部抹掉** —— 一个模块的失误让所有监听者失联；
2. **外部可以随意 `Invoke()`** —— 谁都能触发业务事件，封装彻底失效，调用方无法信任事件源。

`event` 把这两条彻底堵死：**只有定义它的类内部能触发和整体赋值，外部只能订阅/退订。**

### 和属性的类比

| | 字段 → 封装后 | 权限 |
| --- | --- | --- |
| 数据 | `int age` → `int Age { get; set; }` | 控制读写 |
| 委托 | `Action OnFire` → `event Action OnFire` | 控制 `+=`/`-=` 与 `Invoke` |

这个类比能一句话把 event 的定位讲清楚。

## 三、事件 vs UnityEvent

| | C# `event` | `UnityEvent` |
| --- | --- | --- |
| 序列化 | ❌ 不能（委托不可序列化） | ✅ 可以，Inspector 里拖拽配置 |
| 编辑器可视化 | ❌ | ✅ 适合策划/美术配置 |
| 性能 | 直接调用委托，开销小 | 有一次装箱/反射式调用开销，相对更重 |
| 参数 | 签名自由 | 支持 0~4 个固定类型参数（`UnityEvent<T0..T3>`） |
| 适用 | 代码内部逻辑解耦 | **需要非程序在 Inspector 配的回调** |

**选型一句话**：纯代码模块间通信用 `event`/`Action`；要给策划在面板上挂回调就用 `UnityEvent`。

## 四、最大的坑：订阅不取消 = 内存泄漏

```csharp
publisher.OnXxx += HandleXxx;   // ① 订阅：publisher 持有 handler
// ... 对象被 Destroy / 离开作用域 ...
// 忘了 -=  →  publisher 仍握着这条委托 → 它隐式持有 this → 订阅者永远无法被 GC 回收
```

**为什么静态事件尤其危险**：静态成员的生命周期 = **整个应用程序域**，是永不释放的 GC Root。订阅静态事件 = 把自己挂到一个永远活着的对象上 → **必然泄漏**，且场景切换也解不掉。

**三种解法**：

1. **最稳**：在 `OnEnable` 里订阅、`OnDisable` 里退订（成对出现，天然跟随 `SetActive`）；
2. **弱引用事件**：发布者只持有 `WeakReference`，订阅者被回收后自动失效；
3. **一次性订阅**：明确只触发一次的回调，在回调体内立刻 `-=`。

深挖闭包与隐藏类（`c__DisplayClass`）如何加剧这类泄漏 → 📎 [[C# 闭包与委托 — 隐藏类与 GC 陷阱]]

## 五、面试答题框架

① 委托 = 类型安全的函数指针 + target（实例方法持有 `this`）→ ② `+=`/`-=` 构成多播委托链，按序执行、异常会截断 → ③ **event 是 delegate 字段的封装**：编译成私有字段 + add/remove 访问器，外部只能订阅/退订，不能赋值覆盖、不能 Invoke → ④ 为什么需要它（防外部清空订阅 + 防乱触发）→ ⑤ 与 UnityEvent 的取舍（序列化/可视化 vs 性能）→ ⑥ 订阅不取消 → GC 泄漏，静态事件最危险，靠 OnEnable/OnDisable 成对处理。
