### FireSim_URP_PC — TaskStateManager 注册制重构：Init 退役，任务自注册

📎 [[UI-逻辑-数据分层与事件驱动]]

**目标文件**：`Assets/Scripts/Author/Wt/UI/WristUI/TaskTips/TaskStateManager.cs`

**问题**：原链路是 `TaskPanelPlus.Init()` 里用 `FindObjectOfType<SceneTaskBase>().transform.parent` 反查任务根 → `GetComponentsInChildren` 收集 → `TaskStateManager.Init(tasklist)` 灌入字典。这套「UI 去场景里找任务」的方式有三个硬伤：

1. `FindObjectOfType<T>()` 默认不找 inactive 对象 → 任务未激活时找不到；
2. 依赖「第一个命中的任务的父节点含全部任务」这一结构假设 → 任务分散在多父节点下会漏收集，且「第一个」顺序不确定；
3. **UI 的 Init 必须早于任务启动**，否则任务后到就永远建不出列表项（时序耦合）。

**方案（注册制为唯一数据源）**：任务自己注册进数据层，UI 只订阅事件。数据层只保留 `sceneTasksDict`（TaskType → 实例）+ `dataDict`（TaskType → TaskStatus），**删除 `Init(SceneTaskBase[])`**。

```cs
public void RegisterTask(SceneTaskBase sceneTaskBase)
{
    if (sceneTaskBase == null) return;

    TaskType taskType = sceneTaskBase.TaskTypeBase;
    if (sceneTasksDict.TryGetValue(taskType, out var exist))
    {
        if (exist == sceneTaskBase) return;          // 幂等：同一实例重复注册直接返回
        Debug.Log($"[TaskStateManager]{taskType}已有任务实例,注销旧实例");
        UnregisterTask(exist);                        // ← 关键：注销的是【旧实例】exist
    }

    sceneTasksDict[taskType] = sceneTaskBase;
    if (!dataDict.ContainsKey(taskType))
        dataDict[taskType] = TaskStatus.NotFinished;

    // 先减后加，防重复订阅
    sceneTaskBase.OnTaskStateChanged    -= OnSceneTaskStateChanged;
    sceneTaskBase.OnTaskStateChanged    += OnSceneTaskStateChanged;
    sceneTaskBase.OnTaskProgressChanged -= OnSceneTaskProgressChanged;
    sceneTaskBase.OnTaskProgressChanged += OnSceneTaskProgressChanged;

    ApplySceneTaskState(taskType, sceneTaskBase.TaskStateBase);   // 晚注册补偿
    OnTaskRegistered?.Invoke(sceneTaskBase);                      // 通知 UI 建项
}

public void UnregisterTask(SceneTaskBase task)
{
    if (task == null) return;

    task.OnTaskStateChanged    -= OnSceneTaskStateChanged;
    task.OnTaskProgressChanged -= OnSceneTaskProgressChanged;

    TaskType type = task.TaskTypeBase;
    if (sceneTasksDict.TryGetValue(type, out var cur) && cur == task)
        sceneTasksDict.Remove(type);
    dataDict.Remove(type);                            // ← 两个字典必须同步清理
}
```

配套把 `Clear()` 作为场景重载入口（替代原 `Init` 的清理职责）：

```cs
public void Clear()
{
    foreach (var t in sceneTasksDict.Values)
    {
        if (t == null) continue;
        t.OnTaskStateChanged    -= OnSceneTaskStateChanged;
        t.OnTaskProgressChanged -= OnSceneTaskProgressChanged;   // ← 原 Init 漏了这个
    }
    sceneTasksDict.Clear();
    dataDict.Clear();
}
```

**收益**：零 Find、零结构假设、支持 inactive 任务，并**顺带根治了「UI Init 早于 TaskStart」的时序问题**——任务后注册也能通过 `OnTaskRegistered` 动态补建列表项。

### FireSim_URP_PC — TaskStateManager 四轮复查：3 个真 bug 的定位与修复

📎 [[UI-逻辑-数据分层与事件驱动]]

**目标文件**：同上。初版注册制写完后逐轮复查，抓出三个会真实炸掉功能的 bug：

**Bug 1（严重）—— `CompletedTaskCount` 的 getter 会累加字段**

```cs
// ❌ 错误：每读一次属性，就把「已完成数」往字段上再加一遍
public int CompletedTaskCount
{
    get
    {
        foreach (var t in sceneTasksDict)
            if (t.Value.IsCompleted) completedTaskCount++;   // 副作用写在 getter 里
        return completedTaskCount;
    }
}
```

UI 的 `Refresh` 每次读它 → 标题数字暴涨；且 `SetStatus` 里另有一处 `completedTaskCount++` → **双重计数**。

```cs
// ✅ 正确：只计算不累加，用局部变量；顺带解决「状态回退时计数不减」
public int CompletedTaskCount
{
    get
    {
        int count = 0;
        foreach (var sceneTaskBase in sceneTasksDict)
        {
            if (!sceneTaskBase.Value.IsCompleted) continue;
            count++;
        }
        return count;
    }
}
```

改完后 `completedTaskCount` 字段、`CompletedTaskCount` 的 setter、`SetStatus` 里的 `++`、`Clear()` 里的 `= 0` 全部成了无读者的死代码，一并清掉。

**Bug 2 —— `RegisterTask` 的冲突判断恒为真**

```cs
// ❌ 条件永远成立：字典的 key 就是 taskType，取出来必然等于 taskType
if (sceneTasksDict.TryGetValue(taskType, out var exist))
{
    if (exist.TaskTypeBase == taskType) return;   // 恒真 → 新任务永远注册不进来
    ...
    UnregisterTask(sceneTaskBase);                // 且传的是【新任务】，应为旧实例 exist
}
```

后果：同类型替换逻辑形同虚设，且 `UnregisterTask` 传错实例 → 旧实例的事件订阅**没被解绑**，成为「幽灵订阅者」，它再广播状态/进度会按 `TaskType` 污染新实例的数据。

```cs
// ✅ 正确
if (exist == sceneTaskBase) return;
UnregisterTask(exist);
```

**Bug 3 —— `UnregisterTask` 清理不完整**：漏了 `dataDict.Remove(type)` → `DataDict` 与 `SceneTasks` 数量不一致，`GetTaskState(type)` 会返回已注销任务的残留状态，UI 按 DataDict 遍历也会看到残留项。（另：早期版本还残留一个 `_registerSceneTasks` 平行列表与 `OnTaskUnregistered` 事件，前者造成双数据源、后者无人订阅，均按 YAGNI 删除。）

**踩坑总结（注册制改写的三条铁律）**：
- 带副作用的逻辑**绝不能写在 getter 里**——实时统计就该用局部变量；
- 用字典 key 反查出来的值，**不可能**与 key 不等，拿它做判断条件必是恒真/恒假；
- 同一个实体在多个容器里有副本时（`sceneTasksDict` / `dataDict` / 曾经的 `_registerSceneTasks`），**增删必须成对**，否则迟早不一致。

private void OnEnable()  { SubscribePanel(); }

private void SubscribePanel()
{

### FireSim_URP_PC — TMP SetText 零分配落地

📎 [[TMP Text 零分配更新]] 📎 [[UGUI多级UI性能优化与Canvas重建]]

**目标文件**：`TaskPanelPlus.cs`（`Refresh` 与 `CreatItem` 两处）

**问题**：进度文本原来是字符串插值 `$"{p}/{s}"` → 每次刷新产生一次 string 分配 + `float.ToString` 装箱风险。

```cs
// ✅ 改用 TMP 的 SetText(format, args...) 重载：写内部 char buffer，不产生 string
item.tmp_Progress.SetText("{0}/{1}",
    Mathf.RoundToInt(sceneTask.TaskProgress),
    Mathf.RoundToInt(sceneTask.TaskStep));
```

**要点**：
- 该重载参数类型是 `float`，`int` 隐式转换**不装箱**；但它只做 `{n}` 占位替换，**不支持 `{0:0}` 格式化**，所以先 `Mathf.RoundToInt` 取整；
- 真正该优化的顺序是 **TMP 文本重建（Canvas/Mesh 重建）> string GC**——所以优先级是「避免无变化时 setText」>「避免高频调用」>「避免 string 分配」。本次更新是事件驱动（状态/进度变化）低频，StringBuilder 反而是过度设计（最后仍要 `ToString()`）；
- 遗留：`TaskStep == 0` 时原来的「分母为 0 只显示已完成数」降级被移除 → 会显示 `0/0`；`tmp_titleProgress` 两处仍为字符串插值（可选统一）。

### FireSim_URP_PC — 架构咨询三则（Find 兜底评价 / Instance 缓存 / StringBuilder）

📎 [[单例模式与静态类选型]]

**咨询 1：`TaskPanelPlus.Init` 用 Find 获取任务列表合不合理？**

结论：「Inspector 引用为主 + Find 兜底并打警告」这个模式本身**合理务实**，比纯 Find 好得多，但兜底路径有三个具体问题：① `FindObjectOfType<T>()` 默认不找 inactive；② 依赖 `first.transform.parent` 的结构假设；③ 该方法在较新 Unity 已过时（推荐 `FindAnyObjectByType` / `FindObjectsByType`）。

Find 的通用适用边界：✅ 一次性初始化兜底 + 日志警告、编辑器工具；❌ 每帧调用、❌ 作模块通信主干、❌ 依赖「第一个命中」及其层级。→ 最终采用了结构最优的「任务自注册」方案（见首节）。

**咨询 2：要不要缓存 `TaskStateManager.Instance`？**

结论：**性能上没必要**。它是 `public static TaskStateManager Instance { get; } = new();`（静态只读自动属性 = 一次静态字段读取，JIT 通常内联），不是 `Find`/`GetComponent` 类查找，也不在每帧热路径。缓存成**方法内局部变量**的唯一理由是**可读性**（同一方法引用 4~5 次时少打字），不必提升为类字段。

反面提醒：① 不要把它做成 `[SerializeField]` 字段（破坏单例语义、可能漏配）；② 事件订阅/解绑要基于同一引用（单例恒等，天然满足）。**真正必须缓存的是** `GetComponent`/`Find` 类查找、`Camera.main`、Update 中重复调用的昂贵 API；若将来 `Instance` 改成懒加载/可替换（测试注入），缓存价值才会上升。

**咨询 3：文字更新要不要用 StringBuilder 减 GC？** → 结论见上一节（没必要，真正成本在 TMP 文本重建）。
