#### 2. `Assets/Scripts/Role/EnemyAI.cs`（16:19）—— 三处坐标类根因修复

昨天这个文件只写了 `Init` + 装配枪，今天补完巡逻/追击后连爆三个 bug，全部是「代码自洽但整体反了」型。

**(a) 方向向量算反：`(self - target)` 写成了目标→自己**

```diff
- Vector3 dir = (transform.position - go.transform.position).normalized;
+ Vector3 dir = (go.transform.position - transform.position).normalized;
```

追击分支同样一处。这个 bug 的迷惑性在于：`Vector3.Dot(transform.forward, dir)` 和 `Move(dir, runSpeed)` 用的是**同一个反向向量**，所以「判断」和「移动」内部是自洽的 —— 敌人不会站着不动，而是只在「目标位于背后 ±72°」时才触发追击，然后背对目标一路跑，目标永远在背后 → 条件永远成立 → 越跑越远。**判据：凡是 `A - B` 的方向向量，先在心里念一遍「从谁指向谁」。**

**(b) 巡逻点 y 被 spawn 高度冻结 → 到达判定永假**

根因链：`FightingManager` 把敌人生成在 `+ Vector3.up * 5f`，第一帧 `Update` 时敌人还在空中（y≈4），此时算出的巡逻点 `position + dir * R` 把 **y 一起冻结在 4 米**。落地后 `Vector3.Distance(self, targetPos)` 里恒定夹着 ~4m 的 Δy → 永远 ≥ 1m → `isPatrolling` 永不置回 `true` → `targetDir` 永不刷新 → 每帧 `Move(targetDir)` 变成固定方向直走。

修复是把所有巡逻相关坐标压到水平面：

```cs
private Vector3 SelfPos => new(transform.position.x, 0, transform.position.z);

targetPos = SelfPos + targetDir * R;
targetPos = new Vector3(targetPos.x, 0, targetPos.z);
...
if (Vector3.Distance(SelfPos, targetPos) < 1f) isPatrolling = true;
```

> **通用教训**：`Vector3.Distance` 是三维修度，任何「平面寻路 / 平面巡逻 / 平面射程」的判定都必须先把 y 拍平。地形有高差时这个 bug 会变成「有时候能到、有时候永远到不了」，最难复现。

**(c) `Random.Range(0, 6)` 是 int 重载**

```diff
- float angel = Random.Range(0, 6) * 72f;
+ float angel = Random.Range(0f, 6f) * 72f;
```

`Random.Range(int, int)` **上界开区间**，只会返回 0~5；乘 72 后 0° 和 360° 语义重复，等于「正前方」占了 1/3 概率，敌人三分之一的情况会继续朝原方向走。换成 float 重载后 `[0, 6)` 连续均匀。这是本项目第 **4** 次栽在 `Random.Range` 的重载歧义上（前三次：`Random.Range(-1,1)` 取不到 1、`Random.Range(0, count)` 与 `Range(0f, count)` 混用）。

### 其他技术产出（Part D）

#### 1. 接雨水：三处下标写错 → 3000 组对拍 2881 组错

`D:\Notes` 今日 10:41 commit `fd2aab5`，新建 `resources/algorithm/算法思想/接雨水.md`（180 行）。

核心错误只有三个字母：

```cpp
for (int m = 0; m < n; m++) {
    r += min(leftMax[n], rightMax[n]) - arr[n];   // ❌ 三个都该是 m
}
```

`n` 是长度，合法下标是 `0..n-1` → `leftMax[n]` / `rightMax[n]` / `arr[n]` **全部越界一个元素**。`vector::operator[]` 不做边界检查，所以不崩不报错，读到的是一段无关内存。

实测：

| 版本 | 错组数（3000 组随机对拍） |
| --- | --- |
| 原版 | **2881 / 3000**（剩下 119 组只是正确答案本来就为 0） |
| 三个 `n` 改成 `m` | **0** |

同一组 `[4,2,0,3,2,5]` 两次运行分别得到 `0` 和 `-201325074`（后者同时是 `int` 溢出）—— **同一份代码、同一个输入、不同结果，就是越界读的铁证**。

**可迁移的判据**：凡是在 `for (int m = 0; m < n; m++)` 里，下标位置出现 `n` 一定是写错了（除非本来就故意取「末尾后一位」当哨兵）。

#### 2. ACM 模式 IO 加速实测：`sync_with_stdio` 与 `tie` 到底哪个在起作用

`D:\Notes` 今日 10:45 commit `a24fb3b`，补强 `resources/algorithm/ACM模式输入输出.md` 第九节（+96 行）。1e6 个 `int` 实测：

| 配置 | 耗时 | 相对默认 |
| --- | --- | --- |
| 默认（同步 + tie） | 473 ms | 1× |
| 只关 `sync_with_stdio` | **87 ms** | **5.4×** |
| 两个都关 | 85 ms | 5.6× |
| 只解 `tie` | 468 ms | ≈1× |
| `scanf`（关同步后的对照） | 240 ms | — |

**结论**：加速几乎全部来自 `sync_with_stdio(false)`（断开 C/C++ 两套缓冲区同步检查）；`tie(nullptr)` 省的是「每次读之前 flush cout」，没有真实输出等待时基本无收益 —— 但它是免费的，照写。关同步后的 `cin` 比 `scanf` 还快一倍多。代价：不能与 `scanf`/`printf` 混用、交互题必须手动 flush。

> 真正更常见的 TLE 元凶不是这两行，而是 **`endl`**（每次强制 flush）。

#### 3. 敌人 AI 从「能编译」到「能跑」：三重根因的排查顺序

今天最值钱的不是修了什么，而是**三个 bug 互相掩盖的排查顺序**：

1. 先看「为什么不刷新目标」→ 发现 `isPatrolling` 卡在 `false`（状态机层）
2. 再问「为什么到不了点」→ `Vector3.Distance` 里恒定夹着 4m Δy（坐标层，spawn 抬 5m 的连带反应）
3. 最后才暴露「为什么方向是反的」→ 前两个修完，敌人终于动了，才看得出是背对目标跑（向量层）

如果一上来就盯着方向向量看，会发现「判断和移动用的是同一个向量、逻辑自洽」而放过它 —— **表现层 bug 会掩盖逻辑层 bug，必须先让系统动起来再判断方向对不对**。

#### 4. NavMeshAgent 迁移的可行性结论（16:22，未动手）

环境事实：Unity **2022.3.62f3c1**，`Packages/manifest.json` **没有** `com.unity.ai.navigation`，只有 `com.unity.modules.ai`（legacy Navigation + `NavMeshAgent` 可用，`Window > AI > Navigation` 可直接 Bake）；项目里**尚无任何 NavMesh 烘焙资源**，代码里零 NavMesh 引用。

## Ideas

- `EnemyAI` 现在把「感知 / 决策 / 移动 / 动画」四件事全塞在一个类里，`OnPatrol` 同时干「找目标」和「改状态」。拆成 `Perception`（谁在范围内）+ `Brain`（该追还是该巡）+ `Locomotion`（怎么走）三层，才能接 FSM 或行为树 —— 📎 [[有限状态机FSM — 手写实现与状态切换边界]] / 📎 [[行为树工程实现 — 黑板、RUNNING 中断与节点生命周期]]
- 「巡逻点 y 被冻结」本质是**生成时机与落地时机错位**：`Start` 里算出的世界坐标在物体还在空中时就固化了。这类问题有个通用解法 —— 所有「延迟生效的世界坐标」都存成「相对锚点 + 偏移」，用的时候再合成。
- `_minDis` 就地改写入参这个坑，和 `out bool` 被循环覆盖是同一类：**C# 的参数语义（值传递 vs 引用传递）被当成「变量共享」用**。值得单独整理一篇「参数传递语义踩坑集」。
- 8 个敌人 + 玩家互撞导致卡死，短期可以用 `Physics.IgnoreCollision` 或分层碰撞矩阵解决，长期还是得上寻路。
- 接雨水那题的「同一代码两次运行不同结果」是个很好的**自动化对拍**教学案例 —— 比任何静态分析都能说明 UB 的危害。
