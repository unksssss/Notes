#### Q1（项目实战 ✅）VFX Graph Shader 编译缓存重导

**题目**：修改了 VFX Graph 引用的 shader 属性名后编辑器报错"找不到属性"，正确修复方式是？
- **用户答案**：B
- **正确答案**：B
- **用户结果**：✅ 答对

**知识点详解**：

VFX Graph 内部维护了自己的 shader 编译缓存。当修改 VFX 中引用的 shader 属性名时，缓存的 shader 编译结果仍引用旧属性名，导致运行时或编译时报错。

**关键机制**：
1. VFX Graph → VFX 编译器 → HLSL shader 生成 → 内置 shader 缓存
2. 属性名变更后，缓存 stale，需要触发 VFX 文件重新编译
3. **右键 → Reimport** 是标准修复方式，触发 VFX 重新走一遍完整编译流水线
4. 删除 `Library/` 目录属于暴力手段（等效重建整个项目缓存），杀鸡用牛刀且耗时极长
5. 仅重启 Unity 不保证清 shader 缓存（Library 目录仍在）
6. 从 VFX Inspector 也能触发 Recompile，但右键 Reimport 是最直接途径

**避免方法**：大范围 shader 改动前先做 VFX 文件备份，或者用 ShaderGraph 属性暴露后统一管理。

// ✅ 换成在游戏运行时创建，或在 Editor 中执行后手动播放

**Obi 物理模拟依赖链**：

#### Q3（经典面试 ❌）struct 装箱陷阱

**题目**：`List<WeaponData>` 索引器赋值给接口引用，是否会装箱？
- **用户答案**：D（认为是 ref return）
- **正确答案**：C（发生了装箱）
- **用户结果**：❌ 答错

**知识点详解**：

```csharp
interface IResettable { void Reset(); }

struct WeaponData : IResettable
{
    public int damage;
    public void Reset() { damage = 0; }
}

var list = new List<WeaponData> { new WeaponData { damage = 10 } };
IResettable res = list[0];  // ← 这里装箱！
res.Reset();  // 修改的是堆上的 boxed 副本，list[0] 不受影响
```

**核心原理**：

1. **接口是引用类型**：struct 赋值给 `interface` 变量时，值类型 → 引用类型的转换必然发生**装箱**（在堆上分配一个 boxed 副本）
2. **`List<T>` 索引器是值返回**：`list[0]` 返回的是 struct 的**值副本**，不是引用。D 的选项"ref return"是错误的——`List<T>` 默认索引器没有 `ref` 修饰
3. **装箱后的隔离**：`res.Reset()` 修改的是堆上 boxed 副本的 `damage`，`list[0].damage` 仍然是 10

**如何避免装箱**：
```csharp
// 方式1：直接访问 struct 索引器（不经过接口）
list[0] = new WeaponData { damage = 0 };  // 直接赋值

// 方式2：使用 CollectionsMarshal（.NET 5+）
ref var item = ref CollectionsMarshal.AsSpan(list)[0];
item.Reset();  // 通过 ref 直接操作数组中的 struct

// 方式3：用泛型约束而不是接口引用
void Reset<T>(ref T data) where T : IResettable
{
    data.Reset();  // 泛型方法中调用接口方法不会装箱（JIT 生成特化版本）
}
```

**性能影响**：装箱分配堆内存 + GC 压力。在 Update 循环或频繁调用的路径中，避免 struct → interface 转型。

**深入追问：为什么 `List<T>` 索引器是值返回？**

**底层原理**：

`List<T>` 内部维护了一个 `T[] _items` 数组。索引器的 C# 编译器生成逻辑相当于：

```csharp
// List<T> 索引器编译后的伪代码
public T get_Item(int index)
{
    return _items[index];  // ← 返回的是 _items[index] 的副本
}
```

没有 `ref` 修饰符 → 值返回。结构体的**所有字段**被逐字节拷贝到调用方的栈上。

**三步拆解 `IResettable res = list[0]`**：

```
第一步: list[0] 值返回
  ┌─ 堆上数组 _items[0]: damage=10 ─┐
  │   ↓ 值拷贝                        │
  │  栈上临时变量 tmp: damage=10      │
  └───────────────────────────────────┘

第二步: 赋值给接口引用 → 装箱
  ┌─ 栈上 tmp: damage=10 ────────────┐
  │   ↓ 装箱                           │
  │  堆上 boxed 对象: damage=10       │
  └───────────────────────────────────┘

第三步: res.Reset() 改的是 boxed 对象
  ┌─ boxed.damage = 0 ← res.Reset() ─┐
  │  但 list[0].damage 仍然 = 10     │
  └───────────────────────────────────┘
```

**值返回 vs ref return 对比**：

| 操作 | 行为 | 堆分配 | 能否原地修改 |
|------|------|--------|------------|
| `var x = list[0]` | 值拷贝 | 无 | ❌ 改的是副本 |
| `IInterface x = list[0]` | 值拷贝 → 装箱 | ✅ 有 | ❌ 改的是 boxed |
| `ref var x = ref span[0]` | **零拷贝引用** | 无 | ✅ 原地改 |

**如何用 ref return 避免装箱**：

```csharp
using System.Runtime.InteropServices;

// ✅ 方式一：CollectionsMarshal.AsSpan
ref var item = ref CollectionsMarshal.AsSpan(list)[0];
item.damage = 999;  // 直接修改数组中原始 struct，零分配

// ✅ 方式二：直接用数组（如果持有 _items 引用）
WeaponData[] arr = list.ToArray();  // 注意：ToArray() 又拷贝了一次
```

**性能实测结论**：
- 装箱触发：堆分配 → GC 标记 → 回收。高频路径（Update）下每秒几千次装箱直接导致 GC spikes
- `ref CollectionsMarshal.AsSpan` 是零分配操作，适用于 Update 循环、物理回调等热路径

#### Q4（经典面试 ✅）IL2CPP 特性

**题目**：以下关于 IL2CPP 的说法，哪个是正确的？
- **用户答案**：B
- **正确答案**：B
- **用户结果**：✅ 答对

**知识点详解**：

IL2CPP（Intermediate Language To C++）是 Unity 的 AOT 编译后端，核心流程：

```
C# 源码 → IL（中间语言）→ C++ 代码 → 原生二进制
```

**各选项解析**：

| 选项 | 内容 | 正误 | 原因 |
|------|------|------|------|
| A | 保留了 JIT 编译器 | ❌ | IL2CPP 是纯 AOT，没有 JIT |
| **B** | **C# IL → C++ → 原生二进制** | **✅** | **核心流程正确** |
| C | 不支持任何泛型 | ❌ | 支持泛型，通过代码分裂/共享机制处理 |
| D | 编译比 Mono 快，运行更慢 | ❌ | 编译比 Mono 慢得多（多了 C++ 编译步骤），运行性能更好（原生代码） |

**IL2CPP 关键特性**：

1. **泛型处理**：IL2CPP 使用泛型代码分裂（Generic Code Splitting）——对于引用类型泛型参数共享同一份 C++ 实现，值类型泛型参数生成特化版本。不是"不支持泛型"
2. **代码裁剪（Managed Stripping）**：IL2CPP 搭配 Unity 的代码裁剪，会移除未使用的 IL 代码，减少包体。Level 可选：Disabled → Low → Medium → High
3. **反射限制**：AOT 编译下动态 `Assembly.Load`、`Activator.CreateInstance(type)` 可能失败，需要提前通过 link.xml 保留类型
4. **编译时间**：IL2CPP 比 Mono 慢很多（主要原因：生成 C++ 代码 + C++ 编译器编译），但 iOS/主机平台只能用 IL2CPP
5. **运行时性能**：通常比 Mono 更好（原生二进制 vs 解释执行），尤其是数值密集型计算

#### Q5（项目实战 ✅）VR 爆炸力定向替代方案

**题目**：VR 消防仿真中 `Rigidbody.AddExplosionForce` 效果不稳定，更可靠的替代方案？
- **用户答案**：C
- **正确答案**：C
- **用户结果**：✅ 答对

**知识点详解**：

`AddExplosionForce` 的缺陷：
1. 内置的**平方反比衰减曲线**不可控，距离爆炸点越近冲击力越大，但混合多个爆炸源时衰减叠加效果难以预测
2. 重叠/堆叠物体产生奇怪的推力叠加，尤其是紧密排列的物体
3. 只计算从爆炸点到 collider 最近点的方向向量，对凹形物体可能产生奇怪方向

**推荐的 C 方案实现**：
```csharp
void ApplyExplosionForce(Vector3 origin, float radius, float force, LayerMask targetLayers)
{
    Collider[] hits = Physics.OverlapSphere(origin, radius, targetLayers);
    foreach (var hit in hits)
    {
        Rigidbody rb = hit.attachedRigidbody;
        if (rb == null) continue;

        Vector3 dir = (hit.transform.position - origin).normalized;
        float dist = Vector3.Distance(origin, hit.transform.position);
        float falloff = 1f - Mathf.Clamp01(dist / radius);

        // 使用 Impulse 模式：瞬间施加冲量
        rb.AddForce(dir * (force * falloff), ForceMode.Impulse);
    }
}
```

**手动方案的优势**：
1. **方向精确可控**：可以改用 collider.bounds.center 或质心替代 transform.position 来计算方向
2. **衰减自定义**：可以换用 `Mathf.SmoothStep` 或 `AnimationCurve` 自定义衰减曲线
3. **分层施加**：可以对不同 Layer 施加不同的力、额外的 upForce（扬尘效果）、随机扰动
4. **物理引擎依然参与**：`AddForce(Impulse)` 会将冲量提交给 PhysX 物理引擎，碰撞响应、摩擦、反弹都正常

**四种方案对比**：

| 方案 | 物理正确 | 可控性 | 适用场景 |
|------|---------|--------|---------|
| A. Transform.position 手动移动 | ❌ | ✅ | 纯视觉不需要物理交互 |
| B. CharacterController.Move | ❌ | ✅ | 角色控制（非物理物体） |
| **C. AddForce + 方向向量** | **✅** | **✅** | **物理爆炸、碎片飞散** |
| D. 直接改 velocity | ⚠️ 部分 | ⚠️ | 特效/预计算轨迹 |

#### Q1（项目实战 ✅）静态批处理规则

**题目**：关于 Unity 静态批处理（Static Batching），哪个说法正确？
- **用户答案**：C
- **正确答案**：C
- **用户结果**：✅ 答对

**知识点详解**：

| 选项 | 内容 | 正误 | 原因 |
|------|------|------|------|
| A | 光照贴图不同也能合并批次 | ❌ | 光照贴图不同 → 不同材质球 → 无法合并 |
| B | 静态批处理后 Transform 信息丢失 | ❌ | 静态批处理只是合并网格，不丢失 Transform |
| **C** | **需要 Batching Static + 相同材质球** | **✅** | **核心条件正确** |
| D | Runtime 时在 Profiler 才能看到 | ❌ | Editor 的 Game 视图 Stats 窗口直接显示 Saved by batching |

**静态批处理的工作原理**：
1. Unity 在 **构建时（Build）或进入 Play Mode 时** 将标记为 Batching Static 的物体网格合并为一个大网格
2. 合并后的网格使用**同一个材质球**渲染，一次 DrawCall 绘制所有内容
3. 每个子物体保留自己的 Transform 信息，在 GPU 侧通过索引偏移量定位

**静态批处理条件检查清单**：
- ✅ 物体标记 `Batching Static`（或 Inspector 中勾选相应 Static 标记）
- ✅ 使用**完全相同的材质球**（同一个 Material 实例）
- ✅ 网格格式支持合并（部分 GPU 不支持 32-bit index buffer 限制合并网格大小 — 通常不超过 64K 顶点）
- ❌ 光照贴图不同 → 材质不同 → 直接拆批
- ❌ 光照探针偏移不同 → 可能拆批

**静态批处理 vs GPU Instancing vs SRP Batcher**：

| 特性 | 静态批处理 | GPU Instancing | SRP Batcher |
|------|-----------|---------------|-------------|
| 合并时机 | Build 时 | Render 时 | Render 时 |
| 顶点上限 | ~64K | 无（受显存限制） | 无 |
| 材质要求 | 完全相同 | 可以不同（属性差异） | 相同 Shader Variant |
| 网格要求 | 不同网格可合并 | **相同网格** | 不同网格可合并 |
| 内存开销 | 合并后网格常驻显存 | 低（实例化数据流） | 中等（CBV 缓存） |
| 动态物体 | ❌ 不支持 | ✅ 支持 | ✅ 支持 |

#### Q2（项目实战 ✅）CharacterController 斜坡处理

**题目**：CharacterController 斜坡移动，哪种处理方式正确？
- **用户答案**：C
- **正确答案**：C
- **用户结果**：✅ 答对

**知识点详解**：

```csharp
// ✅ 正确做法：获取地面法线 → 投影运动方向
void OnControllerColliderHit(ControllerColliderHit hit)
{
    // hit.normal 就是地面法线

```

**各选项解析**：

| 选项 | 内容 | 正误 | 原因 |
|------|------|------|------|

| **C** | **OnControllerColliderHit 获取法线 + ProjectOnPlane** | **✅** | **标准做法** |
| D | 换成 Rigidbody 物理移动解决一切 | ❌ | Rigidbody 也面临同样问题（除非用专门的斜坡处理组件） |

**CharacterController 斜坡处理完整方案**：
```csharp
public class CharacterControllerSlope : MonoBehaviour
{
    private CharacterController controller;
    private Vector3 moveDirection;
    private Vector3 groundNormal = Vector3.up;
    private float slopeLimit = 45f;

    void Awake() => controller = GetComponent<CharacterController>();

    void OnControllerColliderHit(ControllerColliderHit hit)
    {
        groundNormal = hit.normal;

        // 检测是否超过斜坡限制
        float angle = Vector3.Angle(Vector3.up, hit.normal);
        if (angle > slopeLimit)
        {
            // 超过斜坡限制 → 禁止继续向上
            moveDirection = Vector3.ProjectOnPlane(moveDirection, hit.normal);
        }
    }

    void Update()
    {
        Vector3 input = new Vector3(Input.GetAxis("Horizontal"), 0, Input.GetAxis("Vertical"));
        // 沿地面法线投影输入方向
        moveDirection = Vector3.ProjectOnPlane(input, groundNormal).normalized;
    }
}
```

#### Q3（项目实战 ✅）WaitForSeconds + timeScale=0

**题目**：协程中 `yield return new WaitForSeconds(2f)`，当 `Time.timeScale = 0` 时会发生什么？
- **用户答案**：C
- **正确答案**：C
- **用户结果**：✅ 答对

**知识点详解**：

```csharp
// WaitForSeconds 的内部实现原理
// 等价于：
float waitUntilTime = Time.time + duration;  // 记录期望的结束时间
while (Time.time < waitUntilTime)
    yield return null;  // 每帧检查

// timeScale=0 → Time.time 停止增长 → waitUntilTime 永远到不了 → 协程永远等待
```

**核心原理**：

1. `WaitForSeconds` 在**构造时**读取 `Time.time` 记录当前时间 + duration 得到预期恢复时间
2. 每帧 Unity 的协程调度器检查 `Time.time >= waitUntilTime`
3. `Time.timeScale = 0` → `Time.time` **不增长**（因为有 `Time.time = Time.realtimeSinceStartup * timeScale`）
4. 因此 `Time.time` 永远达不到 `waitUntilTime`，协程永远等不到恢复

**各选项解析**：

| 选项 | 内容 | 正误 | 原因 |
|------|------|------|------|
| A | 协程无效，因为协程不在主线程跑 | ❌ | 协程始终在主线程运行 |
| B | WaitForSeconds 等价于 yield return null | ❌ | WaitForSeconds 是专门的计时器，不是 null |
| **C** | **协程永远等不到恢复，因为 Time.time 不增长** | **✅** | **正确解释了根本原因** |
| D | 协程会在 WaitForSeconds 中断 | ❌ | 不完全准确——不是中断，是等不到恢复 |

**相关 API 对比**：

| API | 受 timeScale 影响 | 受 unscaled 影响 | 用途 |
|-----|------------------|------------------|------|
| `WaitForSeconds` | ✅ 是 | ❌ 否 | 游戏内计时 |
| `WaitForSecondsRealtime` | ❌ 否 | ✅ 是 | UI动画、不受暂停影响 |
| `WaitForEndOfFrame` | ❌ 否 | ❌ 否 | 帧尾回调 |
| `WaitUntil` | ❌ 否 | ❌ 否 | 自定义条件等待 |

#### Q4（经典面试 ✅）Awake/OnEnable/Start 生命周期批次执行

**题目**：Unity MonoBehaviour 生命周期事件 Awake/OnEnable/Start 的执行顺序？
- **用户答案**：B
- **正确答案**：B
- **用户结果**：✅ 答对

**知识点详解**：

| 选项 | 内容 | 正误 | 原因 |
|------|------|------|------|
| A | Start 会被延迟到下一帧 | ❌ | Start 在第一个 Update 之前，不是延迟到下一帧 |
| **B** | **所有 Awake → 所有 OnEnable → 所有 Start → 第一个 Update** | **✅** | **批次执行顺序正确** |
| C | Awake/Start 受 enabled=false 影响 | ❌ | Awake 和 Start 不受 enabled=false 影响，OnEnable 受 |
| D | Start 是协程函数 | ❌ | Start 是普通生命周期函数，不是 IEnumerator |

**批次执行顺序详解**：

```
场景加载开始
  ↓
所有对象的 Awake() 执行完毕 ← 批次1
  ↓
所有对象的 OnEnable() 执行完毕 ← 批次2（只有 enabled=true 的对象会收到）
  ↓
所有对象的 Start() 执行完毕 ← 批次3
  ↓
第一个 Update() ← 逐帧开始
```

**关键点**：
1. **批次内顺序不确定**：同一批次内（如多个对象的 Awake），执行顺序取决于对象在 Hierarchy 中的顺序，不要依赖特定顺序
2. **OnEnable 的先后条件**：prefab 实例化后如果 `enabled = false`，则 OnEnable 在后续 `enabled = true` 时才触发，不影响 Awake/Start 的批次
3. **销毁时逆序**：对象销毁时执行相反顺序 —— OnDisable → OnDestroy
4. **差异对比**：

| 方法 | 调用时机 | 受 enabled 影响 | 是否批次执行 |
|------|---------|----------------|------------|
| Awake | 对象实例化后立即执行 | ❌ | ✅ 同一批 |
| OnEnable | 对象 SetActive(true) 时 | ✅ 是 | ✅ 同一批 |
| Start | 第一个 Update 之前 | ❌ | ✅ 同一批 |
| Update | 每帧 | ✅ 是 | ❌ 逐帧 |

#### Q5（经典面试 ❌）struct 装箱陷阱（连续第 2 次失分 ❌）

**题目**：struct 装箱后拆箱副本修改，原值变化？
```csharp
struct ScoreData
{
    public int value;
    public ScoreData(int v) => value = v;
    public void Reset() => value = 0;
}

var scores = new List<ScoreData> { new ScoreData(10) };
IResetable reset = scores[0];  // 装箱
((ScoreData)reset).value = 0;   // 拆箱修改
Console.WriteLine(scores[0].value);  // 输出？
```
- **用户答案**：A（认为是 0）
- **正确答案**：B（输出 10）
- **用户结果**：❌ 答错

**核心原理（与 Day 9 互补）**：

```csharp
// 代码执行流程分解
var scores = new List<ScoreData> { new ScoreData(10) };
// scores[0] = { value=10 } ← 数组中的原始数据

IResetable reset = scores[0];
// ① list[0] 值返回 → 栈上临时副本（value=10）
// ② 赋值给接口引用 → 堆上 boxed 对象（value=10）

((ScoreData)reset).value = 0;
// ③ 拆箱：从 boxed 对象复制到**新的栈上临时变量**（value=0）
// ④ 修改的是这个新临时变量的 value，boxed 对象不受影响
// ⑤ 临时变量在表达式结束后立即丢弃

Console.WriteLine(scores[0].value);  // 仍然是 10
```

**关键记忆点**：
1. **装箱 = 复制**：值类型转接口引用时，会在堆上创建一个全新的 boxed 副本
2. **拆箱 = 再复制**：从接口引用转回值类型时，又从 boxed 对象复制一份到栈上
3. **两次复制 → 完全隔离**：`((ScoreData)reset).value = 0` 修改的是第二次复制的临时变量，原始数据、boxed 对象、list[0] 纹丝不动
4. **与 Day 9 的对比**：
   - Day 9：`res.Reset()` 改的是 boxed 副本（list[0] 不变）
   - Day 10：`((ScoreData)reset).value = 0` 改的是拆箱临时副本（boxed 和 list[0] 都不变）

**Day 9 → Day 10 失分原因分析**：
- Day 9 的答错说明对**装箱的堆上隔离机制**理解不够扎实
- Day 10 的答错说明对**拆箱后修改行为**这个互补知识点也没掌握
- 这两个知识点是同一类问题的正反两面，建议对照记忆
