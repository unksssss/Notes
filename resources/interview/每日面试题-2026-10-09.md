## 选择题（Q1~Q5）

### Q1【库外新题·面经】大世界场景的 CPU 端视锥剔除

**来源**：牛客·「unity 引擎 一面+二面」（图形向）

开放世界场景里有上万个 Renderer，逐物体做视锥剔除是 O(N)。要把它降到 O(logN) 量级，业界常用的做法是？

- A. 依赖 Unity 内置 Frustum Culling 即可，它内部已经做了场景空间划分
- B. 用八叉树 / 四叉树 / BVH 做空间划分，剔除时先测节点包围盒，不相交则整棵子树跳过
- C. 开启 GPU Instancing，重复物体交给 GPU 就不用 CPU 剔除了
- D. 全部标记为 Static 走静态批处理，批处理自带剔除

**参考答案**：**B**

**解析**：

1. **Unity 内置的视锥剔除不做场景级空间划分**——它仍然是逐 Renderer 用包围盒与六个视锥平面求交，复杂度 O(N)。这是最容易答错的一点（选项 A 是陷阱）。
2. **层次剔除（hierarchical culling）** 的核心是三态判定：节点包围盒**完全在视锥外** → 整棵子树直接跳过；**完全在内** → 整棵子树全部接受，不再下钻；**相交** → 才递归子节点。所以是 O(logN) 级，且能批量剔除。
3. **三种结构怎么选**：
   - **八叉树**：3D 空间均匀递归八分，适合分布较均匀的三维场景（如室内多层、洞穴）；
   - **四叉树**：只在 XZ 平面划分，适合地形、俯视 2.5D、大世界地块；
   - **BVH**：按物体聚类而非等分空间，适合**分布疏密不均**的场景，且**动态物体重插成本低**（只需自底向上重算父节点包围盒）。
4. **工程取舍**：静态物体预烘焙八叉树/四叉树并序列化；动态物体用 BVH 或**松散八叉树（loose octree）**——把节点边界放大一圈，物体在小范围移动时不会跨节点，避免每帧重插。

### Q2【官方新特性】Unity 6.7 LTS 的 SCGI

**来源**：Unite 2026 主题演讲 + Unity 6.4→6.8 路线图

关于 Unity 6.7 LTS 主推的实时全局光照方案 **SCGI（Surface Cache GI）**，下列说法正确的是？

- A. SCGI 仍需预先烘焙光照贴图，只是烘焙速度更快
- B. SCGI 用世界空间的 Surface Cache 缓存表面光照，免烘焙且支持动态几何体
- C. SCGI 是屏幕空间方案（SSGI 升级版），只能接收屏幕内可见物体的光照贡献
- D. SCGI 仅在 Built-in 渲染管线提供，URP 不支持

**参考答案**：**B**

**解析**：

1. **关键在于「世界空间」而非「屏幕空间」**。屏幕空间 GI（SSGI）只能用当前帧可见像素反推光照，导致两个典型缺陷：屏幕外的遮挡物/发光体无法贡献光照；镜头一动边缘就闪烁/漏光。SCGI 用 **Surface Cache（世界空间表面缓存）** 存住每个表面的 irradiance，天然规避这两个问题。
2. **免烘焙**：不需要 Lightmap UV、不需要漫长的烘焙等待，美术改完光照即刻可见。
3. **支持动态几何体**：动态物体移动不必重新烘焙，也不依赖 Light Probe 的稀疏采样。
4. **路线图关联考点**（同一条官方动态里的其他点，容易被追问）：
   - **Built-in 渲染管线 6.5 起弃用**，URP 成为唯一统一管线；
   - **6.6 支持 DXC** 编译 DX12 shader（替代老 FXC）；
   - **6.7 快速构建配置**把 shader 构建时间缩短最高 90%；
   - **CoreCLR 迁移 6.5→6.8**，取消 domain reload，支持 .NET 10 / C# 14。

### Q3【库外新题·面经】AB 依赖包被提前卸载导致材质变洋红

**来源**：CSDN·Unity 面试高频问题

主资源包 `A` 依赖共享材质包 `M`。若先把 `M` 卸载，之后再加载 `A` 并实例化其中的 prefab，会出现什么现象？根因是什么？

- A. 没有影响，材质引用会在需要时自动重新加载
- B. 材质变洋红/粉红（Missing），因为 `M` 里的资产对象已被卸载，A 的依赖引用悬空
- C. 直接抛 NullReferenceException 崩溃
- D. 材质变黑，但功能完全正常

**参考答案**：**B**

**解析**：

1. **AssetBundle 依赖是「对象级引用」而非「路径级引用」**：打主包时，被依赖的资产**不会**打进主包，而是留一个对依赖包的引用。加载主包前必须先加载依赖包，否则引用悬空。
2. `Unload(false)` 只卸载 bundle 内的**资产对象**（Asset），不销毁已实例化到场景里的对象；但那些仍活着的实例身上的材质引用，会指向一个**已被销毁的 Unity Object** → 渲染时拿不到 shader/贴图，Unity 用**洋红色（Magenta）**兜底显示。
3. **正确的卸载顺序**（三步）：
   1. 先 `Destroy` 所有由该批 bundle 实例化出的 GameObject；
   2. 再 `Unload(false)` 各主包；
   3. **最后**才 Unload 共享依赖包，且必须确认它的**引用计数归零**（所有依赖它的主包都释放完）。
4. 📎 详见 [[AssetBundle 生命周期与卸载语义]]

### Q4【拔高】多 Bundle 共享依赖时的 `Unload(true)`

包 `A` 和包 `B` 都依赖共享包 `M`，且场景里已有从 `A`、`B` 的 prefab 实例化出来的物体（它们身上的材质来自 `M`）。此时对 `M` 调用 `Unload(true)`，结果是？

- A. 只卸载 `M` 自身，`A`/`B` 加载出来的实例不受影响
- B. 连带销毁**所有**从 `M` 中资产实例化出的对象，包括 `A`/`B` 生成的实例正在使用的那些
- C. 抛异常——共享依赖包不允许调用 `Unload(true)`
- D. 自动把 `M` 的资产深拷贝到 `A`、`B` 中，之后再卸载

**参考答案**：**B**

**解析**：

1. `Unload(false)` 与 `Unload(true)` 的唯一分界线就是：**是否连带销毁「由本 bundle 内资产实例化出来的对象」**。`true` 会遍历并销毁所有这类实例——**不管这些实例是哪个 bundle 的 prefab 生成的**，只要它用到的资产属于 `M`，就在销毁名单里。
2. 这正是共享依赖**绝不能 `Unload(true)`** 的原因：你以为在卸载共享材质，实际把别人正在用的物体全干掉了。
3. **正确做法 = 引用计数**：依赖包被 N 个主包依赖时计数 = N；每个主包释放时 -1；归零后才 `Unload(false)`。Addressables 内建的引用计数就是干这个的（见 S5）。
4. 📎 详见 [[AssetBundle 生命周期与卸载语义]]

### Q5【算法·库外新题】有向图判环

判断一个**有向图**是否存在环，下列哪种方法**不适用**？

- A. Kahn 算法（拓扑排序，入度法）：若最终输出的节点数 < 总节点数，则有环
- B. DFS 三色标记法：递归栈上遇到灰色节点即有环
- C. 并查集（Union-Find）：合并时若两点已在同一集合则有环
- D. Tarjan 强连通分量：存在大小 > 1 的 SCC 则有环

**参考答案**：**C**

**解析**：

1. **并查集只能判「无向图」的环**——它依赖「边没有方向、连通即等价」的语义。有向图里 `A→B` 和 `B→A` 完全不同，并查集会把它俩当成同一条无向边，从而漏判/误判。
2. **Kahn 入度法**（最常用，也最易写）：统计每个节点入度 → 把入度为 0 的入队 → 出队时把它指向的节点入度 -1，若减到 0 则入队 → 循环结束。若**出队总数 < 节点总数**，说明剩下的节点入度永远降不到 0，即存在环。复杂度 **O(V+E)**。
3. **DFS 三色标记**：白（未访问）/ 灰（在当前递归栈上）/ 黑（已完成）。遍历中若遇到灰色邻居 → 有**回边** → 有环。同样 O(V+E)，还能顺带输出具体环路径。
4. **Tarjan SCC**：强连通分量大小 > 1（或单点带自环）即有环，O(V+E)，适合要进一步做「缩点」的场景。
5. **工程落点**：Unity 里这个模型的典型应用是**资源/模块的依赖环检测**（AB 循环依赖、Assembly Definition 循环引用、技能 buff 互相触发的死循环）。

### S1【真实面经】协程的执行顺序由什么决定

**来源**：蛮啾·Unity 客户端一面

**问题**：协程的执行顺序由什么决定？如果同一帧有多个协程的恢复条件同时满足，谁先执行？

**参考答案要点**：

1. **协程不是多线程**，它跑在主线程上，靠 Unity 每帧把 `IEnumerator` 的 `MoveNext()` 推进一次。本质是**编译器生成的状态机**（`yield return` 处切分成多个状态）。
2. **恢复时机由 yield 对象的类型决定**，这是唯一决定因素：
   - `yield return null` → 本帧 Update 之后、LateUpdate 之前恢复；
   - `yield return new WaitForFixedUpdate()` → 下一次 FixedUpdate 之后；
   - `yield return new WaitForSeconds(t)` → 用 `Time.timeScale` 缩放的计时，到点后的那一帧；
   - `yield return new WaitForSecondsRealtime(t)` → 不受 timeScale 影响；
   - `yield return StartCoroutine(other)` → 嵌套，内层跑完才继续；
   - `yield return www / AsyncOperation` → 每帧检查 `isDone`，完成后恢复。
3. **同帧多个协程同时就绪时的顺序 = 启动顺序**（Unity 内部维护一个待恢复队列，按入队先后）。但**不要依赖这个顺序写业务逻辑**——它是实现细节，跨版本不保证。
4. 📎 详见 [[协程原理与unitask]]

### S2【真实面经】TMP 如何渲染一个汉字

**来源**：蛮啾·Unity 客户端一面

**问题**：Unity 内置 `Text` 和 `TextMeshPro` 有什么区别？TMP 渲染一个汉字的具体过程是怎样的？

**参考答案要点**：

1. **根本区别在字体资产的表示方式**：
   - 内置 `Text` 用**动态字体**，运行时把字形**栅格化成位图**塞进一张动态字体贴图 → 放大就糊、字号多时贴图暴涨、贴图满了要重建 → 卡顿；
   - **TMP 用 SDF（Signed Distance Field，有向距离场）字体图集**：贴图里存的不是字的像素，而是**每个像素到字形边缘的距离**。渲染时在 shader 里用 `smoothstep` 在距离场阈值附近做抗锯齿 → **任意缩放都锐利**，一张图集覆盖所有字号。
2. **渲染一个汉字的流程**：
   1. 文本字符串 → 逐字符查 **TMP Font Asset** 的字符表（character table），拿到该字的 **glyph index**；
   2. 用 glyph 的 glyphRect 去 **SDF 图集**里取 UV；
   3. 按字形度量（advance / bearing / ascender）算出这个字的**四个顶点位置**与 UV，塞进 TMP 生成的网格（`TMP_Text` 自己造 mesh，不依赖 UGUI Image）；
   4. 顶点上带 UV2 通道存 SDF 参数，交给 **TMP 的 SDF shader**，用距离场做边缘抗锯齿 → 输出。
3. **汉字的关键坑**：英文字符集小（几十个），SDF 图集一张就够；**汉字常用字 3000+，全量进图集会撑爆显存**。解决：**动态 SDF 字体资产（Dynamic Font Asset）**——运行时按需把新字加进图集（配合 `TMP_Settings.fallbackFontAssets` 做多级回退）。代价是首次出现新字时有一次图集写入开销，所以要**预热常用字**。
4. 📎 详见 [[TMP Text 零分配更新]]

### S3【真实面经】静态图集 vs 动态图集

**来源**：蛮啾·Unity 客户端一面 + Unity 6.4 官方 API

**问题**：SpriteAtlas 的静态图集和动态图集有什么区别？各自适用场景？Unity 6.4 里怎么在运行时创建图集？

**参考答案要点**：

1. **静态图集（Static / "Include in Build"）**：打 SpriteAtlas 资产时，成员精灵在**编辑器期**就确定并打包进图集。运行时**成员不可变**，但**加载即完整、无运行时开销** → 适合 UI 图标、固定资源。
2. **动态图集（Dynamic）**：勾选后，运行时才向图集**请求**精灵（`GetSprite` / 带 `atlasRequested` 回调），按需填充。优点：能容纳运行时下载/生成的图；缺点：首次填充有开销，且图集可能被多次重排。
3. **对合批的影响**：两者都能合批，但**动态图集在填充过程中贴图内容会变**，需要小心 GPU 上传时机；静态图集不存在这个问题。
4. **Unity 6.4 的运行时建图集 API**：

```csharp
var atlas = SpriteAtlasManager.CreateSpriteAtlas();  // Unity 6.4+
atlas.Add(new[] { sprite1, sprite2 });               // 运行时添加成员
// 之后 Image.sprite 指向它即可参与合批
```

   这让「运行时下载的图片也要合批」成为可能——以前这类图只能当散图，必然破批。
5. 📎 详见 [[UGUI 图集原理与合批]]

### S4【真实面经】延迟渲染 vs 前向渲染、G-Buffer、MSAA 为何不兼容

**来源**：牛客·「unity 引擎 一面+二面」（图形向）

**问题**：前向渲染和延迟渲染的区别？延迟渲染的 G-Buffer 里存了什么？为什么 MSAA 和延迟渲染不兼容？

**参考答案要点**：

1. **前向渲染（Forward）**：每个物体在**一次**绘制中直接算完所有光照再写颜色缓冲。复杂度 ≈ **O(物体数 × 光源数)**，光源一多就爆炸；但**天然支持 MSAA**、支持半透明、可用任意 shading model（每个材质自己算）。
2. **延迟渲染（Deferred）**：分两趟。
   - **第一趟 G-Buffer Pass**：把几何信息写进多张渲染目标（MRT），**不做光照**；
   - **第二趟 Lighting Pass**：对每个**屏幕像素**用 G-Buffer 数据算光照 → 复杂度 ≈ **O(屏幕像素 × 光源数)**，光源数量与物体数量解耦，光源多时优势巨大。
3. **G-Buffer 常见内容**（不同管线略有出入）：
   - **Albedo / Diffuse Color**（RGB）+ **Occlusion** 或 **Material ID**（A）
   - **Specular Color**（RGB）+ **Smoothness/Roughness**（A）
   - **World Normal**（RGB，常做八面体压缩存两张分量）+ 剩一个通道
   - **Depth / Stencil**（深度模板缓冲，或单独一张存线性深度）
   - 有的管线再加 **Emission**、**Velocity（用于 TAA/运动模糊）**
4. **为什么 MSAA 不兼容（核心考点）**：
   - MSAA 的原理是：光栅化阶段对**几何边缘**做**多次覆盖采样（coverage）**，但**着色只算一次**，最后按覆盖率把颜色与背景混合 → 只对「几何边缘」有效，成本远低于超采样。
   - 延迟渲染到 Lighting Pass 时，**几何信息已经没了**（只有一堆 G-Buffer 像素），无法知道哪个像素处于三角形边缘 → **覆盖率信息丢失**，MSAA 无从下手。
   - 若强行对 G-Buffer 做 MSAA，会得到「**多个不同的表面被平均**」的荒谬结果：边缘像素的前景色和背景色被插值成一条错误颜色的缝（法线插值尤其灾难）。
   - 所以延迟管线的抗锯齿改用**后处理方案**：**FXAA / SMAA（形态学）** 或 **TAA（时域抗锯齿，靠多帧抖动采样累积）**。
5. **其他取舍**（常被追问）：延迟渲染**半透明麻烦**（必须先前向画完不透明，再单独前向画半透明）、**显存带宽吃紧**（G-Buffer 每帧读写量大）、**不支持每物体不同 shading model**（G-Buffer 布局是统一的）。

### S5【真实面经】Addressables 引用计数与 Release 时机

**来源**：CSDN·Unity 面试高频问题

**问题**：Addressables 的引用计数是怎么工作的？什么时候该调用 `Release`？`LoadAssetAsync` 和 `InstantiateAsync` 该怎么取舍？

**参考答案要点**：

1. **引用计数的对象不是「资源文件」而是「句柄 AsyncOperationHandle」**。每次 `LoadAssetAsync` 同一地址，返回**不同句柄**但底层共享同一份加载结果，内部计数 +1；每 `Release(handle)` 一次计数 -1；**归零时才会真正卸载**该资源。
2. **两条铁律**：
   - **谁加载谁释放**，且**每个 handle 只 Release 一次**（重复 Release 会报 "handle 已被释放" 类错误）；
   - **Release 的是 handle，不是对象**。用 `Addressables.ReleaseInstance(instance)` 释放实例时，它内部会找到创建该实例的 handle 并 Release；但你手动 `Destroy(instance)` 就**不会**减计数 → 内存泄漏。
3. **Release 时机**：资源确定不再使用的那一刻。常见错误是「切场景时统一 Release」——如果新场景立刻又要加载同一资源，会造成**卸载→重新加载**的抖动。正确粒度是**跟着持有者的生命周期**：这个 GameObject 销毁时就释放它加载的资源（在 `OnDestroy` 里配对）。
4. **`LoadAssetAsync` vs `InstantiateAsync`**：
   - `InstantiateAsync(addr)` = 加载 + 实例化二合一，Addressables **会记住实例与 handle 的绑定**，`ReleaseInstance` 时自动回收 → **推荐**，尤其是同一 prefab 要实例化多次的场景；
   - 若你只想加载资产自己控制实例化时机（比如要 pool 起来），用 `LoadAssetAsync` + 自己 `Instantiate`，但要记得**自己配对 Release**。
5. **分组策略要点**：按「**生命周期一致**」分组，而不是按目录/类型分。UI 图标一组、关卡资源一组、常驻资源一组——生命周期不一致的资源放同一个 bundle，会导致「为了释放一个小资源，把整包都留在内存」。
6. 📎 详见 [[Addressables资源生命周期]]

### S6【拔高】SRP Batcher 的 CBUFFER

**来源**：拔高题（已掌握点换角度加深，历史：Day 36 S2 ⚠️ 0.5 → Day 37 Q5 补讲后答对）

**问题**：SRP Batcher 到底批处理掉了什么？为什么说它靠的是 CBUFFER 的统一布局？为什么 `MaterialPropertyBlock` / 直接改 `material.color` 会破坏它？

**参考答案要点**（要答到 CBUFFER 层）：

1. **传统批处理（静态/动态合批）** 减少的是 **DrawCall 数量**（合并网格）；**SRP Batcher 减少的不是 DrawCall 数，而是每次 DrawCall 的 CPU 设置开销（SetPass Call）**。DrawCall 数可能一个都没少，但每次绘制的 CPU 时间大幅下降。
2. **机制**：SRP Batcher 把「**每个材质的属性**」持久化地缓存在 GPU 的 **CBUFFER（常量缓冲）**里，并要求所有使用同一 shader 的材质遵循**统一的 CBUFFER 布局**（变量名、类型、顺序完全一致）。于是：
   - 材质数据**只在变化时上传一次**，不随每次绘制重传；
   - 绘制时只需绑定一个「CBUFFER 偏移」，不做 SetPass → CPU 开销骤降。
3. **破坏它的原因**：
   - **改 `material.color` / `material.SetFloat`** → Unity 会为这个材质创建一份**独立实例**（material instancing），数据变了就要重新上传 CBUFFER → 打断批；
   - **用 `MaterialPropertyBlock`（MPB）** → MPB 是给**单个 Renderer** 传参的机制，它的数据**不在那个统一 CBUFFER 里**，SRP Batcher 无法复用 → 破坏。
   - 想给不同实例不同的参数又不破批：走 **GPU Instancing 传实例数据**（但见下一条）。
4. **与 GPU Instancing 互斥**：SRP Batcher 要求「按材质聚合」，GPU Instancing 要求「按网格 + 实例属性数组聚合」，两者对 draw 的组织方式冲突——**同一个物体不能同时享受两者**。用 Instancing 时物体会被排除出 SRP Batcher。
5. **面试加分**：SRP Batcher 的兼容条件是 **shader 必须把材质属性声明在 `UnityPerMaterial` CBUFFER 内**（Built-in 的老 shader 常常不符合，这是 HLSL 转 URP 时的常见坑）。
6. 📎 详见 [[Unity 渲染批处理体系]]

### S7【拔高】对象池进阶

**来源**：拔高题（已掌握点加深，历史：Day 36 S7 ⚠️ → Day 37 S4 ✅）

**问题**：① 对象池在场景切换时该怎么处理？② 是不是所有频繁创建销毁的对象都该池化？请给出不该池化的判据。

**参考答案要点**：

1. **跨场景清理策略**（三种，按项目选）：
   - **`DontDestroyOnLoad` 常驻池**：适合全局通用对象（伤害数字、特效、子弹）。**必须自己管生命周期**，否则成为跨场景内存泄漏源；
   - **按场景生命周期绑定**：在 `SceneManager.sceneUnloaded` 回调里 `Clear()` 并 `Destroy` 池中对象。适合「只在当前场景用」的池；
   - **引用计数 + 延迟销毁**：切场景时标记 pending clear，若有对象仍被引用则等它归还后再销毁。最稳，实现最复杂。
2. **必须做的清理动作**（常被漏答）：`Clear()` 只清列表是不够的，要 `Destroy` 掉池里的 GameObject，否则它们只是从池里移除，**还在场景里占内存**。
3. **不该池化的判据（反面清单）**：
   - **长生命周期对象**：池化的收益来自「创建/销毁频次」，玩家角色、UI 面板、场景管理器这类**几分钟才一次**的对象，池化只会**白白常驻内存**；
   - **内存占用大但数量少**：带大贴图/大网格的对象（比如过场动画的专属模型），池化 = 长期占着显存，得不偿失；
   - **状态复杂难重置**：池化的最大隐患是「**归还时忘了重置状态**」——脏数据带到下一次使用。状态越多越容易漏，重置成本可能超过创建成本；
   - **数量不可预测且可能暴涨**：池会为了应对峰值而膨胀，且**默认不会自动缩容**，峰值过后内存一直不降（要加空闲缩容策略）。
4. **一句话判据**：**高频 + 短命 + 状态简单 + 体积小** 才池化。四者缺一就该重新算账。
5. 📎 详见 [[对象池实现]] 📎 [[对象池 OnEnable OnDisable 最佳实践]]

### S8【实战复习】静态事件的内存泄漏

**问题**：用事件驱动做 UI 与逻辑分层时，订阅事件后忘记取消订阅会怎样？静态事件为什么尤其危险？怎么解？

**参考答案要点**：

1. **泄漏的本质**：`somePublisher.OnXXX += Handler;` 这行代码让 **Publisher 持有了 Subscriber 的委托引用**，而实例方法的委托**隐式持有 `this`** → Publisher 活着，Subscriber 就**永远无法被 GC 回收**（即使它的 GameObject 已经 Destroy 了）。
2. **表现**：切场景后 MonoBehaviour 的 `OnDestroy` 明明执行了，但对象还在内存里；反复进出场景内存持续上涨；更糟的是**已销毁对象的回调仍被触发**，访问已销毁的 Unity Object → 报 "has been destroyed but you are still trying to access it"。
3. **静态事件尤其危险**的原因：静态成员的生命周期 = **整个应用程序域**，它是「永不死亡的根（GC Root）」。订阅一个静态事件 = 把自己的引用挂到了一个永远不会释放的对象上 → **必然泄漏**，不随场景切换而解除。
4. **三种解法**：
   - **最稳、最推荐**：在 `OnEnable/OnDisable` 中**成对**订阅/取消（而不是 `Awake/Start`），配合 `SetActive` 语义天然对齐；
   - **弱引用事件（WeakEvent）**：Publisher 只持有 `WeakReference<Subscriber>`，Subscriber 被回收后自动失效并从订阅列表移除。适合静态事件/全局事件总线；
   - **一次性订阅**：明确只触发一次的（如资源加载完成回调），回调里立刻取消订阅。
5. **为什么用 OnEnable/OnDisable 而不是 Awake/OnDestroy**：对象被 `SetActive(false)` 时 `OnDisable` 会执行 → 顺带停止响应事件；而 `OnDestroy` 之前对象一直活着。另外 `Awake` 在对象首次激活时才调用，**重复激活不会重新订阅**。
6. 📎 详见 [[UI-逻辑-数据分层与事件驱动]]

### S9【经典基础】TCP vs UDP

**问题**：游戏里 TCP 和 UDP 分别用在什么场景？UDP 不可靠，怎么让它变可靠？

**参考答案要点**：

1. **对比**：TCP 可靠有序、有拥塞控制、面向流；UDP 无连接、不保证到达/顺序、无拥塞控制、面向报文、头部小（8 字节 vs TCP 20+）。
2. **为什么动作类游戏不直接用 TCP**：TCP 的**队头阻塞**——一个包丢了，后续所有包都要等它重传，而重传至少等一个 RTT。对实时同步来说这是灾难（一个 100ms 的抖动直接把画面卡住）。而且 TCP 的丢包重传在弱网下会**放大延迟**。
3. **场景划分**：
   - **TCP**：登录、支付、聊天、排行榜、存档同步 —— 数据必须完整有序，不在乎多等几十毫秒；
   - **UDP**：实时位置同步、射击判定、帧同步/状态同步的战斗包 —— **新数据比旧数据重要**，丢一帧位置无所谓，下一帧马上来了。
4. **让 UDP 可靠 = 在应用层自己实现 TCP 的子集**，保留 UDP 的无队头阻塞特性：
   - **ACK + 超时重传**（只重传真正需要的那份数据）；
   - **序号**（处理乱序与去重）；
   - **滑动窗口 / 拥塞控制**（可选，轻量版）；
   - **选择性重传**：只补丢的那个包，而不是阻塞整条流。
   - 现成方案：**KCP**（牺牲 20%~30% 带宽换 30%~40% 的延迟降低，ARQ 协议，游戏圈常用）、**ENet**、**QUIC**。
5. **关键认知**：「可靠 UDP」不是把 UDP 变成 TCP，而是**按数据的可靠性需求分级**——关键事件（开枪、死亡）走可靠通道，高频状态（位置）走不可靠通道，两者互不阻塞。
6. 📎 详见 [[unity网络同步方案-状态同步vs帧同步]]

### S10【算法·弱点必考】最小栈

**来源**：历史遗留弱点（Day 36 S10 截断未答 + Day 38/39/40 连续三轮计划补考，本轮必出）

**问题**：设计一个栈，除了常规 `push/pop/top` 之外，还能在 **O(1)** 时间内返回栈中的最小元素。

**参考答案要点**（两种解法都要会）：

**解法一：双栈（同步栈）** —— 最直观

```csharp
public class MinStack {
    private Stack<int> data = new Stack<int>();
    private Stack<int> mins = new Stack<int>();   // 与 data 同步，栈顶永远是当前最小值

    public void Push(int x) {
        data.Push(x);
        // 关键：新值 <= 当前最小值 才压入 mins（用 <= 保证重复最小值弹出后仍正确）
        if (mins.Count == 0 || x <= mins.Peek()) mins.Push(x);
    }
    public void Pop() {
        // 关键：弹出的值等于当前最小值时，mins 也要同步弹
        if (data.Pop() == mins.Peek()) mins.Pop();
    }
    public int Top()    => data.Peek();
    public int GetMin() => mins.Peek();
}
```

- 时间复杂度：全部 O(1)；空间复杂度 **O(n)**（最坏情况：元素单调递减，mins 存了所有元素）。
- **易错点 1**：`Push` 里必须是 `<=` 而不是 `<`。若用 `<`，压入两个相同的最小值时 mins 只存一个，弹掉一个后 mins 就没了 → `GetMin` 出错。
- **易错点 2**：`Pop` 里比较用 `==` 而不是 `>=`，因为 mins 里只有「曾成为最小值」的那些值。

**解法二：差值编码（单栈 + 一个变量）** —— 空间 O(1) 的进阶版

栈里存的不是原值，而是**「当前值与当前最小值的差 (diff)」**，另外用一个变量 `min` 记录当前最小值：

```csharp
public class MinStack {
    private Stack<long> diffs = new Stack<long>();  // 必须 long，diff 会溢出 int
    private long min;

    public void Push(int x) {
        if (diffs.Count == 0) { min = x; diffs.Push(0); }
        else {
            diffs.Push((long)x - min);
            if ((long)x < min) min = x;             // 差为负 → 来了新最小值
        }
    }
    public void Pop() {
        long diff = diffs.Pop();
        if (diff < 0) min = min - diff;             // 弹走的是曾经的最小值，还原旧的 min
    }
    public long Top() => diffs.Peek() <= 0 ? min : min + diffs.Peek();
    public long GetMin() => min;
}
```

- 空间 O(1)（只多一个 `min` 变量），时间 O(1)。
- **必须用 `long`**：`x - min` 在 int 边界（如 `x = int.MaxValue`、`min = int.MinValue`）时会**溢出**。这是面试里最常挂的一细节。
- **还原逻辑**：`diff < 0` 说明压入时它刷新了最小值，弹走它要把 `min` 还原成 `min - diff`。

**两种解法的取舍**：双栈好写好懂、生产环境首选；差值编码省空间但易出错，考察的是对「编码与还原」和整数溢出的理解。
