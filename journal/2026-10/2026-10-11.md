#### 1. `Assets/AOT/LoadDllScripts.cs` —— 反射调用被剥离出热更主链路

主链路（Initialize → 版本 → 清单 → 差异下载 → 加载 DLL → Release → 切场景）保持不变，**关键变更是把「反射调用热更类」整段注释掉、移交给 `GameManager`**：

```diff
- // 获取dll中的类
- Type helloType = hotupdateAss.GetType("Hello");
- // 获取类的方法
- MethodInfo helloMethod = helloType.GetMethod("Run");
- // 调用
- helloMethod.Invoke(null, null);
+ /*
+ // 获取dll中的类
+ Type helloType = hotupdateAss.GetType("Hello");
+ ...
+ */
  // 卸载资源包
  dllHandle.Release();
+ yield return new WaitForSeconds(3);
+ // 加载关卡
+ SceneManager.LoadScene("GameScene");
```

**为什么要拆开**：`LoadDllScripts` 的职责收敛为「**把 DLL 加载进内存**」，加载完就 `Release()` 释放资源句柄 + 切场景；「**调用热更代码**」变成一个持续行为，交给常驻的 `GameManager`。这样 Assembly 的生命周期（加载一次、长期持有）和业务驱动（每帧/每事件）就解耦了。

配套两个细节：

- `LoadDllScripts` 在 `Start()` 里 `Instance = this; DontDestroyOnLoad(gameObject);` → **跨场景常驻**，否则 `SceneManager.LoadScene("GameScene")` 一执行，热更 DLL 的引用持有者就没了。
- `HotUpdateDll` 提为公开只读属性，供 AOT 侧其他脚本取用：

```csharp
public static LoadDllScripts Instance { get; private set; }
public Assembly HotUpdateDll { get; private set; }
```

#### 2. `Assets/AOT/GameManager.cs`（新建）—— 每帧反射驱动热更代码

```csharp
public class GameManager : MonoBehaviour
{
    void Update()
    {
        //获取dll中的类
        Type helloType = LoadDllScripts.Instance.HotUpdateDll.GetType("Hello");
        MethodInfo helloMethod = helloType.GetMethod("Run");
        //调用
        helloMethod.Invoke(null, null);
    }
}
```

**做了什么**：从 `LoadDllScripts.Instance` 取到已加载的 Assembly → 反射拿 `Hello` 类型 → 反射拿静态 `Run` 方法 → 每帧调用一次。热更 DLL 里改逻辑，重打一份 DLL 即可改变运行行为 —— **这就是代码热更的最小可验证闭环**。

**⚠️ 性能隐患（当前是「先跑通」阶段，属于已知技术债）**：`GetType` / `GetMethod` / `Invoke` **全在 Update 热路径上，每帧执行 3 次反射**。其中 `Invoke` 是装箱 + 参数数组 + 反射栈帧，`GetMethod` 还要做字符串匹配。优化路径（按性价比排序）：

1. `Start()` 里把 `Type` / `MethodInfo` **缓存成字段**，Update 只留 `Invoke`；
2. 用 `MethodInfo.CreateDelegate<Action>()` 或 `Delegate.CreateDelegate` 转成**强类型委托**，调用开销降到接近直接调用；
3. 反射的 `Invoke` 参数为 `null, null`（静态无参），是反射里最快的一档，但仍远慢于委托。

#### 3. `Assets/HotUpdate/Hello.cs` —— 热更侧业务（每帧旋转两个方块）

```csharp
public class Hello
{
   public static void Run()
   {
       var g1 = GameObject.Find("Square (1)");
       var g2 = GameObject.Find("Square (2)");
       g1.transform.Rotate(0, 0.1f, 0.1f);
       g2.transform.Rotate(0, 0.1f, 0.1f);
   }
}
```

**验证意图**：热更代码里**直接操作场景对象**（`Transform.Rotate`）—— 证明热更 DLL 与 AOT 主包共用同一套 UnityEngine 对象体系，热更逻辑不是"沙箱里跑不了引擎 API"。配合 `GameManager.Update` 每帧调用，视觉上就是两个方块持续旋转。

**⚠️ 性能隐患**：`GameObject.Find` 是**按名字全场景层级遍历**（O(n)），这里每帧调 2 次 → 典型反模式。正确写法是在热更侧入口初始化时缓存 `Transform` 引用：

```csharp
// 推荐：入口初始化时缓存，Run 里只做 Rotate
static Transform _g1, _g2;
public static void Init() {
    _g1 = GameObject.Find("Square (1)").transform;
    _g2 = GameObject.Find("Square (2)").transform;
}
```

（与上面 `GameManager` 的反射缓存是同一类问题：**「每帧做查找」应改成「一次查找 + 缓存引用」**。）

**⚠️ 待核对的一点**：代码里 `defaultVersion = "v1.0"`（远端 URL 的版本一级目录），而本次构建产出的包版本是 **v1.1.5** —— 两者是**不同层级的版本概念**（URL 目录版本 vs YooAssets 包版本），需确认 CDN 上的目录是按 `v1.0` 还是按包版本组织，否则 `RequestPackageVersionAsync` 会取不到版本文件。已列入 Ideas 待验证。

## Ideas

- **反射热路径的三级优化**：`GameManager.Update` 现在每帧 3 次反射 —— 缓存 `Type`/`MethodInfo` → `CreateDelegate<Action>()` 转强类型委托 → 直接在热更 DLL 里暴露入口。用 Profiler 量化三档开销，正好能回答 Q3「反射有多慢」。
- **`GameObject.Find` 的替换实验**：热更侧 `Hello.Run` 每帧 Find 两次；改成「热更入口 `Init()` 缓存 Transform」后对比帧耗时，是理解「查找 vs 缓存引用」最直观的一组数据。
- **版本号两层概念要理清**：代码 `defaultVersion = "v1.0"`（远端 URL 一级目录）与构建产物包版本 `v1.1.5` 不是一回事 —— 需确认 CDN 目录究竟按哪个组织，否则 `RequestPackageVersionAsync` 取不到版本文件（这是热更最常见的"首跑失败"原因之一）。
- **主动造一个 AOT 泛型用例**：在 `Hello` 里 `new List<MyStruct>()` / `new Dictionary<string, MyStruct>()`（MyStruct 只在热更程序集里定义），跑一次「生成 AOT 泛型引用」，观察 `AOTGenericReferences.cs` 从空变成有内容 —— 这是把 HybridCLR 泛型补全从"背结论"变成"看现象"的最短路径。
- **YooAssets 分包粒度**：`BundleCollectorSetting` 现在只收了一个 `HotUpdateDlls` 包，还看不出分包的取舍 —— 按目录 / 按标签 / 显式收集器三种粒度对增量更新包体的影响值得单独实验。
- **资源库仍完全空白的几个方向**（补笔记优先级）：CPU 剔除加速结构（BVH / 四叉 / 八叉树）、SCGI 实时全局光照、延迟渲染 G-Buffer 与 MSAA 不兼容、Shader 编译工具链（DXC / PSO）、拓扑排序判环、程序集卸载与 `AssemblyLoadContext`。
