# 单例模式与静态类选型

> 来源：CSDN《unity几道面试题》真实面经原题："单例一般用在什么地方？什么时候使用单例、什么时候使用静态类？"（Day 37 面经）

## 经验法则

> **要"对象"（实例状态 / 多态 / 生命周期 / 可配置）→ 单例；只要"函数"（纯工具、无状态计算）→ 静态类**

| | 单例 Singleton | 静态类 static class |
|---|---|---|
| 典型场景 | 唯一的对象实例、管理器（AudioManager/GameManager） | 纯逻辑计算、工具函数（Mathf、路径计算） |
| 状态 | 有实例字段，可存储状态 | 只有 static 字段（全局唯一，无法序列化） |
| 生命周期 | 可挂场景、走 Awake/OnDestroy | 跟程序共存亡，无钩子 |
| 继承/接口 | 可以 | **不行** |

## 静态类做不到、单例能做到的四件事（C# 语法硬限制）

1. **不能继承、不能实现接口**——静态类隐式 sealed，天生无法参与多态；想"换一种实现"（测试替换、策略切换）只能靠接口 + 多态，静态类写死
2. **没有实例，不能当参数传递 / 不能存引用**——`X.Method()` 只能写死调用，无法注入、无法替换 → 解耦、单元测试 mock 全部出局
3. **没有生命周期**——静态类跟程序共存亡；MonoBehaviour 单例可挂场景、走 Awake/OnDestroy、用协程
4. **static 字段无法序列化**——状态不能进 Inspector 配置、不能存档

## 单例的缺点（进阶必背）

1. **全局状态 + 隐式依赖**：任何类 `XX.Instance` 一拿就悄悄耦合了它，依赖关系藏在地毯下
2. **难测试**：全局唯一实例不好替换、状态跨测试污染
3. **生命周期坑**：场景切换不销毁会残留/重复初始化；跨场景数据要不要清得自己管
4. **滥用即反模式**：什么都塞单例 = 上帝对象、职责爆炸（ServiceLocator 反模式）

## 与事件驱动分层的对照（实战）

纯逻辑管理器若不需要挂场景，用**普通类 + 注入/静态 Instance** + **事件驱动**（状态变更方不知道谁在听）可避开单例耦合坑——见 [[UI-逻辑-数据分层与事件驱动]]。

## CRTP 自引用泛型单例 —— 一份基类、每个子类各一个实例（2026-11-05 实证）

配表管理器这类「一个子类管一张表」的场景，最省事的写法是**泛型基类里放静态单例**，子类只需声明自己：

```csharp
public abstract class JsonManager<T, U>
    where T : class, IJsonData, new()
    where U : JsonManager<T, U>, new()      // ← CRTP：U 就是派生类自己
{
    private static JsonManager<T, U> instance;

    public static JsonManager<T, U> Instance
    {
        get
        {
            if (instance == null)
            {
                instance = new U();              // 能 new 出具体子类，靠的就是 new() 约束
                instance.LoadConfig();
            }
            return instance;
        }
    }

    protected abstract string JsonPath { get; }  // 带参构造与 new() 冲突 → 用抽象属性传配置
}

public class WeaponGunManager : JsonManager<WeaponConfig, WeaponGunManager>
{
    protected override string JsonPath => "WeaponGun.json";
}
```

### 核心机制：static 字段属于「封闭泛型类型」，不属于泛型定义

`static` 成员在泛型类型里**按每组类型实参各存一份**（JIT 会为每个封闭类型生成独立的静态区）：

| 表达式 | 是否同一份 `instance` |
| --- | --- |
| `JsonManager<WeaponConfig, WeaponGunManager>.instance` | 第 1 份 |
| `JsonManager<BulletConfig, BulletManager>.instance` | 第 2 份 |
| `JsonManager<T, U>`（开放类型） | 不存在，未封闭不能取静态成员 |

→ **一份基类代码，天然得到「每张表一个单例」**，不需要为每张表手写 `static XXX Instance`。这是这套写法唯一不可替代的价值。

### CRTP 到底解决了什么

基类的静态 getter 里要构造**具体子类**。没有 `U` 时只有两条路：反射（`Activator.CreateInstance`，慢且丢编译期检查）或让每个子类各写一遍单例样板。CRTP 把「子类类型」当模板参数回传，`new U()` 就是编译期确定的直接构造 —— **零反射、零样板**。

### 三个必须知道的代价

1. **`new()` 约束 = 单例没封死**：要求 `public` 无参构造，外部依然能 `new WeaponGunManager()` 造出第二份（数据各自一份）。真要封死得用 `Activator.CreateInstance(typeof(U), true)` 调非公开构造，属于过度设计。
2. **静态字段是 GC Root**：`instance` 一旦赋值永不回收，管理器里缓存的东西（配表、贴图引用）会跟着常驻。这是「管理器单例」的正常代价，但**别在里面塞场景对象引用**。
3. **静态状态在 Fast Enter Play Mode 下不会重置**（Unity 6.6 起 FEPM 为新项目默认）：重进 Play 时 `instance` 还指向上一次的对象 → 脏数据。排查用 Project Auditor，或加 `[RuntimeInitializeOnLoadMethod]` 手动清。

### `Instance` 该返回 `U` 还是基类

返回 `JsonManager<T,U>` 时，外部只能调基类成员，子类特有方法要强转：

```csharp
public static U Instance => instance ??= CreateAndLoad();   // 返回 U，外部零强转
```

推荐返回 `U` —— 语义就是「我要那个子类」。

### 反例：状态字段别跟着一起 static

```csharp
// ❌ 静态集合跨实例串味，且永不回收
private static Dictionary<int, T> TConfigDict = new();

// ✅ 实例字段，随单例一起活
private Dictionary<int, T> TConfigDict = new();
```

泛型基类里写 `static` 集合是最容易犯的错：一旦哪天出现第二个实例（测试、多套配置），数据会互相污染，且**没有任何编译期提示**。
