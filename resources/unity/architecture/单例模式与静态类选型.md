# 单例模式与静态类选型

> 来源：CSDN《unity几道面试题》真实面经原题："单例一般用在什么地方？什么时候使用单例、什么时候使用静态类？"（Day 37 面经）

## 经验法则

> **要"对象"（实例状态 / 多态 / 生命周期 / 可配置）→ 单例；只要"函数"（纯工具、无状态计算）→ 静态类**

| | 单例 Singleton | 静态类 static class |
|---|---|---|
| 典型场景 | 唯一的对象实例、管理器（AudioManager/GameManager） | 纯逻辑计算、工具函数（Mathf、路径计算） |
| 状态 | 有实例字段，可存储状态 | 只有 static 字段（全局唯一，无法序列化） |
| 生命周期 | 可挂场景、走 Awake/OnDestroy | 跟程序共存亡，无钩子 |
| 继承/接口 | 可以 | **不行** |

## 静态类做不到、单例能做到的四件事（C# 语法硬限制）

1. **不能继承、不能实现接口**——静态类隐式 sealed，天生无法参与多态；想"换一种实现"（测试替换、策略切换）只能靠接口 + 多态，静态类写死
2. **没有实例，不能当参数传递 / 不能存引用**——`X.Method()` 只能写死调用，无法注入、无法替换 → 解耦、单元测试 mock 全部出局
3. **没有生命周期**——静态类跟程序共存亡；MonoBehaviour 单例可挂场景、走 Awake/OnDestroy、用协程
4. **static 字段无法序列化**——状态不能进 Inspector 配置、不能存档

## 单例的缺点（进阶必背）

1. **全局状态 + 隐式依赖**：任何类 `XX.Instance` 一拿就悄悄耦合了它，依赖关系藏在地毯下
2. **难测试**：全局唯一实例不好替换、状态跨测试污染
3. **生命周期坑**：场景切换不销毁会残留/重复初始化；跨场景数据要不要清得自己管
4. **滥用即反模式**：什么都塞单例 = 上帝对象、职责爆炸（ServiceLocator 反模式）

## 与事件驱动分层的对照（实战）

纯逻辑管理器若不需要挂场景，用**普通类 + 注入/静态 Instance** + **事件驱动**（状态变更方不知道谁在听）可避开单例耦合坑——见 [[UI-逻辑-数据分层与事件驱动]]。
