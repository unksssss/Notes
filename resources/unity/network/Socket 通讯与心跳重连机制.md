# Socket 通讯与心跳重连机制

## 一、Socket 连接建立

### 1.1 两端的 API 顺序（面试可以直接背这个）

```
服务端                                 客户端
Socket()   创建套接字                   Socket()   创建套接字
Bind(ip, port)   绑定端口                Connect(serverIP, port)  → 发出 SYN
Listen(backlog)  进入监听状态
Accept()   阻塞等待 ────────────────→    （三次握手完成）
  ↓ 返回【一个新的 socket】
  ↓ 后续收发全部用这个新 socket
Receive() / Send()                     Receive() / Send()
```

**关键细节：`Accept` 返回的是新 socket，不是监听的那个。**

- 原 socket 继续 `Listen`，负责接收后续的新连接
- 新 socket 代表「这一个」客户端，负责和它收发数据

一句话记：**监听 socket 是门口的前台，Accept 返回的是带客人进房间的服务员。** 前台永远站在门口，不会跟着某一个客人走。

### 1.2 三次握手与 API 的对应关系

| 步骤 | 网络上的包 | 代码层面 |
| --- | --- | --- |
| ① 客户端发起 | `SYN` | `Connect()` 调用即触发 |
| ② 服务端回应 | `SYN + ACK` | 内核自动完成，**连接进入半连接队列** |
| ③ 客户端确认 | `ACK` | 内核自动完成，**连接进入已连接队列** |
| ④ 应用取走 | — | `Accept()` 从已连接队列取出，返回新 socket |

**为什么要三次**：两次无法确认「客户端的接收能力」——服务端发了 SYN+ACK 但客户端可能收不到。第三次 ACK 才能证明双向都通。同时它顺带完成了**初始序列号（ISN）的交换**——没有这一步，后面的可靠性机制无从谈起。

### 1.3 一个常被问的点：`backlog` 是什么

`Listen(backlog)` 的参数是**已连接队列的长度上限**。队列满了之后，新来的连接会被丢弃或收到 RST（取决于系统配置）。

所以高并发服务端把 `backlog` 设太小，会出现「连接偶发失败」这种诡异现象——不是代码 bug，是队列溢出。

## 二、为什么需要心跳

### 2.1 正常断开 vs 异常断开

**正常断开**：一端调用 `Close()` → 发 `FIN` → 对端回 `ACK` → 双向关闭。对端能收到 `OnDisconnected` 回调，一切清楚。

**异常断开**：断电、拔网线、进程被 kill、移动网络切换、NAT 表项过期。此时**一个包都没发出去**，对端的内核毫不知情，socket 仍然是 `ESTABLISHED`。

这种状态叫 **半开连接（half-open）**。

> 你笔记里那句「client 异常无法发送 fin 包，服务器没有办法检测」——说的就是它。这是心跳存在的唯一理由。

### 2.2 为什么 TCP 自带的 KeepAlive 不够用

TCP 确实有 KeepAlive 机制，但游戏里基本不用，四个原因：

| 问题 | 说明 |
| --- | --- |
| **默认太长** | Linux `tcp_keepalive_time` 默认 **7200 秒（2 小时）**，业务早凉了 |
| **只在空闲时发** | 有数据往来时永远不探测，无法表达「应用层还活着」 |
| **跨层不可见** | 它由内核发，应用层拿不到「探测失败」的即时反馈 |
| **NAT 不一定放行** | 很多 NAT 设备对长时间无数据的连接直接回收表项，比 KeepAlive 周期短得多 |

→ 结论：**必须做应用层心跳**，周期自己定，失败自己能感知。

## 三、心跳的两种设计

### 3.1 Ping-Pong（请求-响应）—— 游戏最常用

```
客户端 ──Ping(seq)──→ 服务端
客户端 ←──Pong(seq)── 服务端
```

- 客户端发，服务端**必须回**
- 客户端如果在 N 个周期内没收到 Pong → 判定断线，触发重连
- 服务端也记 `lastRecvTime`，超过阈值没收到任何数据 → 判定该连接死亡，踢掉并清理缓存

**为什么两端都要检测**：客户端检测是为了自己重连；服务端检测是为了释放僵尸连接的账号数据、避免在线人数虚高。

### 3.2 单向心跳

只发不等回，对端靠「多久没收到数据」判断。

优点是省一半流量；缺点是**单向链路故障检测不出来**（我能发出去，但收不到你的包）。游戏里一般不用，除非流量极度敏感。

### 3.3 参数怎么定

| 参数 | 典型值 | 定这个值的理由 |
| --- | --- | --- |
| 心跳间隔 | **3~10 秒**（手游常见 5s） | 太长会被 NAT 表项回收（常见 30s~5min）；太短费流量和电 |
| 超时判定 | **2~3 倍间隔** | 单次丢包不该判定断线，要容忍偶发抖动 |
| 心跳包大小 | 几个字节（只有包头 + 类型） | 它只是保活，不是业务数据 |

> **一个容易忽略的联动**：心跳间隔必须**小于** NAT 表项的超时时间，否则连接会被中间设备悄悄回收——表现为「玩几分钟突然掉线，重连又正常」。

## 四、断线重连

### 4.1 不能「发现断了就立刻重连」

最朴素的写法是 `Connect()` 失败就再 `Connect()`，这会造成两个事故：

1. **服务器重启时雪崩**：几万客户端同时重连，服务端刚起来就被打挂
2. **弱网下疯狂重试**：每帧重连，耗电、耗流量，还会被服务端风控

### 4.2 正确做法：指数退避 + 抖动

```
第 1 次：1s 后
第 2 次：2s
第 3 次：4s
第 4 次：8s
第 5 次：16s（封顶 30s）
每次叠加 ±20% 随机抖动
```

- **退避**：给网络和服务端恢复的时间
- **抖动（jitter）**：把同时重连的客户端打散，避免「同一秒一起冲」
- **次数上限**：比如 5 次后停止自动重连，弹「网络异常，请检查网络后重试」

### 4.3 重连 ≠ 重新 Connect

这是最容易被忽略的一层。TCP 连接重建成功，只代表「管道通了」，**业务状态全是空的**：

1. **重新鉴权**：token 可能已过期，要重发登录/验证
2. **恢复会话**：服务端要知道「你是刚才那个玩家」，而不是新玩家
3. **补状态**：断线期间错过的数据要拉一次全量快照（位置、血量、背包）
4. **重发未确认请求**：客户端发出但没收到响应的消息，要决定是否重发（注意幂等）

### 4.4 要区分「网络断」和「被踢」

服务端主动踢人（顶号、封号、超时清理）时，客户端**不应该无限重连**。协议里要有一个明确的「被踢」错误码，收到就停止重连并提示原因。

## 五、Unity 侧的三个实现坑

### 坑 1：移动端切后台，心跳会停

Unity 在后台时 `Update` 不执行，定时器也可能被系统挂起。回到前台时，服务端那边早就判定超时了。

```csharp
void OnApplicationPause(bool paused)
{
    if (!paused) SendHeartbeatImmediately();   // 回前台立刻补一次
}
```

PC / 主机端不涉及，但移动端必踩。

### 坑 2：`System.Threading.Timer` 的回调不在主线程

它的回调跑在**线程池线程**上，在里面碰 `transform`、UI、`Instantiate` 都是未定义行为。

→ 心跳这种「只发一个包」的逻辑可以放在 IO 线程；但「断线后触发 UI 提示」必须转回主线程（入队 + 主线程 `Update` 消费）。

### 坑 3：心跳包每帧 new 一个，GC 会哭

```csharp
// ✗ 每 5 秒 new 一个 byte[]，长期跑就是持续的小额垃圾
socket.Send(new byte[] { 0x01 });

// ✓ 复用同一个缓冲区
readonly byte[] heartbeatBuffer = new byte[4];
socket.Send(heartbeatBuffer);
```

单次 4 字节不起眼，但挂机 8 小时 × 每秒 0.2 次 = 5760 次分配。**心跳是「必须零分配」的典型场景**，因为它永远在跑。

## 六、对照：我自己的项目（面试话术）

DarkGod 的服务端与客户端**都没有做应用层心跳**，现状是：

| 环节 | 现状 | 风险 |
| --- | --- | --- |
| 断线检测 | 只依赖库的 `OnDisConnected` 回调（即收到 FIN / RST） | 异常断线（拔网线、断电）检测不到，会留僵尸连接 |
| 重连 | `SendMsg` 里发现 socket 为 null 就直接 `InitSvc()` | 无间隔、无次数上限、无退避，弱网下会疯狂重连 |
| 会话恢复 | 重连后重新走登录流程 | 没有「断线重连保留角色」的概念，业务状态全丢 |

**被问到时这样答（承认 + 给出正确做法）**：

> 「我这块做的是 TCP 长连接，断线靠的是连接断开事件，**没有实现应用层心跳**——所以异常断线（比如拔网线）是检测不到的，这是当时的短板。
>
> 如果要补，我会这么做：客户端每 5 秒发一次心跳，服务端 15 秒没收到就判定离线并清理缓存；客户端连续 2 次没收到 Pong 就触发重连，重连用指数退避加随机抖动，从 1 秒涨到封顶 30 秒，最多 5 次。重连成功后不是简单重连就完事，还要重新鉴权、拉一次全量状态。」

**这段话的说服力不在「我会」，而在「我知道自己缺什么」**——面试官听得出来这是真踩过还是背的。

## 七、自测五问

1. `Accept()` 返回的是哪个 socket？服务端后续用哪个收发数据？
2. 为什么 TCP 自带 KeepAlive，游戏还要自己做心跳？（说出两个理由）
3. 心跳间隔为什么不能设成 60 秒？
4. 重连为什么要加随机抖动，而不只是指数退避？
5. 重连成功后，业务上还需要做哪几件事？

> 第 3 题的答案是 **NAT 表项会过期**，不是「服务端等不及」——这个区分能直接看出你有没有想过真实链路。
