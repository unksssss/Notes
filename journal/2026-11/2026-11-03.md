#### 三、`JsonManager<T>`：把「读表 + 按 ID 索引」抽成泛型基类

```cs
public class JsonManager<T> where T : class, IJsonData, new()
{
    private Dictionary<int, T> TConfigDict = new Dictionary<int, T>();

    public JsonManager(string jsonPath)
    {
        var tList = JsonParser<T>.ParseTabel(jsonPath);
        foreach (var item in tList)
            TConfigDict[item.GetID()] = item;   // 重复 ID 静默覆盖
    }

    public T GetConfig(int _ID)
    {
        if (!TConfigDict.TryGetValue(_ID, out T t)) return null;
        return t;
    }

    public List<T> GetAllConfig()
    {
        List<T> tLst = new List<T>();
        foreach (var data in TConfigDict) tLst.Add(data.Value);
        return tLst;
    }
}
```

`WeaponGunManager` 现在只剩转发：

```cs
public class WeaponGunManager : JsonManager<WeaponConfig>
{
    public WeaponGunManager(string jsonPath) : base(jsonPath) { }
}
```

**为什么这么写是对的**：读表逻辑与「表是哪张」彻底解耦，以后加 `BulletConfig` / `LevelConfig` 只需再写一个 `class BulletManager : JsonManager<BulletConfig>` 一行，泛型约束 `class, IJsonData, new()` 保证了「有 ID、能 new」。

**三个边界（未改，先记账）**：

1. `GetAllConfig()` 每次调用都 `new List<T>`，而 `OnSceneCreateGun` 只用一次 —— 现阶段无所谓，但如果 UI 每帧拿就成 GC 源。想稳就缓存成 `IReadOnlyList<T>`，构造时建一次。
2. `Dictionary` 的遍历顺序**在 .NET 里不是契约**。现在看着是插入序（1001→1002→1003），但 `Remove` 之后复用空闲槽就会打乱。凡是「配表顺序有语义」（技能栏、关卡顺序）的地方，`GetAllConfig` 必须靠另一个 `List<T>` 保序，不能靠字典。
3. 重复 ID 是 `TConfigDict[id] = item` 静默覆盖，不报错 —— 配表填错两个 1001 会悄悄丢一条。加个 `if (TConfigDict.ContainsKey(...)) Debug.LogError`。

#### 四、`for (int i = 2; ...)` 为什么是 2，不是 3

昨天 XML 路线里踩的是「三行表头」，今天 JSON 路线只跳 2 行，**不是写错了**：

| 位置 | xlsx 里 | 导出成 JSON 后 |
| --- | --- | --- |
| 第 1 行 字段名 | `ID / WeaponName / …` | **变成了对象的 key**，不再占数组元素 |
| 第 2 行 类型 | `int / string / …` | `Sheet1[0]` |
| 第 3 行 注释 | `武器ID / 武器名称 / …` | `Sheet1[1]` |
| 第 4 行起 数据 | `1001 / AK47 / …` | `Sheet1[2]` 起 |

所以 `i = 2` 正好从第一条数据开始。**这个数字是跟导表格式绑死的**，换导表工具（比如把类型行也去掉、只留注释行）就得跟着改 —— 应该提到常量或配置里，别散落在循环头。

📎 [[配置表读取 — Excel 导表、三行表头与反射映射]]

同一处还有个**异常分支漏 return**：

```cs
if (rows == null || rows.Count < 3)
{
    Debug.LogError("[JsonPath]表结构异常,需要填充数据");
    // ← 这里缺 return，下面 for 会拿 rows 继续跑
}
```

`rows` 为 null 时下一行 `rows.Count` 直接 NRE，LogError 打出来的信息被异常盖掉，反而更难查。**报错后必须中断**，否则「日志里看着有错、实际崩在别处」。

#### 五、🔴 硬伤一：`out` 标志位被循环覆盖 → 事件可能永不触发

这是今天最重要的发现，且是**静默失效**——不报错、不崩，只是 UI 偶尔不刷新。

```cs
bool isAddChanged = false, isSubChanged = false;

for (int i = 0; i < AllWeaponItems.Count; i++)
{
    if (Vector3.Distance(...) < 2f)
        AddAreaWeaponItems(AllWeaponItems[i], out isAddChanged);   // ← 每轮覆盖
}
```

`AddAreaWeaponItems` 内部：

```cs
private void AddAreaWeaponItems(WeaponItem item, out bool isChanged)
{
    if (!AreaWeaponItems.Contains(item))
    {
        isChanged = true;
        AreaWeaponItems.Add(item);
        return;
    }
    isChanged = false;
}
```

**根因**：`out` 不是「只在变化时赋值」，而是**每次调用都必须写一个值**。循环里 7 把枪扫一遍，`isAddChanged` 的最终值 = **最后一次调用**的结果。

- 第 1 把枪进范围（`true`）→ 第 2 把本来就在列表里（`false`）→ 最终 `false`
- 结果：`if (isAddChanged || isSubChanged)` 判 false → `OnAreaWeaponChanged` 不触发 → **UI 不刷新**

只有当「遍历顺序里最后一把枪恰好是新进入的」时才碰巧正确 —— 典型的时序相关 bug，测的时候容易漏，上线后偶发。

**改法（三选一，推荐第一个）**：

```diff
- private void AddAreaWeaponItems(WeaponItem item, out bool isChanged)
+ private bool AddAreaWeaponItems(WeaponItem item)
  {
      if (!AreaWeaponItems.Contains(item))
      {
-         isChanged = true;
          AreaWeaponItems.Add(item);
-         return;
+         return true;
      }
-     isChanged = false;
+     return false;
  }
```

```diff
-         AddAreaWeaponItems(AllWeaponItems[i], out isAddChanged);
+         isAddChanged |= AddAreaWeaponItems(AllWeaponItems[i]);
```

要点：**「有没有变化」是一个聚合量，不能用 out 在循环里传递**。要么返回 bool 让调用方 `|=`，要么把 `isChanged` 做成 `ref`，要么干脆去掉标志位、**每次变化后直接发事件**（7 把枪的量级，多发几次事件比藏 bug 划算）。

另外两个小问题顺手记：

- 删除循环是倒序 `for (int j = AreaWeaponItems.Count - 1; j >= 0; j--)` —— **这个倒序是对的**，正序删会跳元素。但函数内部又 `Contains` 一遍（`AreaWeaponItems[j]` 必然在里面），是冗余的双保险。
- `AddAreaWeaponItems` 里 `Contains` 是 O(n)，整个 `Update` 是 O(n·m)。7 把枪无所谓，但模式别养成 —— 枪多了应该换 `HashSet` 或者干脆用 `Physics.OverlapSphere` 让物理引擎做。

#### 六、🔴 硬伤二：运行时脚本里 `using UnityEditor;`

`FightingManager.cs` 头部：

```cs
using System.Net.Sockets;
using InfimaGames.LowPolyShooterPack;
using UnityEditor;          // ← 运行时脚本
```

`FightingManager` 挂在场景里、属于 `Assembly-CSharp`（运行时程序集）。**打包 Player 时 Unity 不会把 `UnityEditor.dll` 编进运行时程序集**，`using UnityEditor;` 直接 `CS0246: The type or namespace name 'UnityEditor' could not be found` → **构建失败**。

Editor 里一切正常，是因为编辑器下 `Assembly-CSharp` 引用了 `UnityEditor.dll`。这就是「编辑器跑得好好的，一打包就红」的经典成因之一。

规矩：
- 运行时脚本**一行 `UnityEditor` 都不许有**，哪怕只是 `using` 没用上
- 真要 Editor-only 逻辑 → 放 `Assets/Editor/` 目录，或用 `#if UNITY_EDITOR` 包起来
- 同理 `System.Net.Sockets` 今天也没用上，属于噪音，删掉

### 其他技术产出

- **美术资源落地**：三把枪的 prefab 进 `Resources/Prefab/Weapon/`，三张图标进 `Resources/Icon/`，命名与配表 `PrefabName` / `IconName` 逐字一致 —— 这条对上了，所以 `Resources.Load` 能成功。**配表里写的是字符串，资源名改一个字就静默变 null**，这是配表驱动最脆的一环。
- **场景改造**：`Fighting.unity` 新增 `WeaponPoints`（7 个 `Weapoint_0~6`）+ `Weapons`（枪械父节点）+ `Scroll View > Viewport > Content > Item(TxtName/Icon)`。`Instantiate(prefab, Weapons)` 之后又手动 `SetPosition`，注意 `Weapons` 若有缩放会把位置带歪。

## Ideas

- 「变化检测」的正确形状：不是 `out bool` 在循环里传，而是**聚合 + 只在聚合结果为真时发一次事件**。这个模式在伤害飘字、buff 列表、任务追踪里会反复用到。
- 配表驱动的系统，**「资源名 ↔ 配表字符串」是唯一的弱契约**。可以考虑写个 Editor 校验工具：扫一遍配表，把 `Resources.Load` 返回 null 的行全列出来，导表时跑一次。
- 7 个挂点随机 3 种枪，重复率其实很高（期望不重复只有 3!/3^7 ≈ 0.02%）。要么洗牌保证多样性，要么给每种枪配权重。
- `Resources` 这条路走到头就该换 Addressables —— 正好和 `HybirdCLR` 那套 YooAssets 是同一类问题，两边可以对照着看。
