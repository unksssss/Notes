#### ① 溢出伤害统计：`self` 字段是破抽象，正解是「用 `this`」

**目标文件**：`Assets/Scripts/Base/IDamageable.cs`、`Assets/Scripts/Role/Health.cs`、`Assets/Scripts/Base/RoleBase.cs`

**问题**：目标 100 血，一发 30 伤害打到只剩 10 血时，`TotalDamage` 记 30 而不是 10。

**灯皇的第一版**：给 `DamageInfo` 加 `public readonly RoleBase self;`，`Bullet` 里 `hit.collider.GetComponent<RoleBase>()` 取到受伤者传进去，`Health.OnDamage` 里直接 `damage.source.AddTotalDamageNum()` / `damage.self.AddTakeDamageNum()`。

**三处硬伤**：

1. **两次 `GetComponent`** —— `GetComponent<IDamageable>()` + `GetComponent<RoleBase>()`，同一 Collider 查两遍。
2. **破抽象** —— `IDamageable` 的实现者不一定是 `RoleBase`（项目里已有 `P_EXP_Barrel` 炸药桶）。`GetComponent<RoleBase>()` 返回 null 时 `damage.self.AddTakeDamageNum()` 直接 NRE。
3. **`Health` 越权** —— `Health` 只管血量，不该知道 `RoleData` 统计。统计的归属是 `RoleBase`（它才持有 `roleData`）。

**关键洞察**：`RoleBase.OnDamaged(DamageInfo)` 是**实例方法**，`this` 天然就是受伤者 —— `self` 字段完全是多余的。

**落地的改法（4 步）**：

```diff
// 1. IDamageable.cs —— 删字段，回到 5 参数
 public readonly struct DamageInfo
 {
     public readonly int attackDamage;
     public readonly Vector3 hitPoint;
     public readonly Vector3 hitNormal;
     public readonly RoleBase source;
     public readonly int teamID;
-    public readonly RoleBase self;   // 受伤者：多余
 }
```

```cs
// 2. Health.OnDamage —— 算完真伤后【重建】一个 DamageInfo 再广播
int prevHeath = currentHealth;
currentHealth = Mathf.Max(0, currentHealth - damage.attackDamage);
int trueDamageValue = prevHeath - currentHealth;

// readonly struct 在 Unity 2022.3（C# 9）下没有 with 表达式，只能 new
DamageInfo trueDamageInfo = new DamageInfo(trueDamageValue, damage.hitPoint, damage.hitNormal,
                                           damage.source, damage.teamID);
OnDamaged?.Invoke(trueDamageInfo);
if (currentHealth == 0) { isDead = true; OnDied?.Invoke(trueDamageInfo); }
```

```cs
// 3. Bullet.Move —— 只查一次，只依赖接口
IDamageable damageable = hit.collider.GetComponent<IDamageable>();
damageable?.OnDamage(new DamageInfo(attackValue, hit.point, hit.normal, source, 0));

// 4. RoleBase.OnDamaged —— 恢复累加（this 就是受伤者）
protected virtual void OnDamaged(DamageInfo damageInfo)
{
    this.AddTakeDamageNum(damageInfo.attackDamage);
    damageInfo.source?.AddTotalDamageNum(damageInfo.attackDamage);
}
```

**顺带修好的**：`Health.isDead` 现在会正确置 `true`（之前血量归零后每发子弹都重发 `OnDied`，`WaitForDeath` 起多个协程）。

**仍未修**：`Health.TeamID` 私有初值 `-1`，`Bullet` 传的 `teamID` 恒为 `0` → `if (TeamID == damage.teamID) return;` 恒不成立，友伤过滤从未生效，敌人互射能互伤。

#### ② 双 `Health` 真修：`SetActive(false)` 是唯一可靠的时序闸门

**目标文件**：`Assets/Scripts/Fightings/FightingManager.cs`（`OnSceneCreateEnemy`）

**问题**：改完 ① 后玩家 `TotalDamage` 恒为 0，敌人一枪死。

**根因链**：

```text
new GameObject("EnemyAI")            → 默认 active
enemy.AddComponent<EnemyAI>()        → OnEnable 同步触发
  RoleBase.OnEnable: health == null  → GetOrAddComponent<Health>() 造出 Health A，订阅 A
enemy.AddComponent<Health>()         → 造出 Health B
health.Init(roleInfo.Health)         → 只 Init 了 B
enemyAI.health = B                   → 只改了字段引用，订阅仍挂在 A
子弹 GetComponent<IDamageable>()     → 按添加顺序返回 A（currentHealth 从未 Init = 0）
→ trueDamageValue = 0 - 0 = 0，且 currentHealth == 0 立刻成立 → 一枪秒杀
```

**落地代码**：

```cs
GameObject enemy = new GameObject("EnemyAI");
enemy.gameObject.SetActive(false);   // 关键：先关掉，AddComponent 不触发 Awake/OnEnable
var health = enemy.AddComponent<Health>();
health.Init(roleInfo.Health);
var enemyAI = enemy.AddComponent<EnemyAI>();
enemyAI.health = health;             // 在 OnEnable 之前赋好
enemyAI.SetRoleInfo(roleInfo);
enemy.SetActive(true);               // OnEnable 看到 health != null，直接订阅正确的那个
```

> 注意：`new GameObject()` 创建出来**就是 active 的**，`AddComponent` 对 active 对象会**同步**跑 `Awake`/`OnEnable` —— 这是所有「重复组件 + 订阅挂错对象」问题的共同源头。反过来，inactive 对象上 `AddComponent` 不触发任何消息，正是装配期最安全的窗口。

**残留**：`FightingManager` 顶部还有 `using UnityEditor;`（`#if UNITY_EDITOR` 都没包）→ 打包必然 `CS0246`；`int count = 2;` 是调试期硬编码，`roleInfos.Count * 2` 被注释掉了。

#### ③ 订阅幂等写法里藏着一个拼写错误

**目标文件**：`Assets/Scripts/Base/RoleBase.cs`（`OnEnable`）

```cs
health.OnDamaged -= OnDamaged;
health.OnDied    -= OnDamaged;   // ← 应该是 OnDied
health.OnDamaged += OnDamaged;
health.OnDied    += OnDied;
```

`-= OnDamaged` 删的是另一个委托目标，什么都不会删；而 `+= OnDied` 每次 `OnEnable` 都加一遍 → **`OnDied` 多播链持续累积**。对象池/`SetActive` 复用时会一次击杀加 N 次击杀数。

**这类 bug 的特征**：`-=` 删不存在的委托**不报错、不打警告**，静默无效。所以幂等订阅的正确姿势是「**同一个方法名成对出现**」，最好把订阅/退订收进一对 `Subscribe()/Unsubscribe()` 私有方法，肉眼 diff 就能对齐。

#### ④ `ClearAll()` 先 `Clear()` 再倒序销毁 → 武器全部泄漏

**目标文件**：`Assets/Scripts/Fightings/FightingManager.cs`（`ClearAll`）

```cs
for (int i = enemyLst.Count - 1; i >= 0; i--) Destroy(enemyLst[i].gameObject);
AllWeaponItems.Clear();                                  // ← 先清了

for (int i = AllWeaponItems.Count - 1; i >= 0; i--)      // Count == 0，循环体一次不执行
    Destroy(AllWeaponItems[i].gameObject);
AllWeaponItems.Clear();                                  // 再清一次（无意义）
```

`List.Clear()` 只清元素不清容量，`Count` 立刻变 0 —— 后面的倒序销毁循环条件 `i >= 0` 从 `i = -1` 开始，**一次都不进**。场景重载时 `DontDestroyOnLoad` 之外的物体会被 Unity 清掉，所以现象不明显；但只要换成「不重载场景的重开」或武器挂在常驻节点下，就会实打实泄漏。

**修法**：销毁循环在前，`Clear()` 在最后；两处 `Clear()` 只留一个。

#### ⑤ `ResourcesMgr.ClearPool()` 只清字典，不销毁实例

**目标文件**：`Assets/Scripts/Global/ResourcesMgr.cs`

```cs
public void ClearPool()
{
    gameObjectPool.Clear();   // 池里的 GameObject 一个都没 Destroy
}
```

字典是唯一的引用持有者，`Clear()` 之后那些 `SetActive(false)` 的子弹/特效**再也没人能拿到**，也永远不会被回收 —— 每次 `ReGame` 泄漏一批。正解是遍历销毁：

```cs
foreach (var kv in gameObjectPool)
    foreach (var go in kv.Value)
        if (go != null) Object.Destroy(go);
gameObjectPool.Clear();
```

**同一文件的另一处 O(n)**：`GetInPool` 用 `bullsts[0]` + `RemoveAt(0)`，`RemoveAt(0)` 要搬整个数组。子弹池高频进出，应该用栈语义（`Add` + `[Count-1]` + `RemoveAt(Count-1)`）或改成 `Stack<GameObject>`。

两个后果：

1. **就地排序改源数据** —— UI 层对业务层的数据做了原地重排。今天没炸是因为排序恰好是幂等需求，但只要 UI 换个排序维度（比如按金币），`FightingManager` 那边的顺序就跟着变。
2. **`ClearAll()` 不清 `roleDataLst`** —— `ReGame` → 重载场景 → `FightingManager` 是新实例、`roleDataLst` 是新 List，看似没事；但 `AddRoleData` 的去重靠 `Contains(roleData)` **引用比较**，而 `roleData` 是跟着 `RoleBase` 走的对象。一旦将来改成「不重载场景的重开」，旧 `RoleData` 会一直留在榜上。

**方向**：`Open()` 里 `new List<RoleData>(manager.RoleDataLst)` 做一份快照再排；`ClearAll()` 补 `roleDataLst.Clear()`。

#### ⑦ `Player.Update` 隐藏了 `RoleBase.Update`（CS0114）

**目标文件**：`Assets/Scripts/Role/Player.cs`

```cs
// RoleBase
protected virtual void Update() { }

// Player
private void Update() { ... }   // ← 不是 override，是 hiding
```

`RoleBase.Update` 是 `protected virtual`，`Player` 写 `private void Update()` 会**隐藏**它并触发 `CS0114` 警告。Unity 的消息派发是「按名字找最派生的那一个」，所以今天**行为上没错**（`RoleBase.Update` 本来就是空的），但这和上午 `Player.Awake` 隐藏 `RoleBase.Awake` 是同一个雷 —— 一旦哪天往 `RoleBase.Update` 里塞逻辑，子类静默不执行。

**修法**：`protected override void Update() { base.Update(); ... }`；`Awake` 同理（`protected override void Awake() { base.Awake(); ... }`）。

## Ideas

- 结算面板的数据流值得单独收口：`RoleData` 该由谁持有、UI 拿快照还是拿引用、`ReGame` 清理清单能不能做成一个 `IGameResettable` 接口 —— 现在「谁该清什么」散在 `ClearAll` / `ClearPool` / `OnDestroy` 三处，漏一处就是一个泄漏。
- `InputSystem_Actions` 的教训可以推广：**所有非 `UnityEngine.Object` 的订阅型对象**（`InputAction`、`Action` 字段、`CancellationTokenSource`）都不随场景销毁，必须显式 Dispose。可以把「重开局泄漏」做成一页 checklist。
- 选择排序 + `Compare` 返回 `a-b` 的整数溢出，正好是 Day 73 的 Q4 —— 用自己写的代码当题面，比背答案有效得多。
- `.asmdef` 空白是硬伤：HybridCLR 的冷热分离本质上就是程序集切分，不熟 `.asmdef` 就永远只能照抄教程。
