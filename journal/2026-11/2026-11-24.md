#### 三、三条详细拆解

##### ① `MiniMap.Start` 与 `FightingManager.Start` 的顺序竞争

`FightingManager.Start` 末尾直接驱动小地图：

```cs
UIFightingView.Instance.SetResidueNum();
UIFightingView.Instance.InitMiniMap();
```

而 `MiniMap` 的所有引用都在它自己的 `Start` 里 `transform.Find` 出来：

```cs
void Start()
{
    imgPlayer = transform.Find("player").gameObject;
    imgEnemy  = transform.Find("enemy").gameObject;   // ← 只在 Start 里赋值
    ...
}
```

两个 `Start` 谁先跑**没有保证**——`ProjectSettings/MonoManager.asset` 里没有任何自定义执行顺序，同帧 `Start` 的调用顺序按内部 behaviour 列表来，跟场景层级无关。`FightingManager` 先跑时，`CreateEnemtImgs()` 里 `Instantiate<GameObject>(imgEnemy)` 拿到的是 null：

```
ArgumentException: The Object you want to instantiate is null.
```

即使不抛，下一行 `enemyImg.transform.parent = transform` 也会 NRE，小地图整个不显示。

**根因**：把「引用解析」放在 `Start`（生命周期最晚的初始化点），却让**外部对象**在 `Start` 里驱动它。修法二选一：

```cs
// 方案 A：引用解析提前到 Awake（Awake 一定早于任何 Start）
private void Awake()
{
    imgPlayer = transform.Find("player").gameObject;
    imgEnemy  = transform.Find("enemy").gameObject;
    imgEnemy.SetActive(false);
    rectTransform = GetComponent<RectTransform>();
}

// 方案 B：不依赖隐式时机，给一个显式 Init()，由调用方负责先后
public void Init(Player p, EnemyAI[] enemies) { ... }
```

##### ② 坐标符号反了 180°

```cs
float x = (playerPos.x - enemyAIs[i].transform.position.x) / detectRadius;   // ← 反
float z = (playerPos.z - enemyAIs[i].transform.position.z) / detectRadius;
```

小地图要画的是「敌人相对玩家在哪」，所以偏移必须是 `enemy - player`。写成 `player - enemy` 后两个轴同时取反 = 绕原点转 180°：敌人在右显示在左、在前显示在后。

这个 bug 难查的原因是**它不像 bug**：图标数量对、图标在动、缩放也正常，只有方向错，第一反应容易怀疑美术资源或 `Image` 的 pivot。

正确写法（顺便补 yaw 抵消与内缩 clamp）：

```cs
float half = rectTransform.rect.width * 0.5f - 10f;          // 10 = 图标半宽
for (int i = 0; i < enemyAIs.Length; i++)
{
    if (!enemyImgs.TryGetValue(enemyAIs[i], out var icon)) continue;   // ⑥ 兜底

    Vector3 d = enemyAIs[i].transform.position - player.transform.position;
    d.y = 0f;
    // 需要「上=玩家前方」时把这行打开（-yaw 抵消玩家朝向）
    // d = Quaternion.Euler(0f, -player.transform.eulerAngles.y, 0f) * d;

    Vector2 p = new Vector2(d.x, d.z) / detectRadius * half;
    if (p.magnitude > half) p = p.normalized * half;          // 圆形雷达按模长 clamp
    icon.localPosition = new Vector3(p.x, p.y, 0f);
}
```

##### ③ 双 `Health` 的「假修复」：一枪死照旧

昨天记录了「敌人身上两个 `Health`」→ `GetComponent<IDamageable>()` 命中没 `Init` 的那个 → 一枪死。今天 `FightingManager` 里多了两行，看起来像修了：

```cs
var health = enemy.AddComponent<Health>();   // 第二个
enemyAI.health = health;                     // 字段指向第二个
health.Init(roleInfo.Health);                // 只给第二个 Init
```

但**订阅早就绑在第一个上了**：

| | 第一个 `Health`（`RoleBase.OnEnable` 的 `GetOrAddComponent` 创建） | 第二个（`FightingManager.AddComponent` 创建） |
| --- | --- | --- |
| `currentHealth` | **0**（从未 `Init`） | 正确血量 |
| `OnDamaged` / `OnDied` 订阅 | ✅ 有 | ❌ 无 |
| `GetComponent<IDamageable>()` 命中 | ✅ **命中它** | 永远轮不到 |

`Bullet` 走 `hit.collider.GetComponent<IDamageable>()`，`CharacterController` 在根节点 → 永远打到第一个 → `Mathf.Max(0, 0 - damage) = 0` → 立刻 `OnDied` → **一枪死，和没修一模一样**。

`AddComponent` 之后再赋字段，改不了「谁被 `GetComponent` 命中」（它按挂载顺序返回第一个），也搬不动委托。真正的修法是**只留一个创建入口**：删掉 `AddComponent<Health>()`，把 `Init` 收进 `RoleBase.SetRoleInfo`。

## Ideas

- 小地图这条链路的正确顺序应该是「`Awake` 拿引用 → `Start` 等数据 → 外部只在数据就绪后调 `Init`」。整个项目里凡是「基类 `OnEnable` 兜底创建 + 装配方 `AddComponent`」的组合都有同类隐患，值得统一收口。
- 敌人 AI 现在靠 `CharacterController` 直线 Move 硬顶墙，`CollisionFlags` 完全没用上。哪怕不上 NavMesh，只用 `Move()` 的返回值做「撞墙 → 换向」也能救掉大半卡死。
- `detectRadius` / `detectDis` / `pursueDis` / `attackDis` / `idleDis` 五个距离阈值散落在两个类里硬编码，且互相重叠（50 < 60、`_minDis` 被就地改写）。该收进 `ScriptableObject` 并画一张区间图。
- `enemyAILst` 暴露成 `List` 引用给每个敌人遍历，是「遍历中改集合」的定时炸弹。给个只读快照或 `for` 反向遍历只是止血，正解是让 `FightingManager` 统一驱动（敌人只上报状态，不互相遍历）。
