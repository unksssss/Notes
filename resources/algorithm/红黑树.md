# 红黑树 Red-Black Tree

自平衡二叉搜索树。C++ `std::map` / `std::set`、Java `TreeMap`、Linux CFS 调度、epoll 的底层结构。

前置知识：[[二叉搜索树BST]]（BST 会退化成链 → 需要平衡树）。

## 一、五条性质

| # | 性质 |
|---|---|
| ① | 节点非**红**即**黑** |
| ② | **根**必须是**黑** |
| ③ | 所有 **NIL 空叶子**算**黑** |
| ④ | 禁止"红红"——红节点的两个孩子必为黑 |
| ⑤ | 从任一节点到其后代 NIL 的**所有路径黑高相等** |

**性质 ④⑤ 是核心**：④ 限制红色不能连续，⑤ 保证黑色分布均匀 —— 两者合起来把树高夹住了。

## 二、黑高推导（为什么是 O(log n)）

设某节点黑高为 `h`（到 NIL 路径上的黑节点数）：

- **最短路径**：全是黑节点 → 长度 **h**；
- **最长路径**：红黑交替（每层最多夹 1 个红，因为禁红红）→ 长度 **≤ 2h**。

于是一棵树的最长路径不超过最短路径的 **2 倍** —— 这就是"**大致平衡**"。

再由 "黑高为 h 的子树至少含 2ʰ − 1 个节点" 推出：

```
n ≥ 2^h - 1  ⟹  h ≤ log₂(n+1)
树高 ≤ 2h ≤ 2·log₂(n+1)      →  O(log n) 有保证
```

**对比**：AVL 是**严格平衡**（左右子树高度差 ≤ 1），红黑树只是"最长 ≤ 2×最短"，**比 AVL 略松**。代价换来的是更少的旋转（见第六节）。

## 三、插入：新节点默认红色

**新插入节点一律染红**。原因：

- 染**红**：只可能违反性质 ④（红红），**局部**可修；
- 染**黑**：必然违反性质 ⑤（该路径黑高 +1），**全局**失衡，修起来麻烦得多。

（最后记得把根强制染黑，满足性质 ②。）

**父节点是黑 → 什么都不用做，插入结束。** 只有**父节点是红**才需要修复。

## 四、插入修复三 case（关键看"叔节点"）

设新节点 X、父 P、祖父 G、**叔 U = G 的另一个孩子**。

| Case | 条件 | 操作 |
|---|---|---|
| **1** | **叔红** | P、U 变**黑**，G 变**红** → 把 **G 当作新节点继续上推**循环（可能一路到根，最后染根黑） |
| **2** | **叔黑 + 之字**（X 与 P 方向相反） | 绕 **P** 旋转"掰直" → 转成的形态落入 **Case 3** |
| **3** | **叔黑 + 一字**（X 与 P 方向相同） | 绕 **G** 旋转 + **P/G 换色** → **修复结束** |

**要点**：
- **旋转次数封顶 2 次**（Case2 → Case3），变色每轮 O(1) 但可能沿路径上推 O(log n) 层；
- Case 1 是唯一会**向上传递**的，其余都在本层解决；
- 判定顺序固定：**先看叔的颜色，再看是"一字"还是"之字"**。

> ⚠️ 常见认知偏差：**不是"颜色决定旋转"，旋转看的始终是结构（一字 / 之字）**，颜色只是 1 bit 的失衡记账 —— 见下节。

## 五、颜色的真正含义：与 2-3-4 树同构

| 红黑树 | 2-3-4 树 |
|---|---|
| **黑**节点 | **占一层**的"格子" |
| **红**节点 | 挂在格子**内部、不占层**的"挂件" |
| 禁止红红 | 每个格子 **key 数 ≤ 3**（即 2/3/4 节点） |
| Case 1（叔红） | 格子**满 4 key → 劈开，中键上提** |

所以红黑树本质是 **"用二叉树的壳子实现的 2-3-4 树"** —— 红色边只是"这条边在 2-3-4 树里不存在"的标记。

**由此推出那条关键认知**：

> AVL 用 `int height` 记账，红黑树用 `bool color` 记账 —— **都是记账方式，旋转与否取决于结构**。
> 认为"红色就要旋转"是错的：Case 1 叔红时**一次旋转都不做**，只变色上提。

## 六、AVL vs 红黑树（纠错备忘）

| | AVL | 红黑树 |
|---|---|---|
| 平衡标准 | 严格（\|bf\| ≤ 1） | 宽松（最长 ≤ 2×最短） |
| **插入**旋转次数 | **至多 1 次**单/双旋 | 0~2 次 |
| **删除**旋转次数 | 最坏 **O(log n) 次** ⚠️ | **≤ 3 次** |
| 查询 | **略快**（树更矮） | 略慢 |
| 插入/删除 | 慢（维护成本高） | **快** |
| 适用 | 查多改少 | **改多查少**（通用容器首选） |

> ⚠️ **易错说法纠正**：常说"AVL 插入要 O(log n) 次旋转"是错的 —— **O(log n) 那部分是沿途 height 的刷新，不是旋转次数**；AVL 插入至多 1 次旋转。AVL 真正的痛点是**删除最坏 O(log n) 次旋转**。
> 红黑树的收益：无违规时插入**零维护** + 旋转封顶 2~3 次。

## 七、应用场景

- **C++ `std::map` / `std::set` / `multimap`**：红黑树（有序、O(log n)）
- **`std::unordered_map`**：哈希表（无序、平均 O(1)）
- **Java 8+ `HashMap`**：链表长度 **≥ 8 转红黑树**、**≤ 6 退化回链表**（`TREEIFY_THRESHOLD = 8`）；C# `Dictionary` **始终是单链表**，不树化（📎 [[哈希表冲突解决与Dictionary底层]]）
- Linux **CFS 进程调度**、`epoll` 事件表
