# 二十四点游戏

## 一、题目

给 4 个数字（通常 1~13），判断能否用 `+ - * /` 和括号，让每个数字**恰好用一次**、结果为 24。

```
4 1 8 7   → true    (8-4)*(7-1) = 24
1 5 5 5   → true    5*(5-1/5)   = 24   ★ 需要分数
3 3 8 8   → true    8/(3-8/3)   = 24   ★ 需要分数
1 1 1 1   → false
```

## 二、核心思路：每次消掉一个数

4 个数不好直接搜表达式，但可以换个视角：

> **任选两个数，用六种运算之一把它们合并成一个新数**，数字个数就从 `n` 变成 `n-1`。
> 递归到只剩 1 个数时，看它是不是 24。

为什么这样能覆盖所有表达式？因为任何合法的 24 点表达式，**最后一层运算必然是某两个子表达式的结果**；倒过来看，就是「先合并两个数」的过程。递归下去就穷尽了所有表达式树。

**六种运算**（不是四种）：

```cpp
a + b        a * b        a - b        b - a        a / b        b / a
```

加减乘除里，`+` 和 `*` 满足交换律，只算一次；`-` 和 `/` **不满足**，两个方向都要算。这一条灯皇的代码写对了。

## 三、★ 唯一致命问题：用 `int` 存中间结果

```cpp
if (num[i] != 0) { temp.push_back(num[j] / num[i]); ... }   // ← int / int
```

**`int / int` 是向零截断的整除**，不是数学除法：

```
12 / 8 = 1      (真实 1.5)
13 / 5 = 2      (真实 2.6)
 1 / 5 = 0      (真实 0.2)
 3 / 4 = 0      (真实 0.75)
```

这等于给题目**偷偷加了一种不存在的运算**（"取整除法"）。后果是双向的：

- **漏判**：真解需要小数中间值，int 算不出来 → `1 5 5 5`（`5*(5-1/5)`）被误判为无解
- **误判**：某条路径用上截断除法，恰好凑出 24 → 明明无解却答 true

实测：`1..13` 随机四数 **20000 组**，与精确解（分数运算）对比 ——

| 类别 | 组数 | 占比 |
|---|---|---|
| **误判**（应 false 却答 true） | **2868** | 14.3% |
| **漏判**（应 true 却答 false） | 38 | 0.19% |
| 合计差异 | 2906 | **14.5%** |

**误判比漏判多 75 倍**，这是关键。因为截断总是让商**变小**（向零），后面再用减法（`13-1=12`）或乘法放大，很容易凑回 24 —— 相当于把「能不能到 24」的门槛降低了。

## 四、一条完整的假路径（实测追出来的）

输入 `8 12 13 1`，真实无解，但 int 版走出这条：

```
int 版：  12 / 8 = 1        13 - 1 = 12        12 + 12 = 24   → 判 true
double：  12 / 8 = 1.5      13 - 1.5 = 11.5    11.5 + 12 = 23.5 → 判 false
```

差别只在第一步：`0.5` 被截断丢掉了，然后 `13-1` 就凭空多出 0.5，一路放大到 24。

> 这题最坑的地方在于：**它是"多算了"而不是"少算了"**。少算你还能靠多测几个用例发现，多算就很容易被误认为「算法对了」。

## 五、手选用例测不出来的原因

灯皇这版在 12 个精心挑的用例上**只错 1 个**：

| 输入 | 真解 | int 版 | 结果 |
|---|---|---|---|
| 4 1 8 7 | true | true | ✓ |
| 1 2 3 4 | true | true | ✓ |
| 6 6 6 6 | true | true | ✓ |
| 3 3 3 3 | true | true | ✓ |
| **1 5 5 5** | true | **false** | ✗ |
| 3 3 8 8 | true | true | ✓ |
| 1 3 4 6 | true | true | ✓ |
| 1 1 1 1 / 2 2 2 2 / 7 7 7 7 | false | false | ✓ |

**只要不测到「需要小数」的组合，就完全看不出来。** 而随机 2 万组一跑，14.5% 全暴露。

> **教训**：这类「数值精度」的 bug，手挑用例几乎无效，**必须随机对拍**。

## 六、正解 A：`double` + eps

```cpp
bool dfs(vector<double>& a) {
    int n = (int)a.size();
    if (n == 1) return fabs(a[0] - 24.0) < 1e-6;     // ★ 不能用 ==
    for (int i = 0; i < n; ++i) {
        for (int j = i + 1; j < n; ++j) {
            vector<double> rest;
            for (int k = 0; k < n; ++k)
                if (k != i && k != j) rest.push_back(a[k]);

            double x = a[i], y = a[j];
            double cand[6];
            int m = 0;
            cand[m++] = x + y;
            cand[m++] = x * y;
            cand[m++] = x - y;
            cand[m++] = y - x;
            if (fabs(y) > 1e-9) cand[m++] = x / y;   // ★ 判零用 eps 而非 == 0
            if (fabs(x) > 1e-9) cand[m++] = y / x;

            for (int t = 0; t < m; ++t) {
                rest.push_back(cand[t]);
                if (dfs(rest)) return true;
                rest.pop_back();
            }
        }
    }
    return false;
}
```

两个细节都不能省：

1. **比较 24 用 `fabs(x - 24) < 1e-6`**：`0.1+0.2 != 0.3` 是浮点的常识，`8/(3-8/3)` 这类算出来可能是 `23.999999999999996`
2. **判零用 `fabs(y) > 1e-9`**：浮点运算可能产生 `1e-17` 这样的「近似 0」，用 `y != 0` 会漏判

实测 `double` 版与精确分数版在 2 万组上 **0 差异**。

## 七、正解 B：分数类（绝对精确）

如果面试官追问「浮点误差怎么办」：

```cpp
struct Frac {
    long long p, q;                 // p/q，约分后 q > 0
    Frac(long long a = 0, long long b = 1) {
        if (b < 0) { a = -a; b = -b; }
        long long g = gcd(llabs(a), llabs(b));
        p = a / g; q = b / g;
    }
};
// 四则运算各自通分；判 24 用 p == 24 && q == 1
```

**优点**：没有任何精度问题，`8/(3-8/3)` 精确得到 24。
**缺点**：代码长，`long long` 在极端嵌套下可能溢出（4 个数不会）。

> **面试策略**：先写 `double` 版（够用、好讲），被追问精度再提分数类。**没人会要求你直接手写分数类**。

## 八、第二个坑：空数组会死循环

```cpp
for (int i = 0; i < num.size() - 1; i++)    // ← size() 返回 size_t
```

`num.size()` 是 `size_t`（无符号）。当 `num.size() == 0` 时：

```
0 - 1 = 18446744073709551615   （下溢）
int i 与它比较时会被转成 size_t → i < 18446744073709551615 恒真
```

实测：调用 `IsTwentyFour({})` **2 秒内没有返回**，确认死循环。

**修法**（任选）：

```cpp
for (size_t i = 0; i + 1 < num.size(); i++)        // ★ 用 i+1 避免减法
for (int i = 0; i + 1 < (int)num.size(); i++)      // ★ 强转成有符号
if (num.size() < 2) return num.size() == 1 && num[0] == 24;   // 提前挡
```

题目保证 4 个数时不会踩到，但这是**同一类「无符号减法下溢」的通病**，值得记住。

## 九、其他小问题（都不影响正确性）

| # | 问题 | 说明 |
|---|---|---|
| 1 | 每层 `vector<int> temp` 全新建 + 拷贝 | 4 个数规模下可忽略；想优化可原地交换 |
| 2 | 没有去重剪枝 | 相同数字组合会重复搜索，规模小无妨 |
| 3 | `num[i] != 0` 判分母是对的 | 但漏了「除出来是小数」这件事（见第三节） |
| 4 | 参数按值传 `vector<int> num` | 每层拷贝一次，4 个数无所谓 |

## 十、复杂度

| 维度 | 值 |
|---|---|
| 递归层数 | 4 → 3 → 2 → 1，共 3 层 |
| 每层分支 | `C(n,2) × 6`：第 1 层 `6×6=36`、第 2 层 `3×6=18`、第 3 层 `1×6=6` |
| 总搜索量 | `36 × 18 × 6 = 3888` 次 |
| 时间 | `O(1)`（相对 4 这个常数），推广到 n 个数是 `O(n! · 6^n)` 级别 |
| 空间 | `O(n)` 递归栈 |

**规模极小**，所以不用考虑剪枝、记忆化。这题考的是**正确性**，不是性能。

## 十一、面试延伸

- **「返回所有解」** → 把 `return true` 改成收集表达式字符串，注意**去重**（`4 1 8 7` 和 `1 4 8 7` 是同一个解）
- **「输出表达式而非 true/false」** → 递归时额外携带字符串，合并时拼成 `(a op b)`
- **「n 个数呢」** → 同一套递归直接适用，只是搜索量爆炸；LC 679 只要求判断
- **「为什么不能用 3 个数先合并」** → 可以，但要保证组合方式完备；「每次合并两个」是**最小完备单位**，最不容易漏
- **LC 679 的官方解法还要求处理 0 和负数** → 判零用 `fabs(x) < 1e-6`，别用 `== 0`
