# 内存管理方案对比

## 光谱一览：从手动到自动

```
手动管理 ←——————————————————————————————→ 完全自动
    │        │         │         │          │
   C/C++    Rust     Swift      Go      Python
           (编译期)    (ARC)   Java/C#  (RefCnt+GC)
                                (GC)
```

| 语言 | 策略 | 释放时机 | 运行时开销 | 风险 |
|:----|:----|:--------|:----------|:----|
| **C/C++** | 完全手动 `malloc/free` `new/delete` | 程序员决定 | 零（无运行时开销） | 内存泄漏、野指针、UAF、double free |
| **Rust** | 所有权 + 借用 + 生命周期（编译期） | 作用域结束 → 编译器自动插入 `drop()` | **零运行时开销** ✅ | 借检查器报错（编译期解决，不产生运行时问题） |
| **Swift** | ARC（自动引用计数） | `refCount == 0` → 立即释放 | 引用计数原子增减 | 循环引用需 `weak`/`unowned` |
| **Go** | 并发三色标记 GC | GC 触发时 | GC STW 暂停 | GC 参数调优复杂 |
| **Java / C#** | 追踪式 GC（标记-清除/标记-压缩） | GC 触发时 | GC STW 暂停 | 不确定的暂停时间 |
| **Python** | 引用计数为主 + 分代GC补充 | `ob_refcnt == 0` 立即释放 | 引用计数增减 | 循环引用需 GC 清扫 |

## C/C++ — 完全手动

```c
int* arr = (int*)malloc(100 * sizeof(int));
// 使用
free(arr);    // 必须手动释放！
arr = NULL;   // 避免 dangling pointer
```

**优点**：极致性能，零运行时开销，内存布局完全可控  
**缺点**：泄漏、野指针、UAF——世界上大量 CVE 漏洞源于此

## Rust — 编译期静态分析

```rust
{
    let v = vec![1, 2, 3];  // v 持有堆内存所有权
    // 使用 v
}   // 作用域结束 → 编译器自动插入 drop(v) → 堆内存释放
```

**精髓**：
- **所有权**（Ownership）：每个值只有一个所有者
- **借用**（Borrowing）：`&T` 不可变引用 / `&mut T` 可变引用
- **生命周期**（Lifetimes）：借用不能超过被借用的值的生命周期

Rust 在**编译期**就算清楚对象的生死，运行时没有任何 GC/引用计数的开销。既没有 C/C++ 的痛苦，也没有 GC 的暂停抖动。

## Swift — ARC（自动引用计数）

```swift
class Player { var name: String }
var p1 = Player(name: "Alice")  // refCount = 1
var p2 = p1                     // refCount = 2
p1 = nil                        // refCount = 1
p2 = nil                        // refCount = 0 → 立即释放 ✅
```

**优点**：确定性释放（refCount=0 立即释放），没有 GC 暂停  
**代价**：引用计数增减有运行时开销，循环引用需手动标记 `weak`

## Java / C# — 追踪式 GC

```csharp
void Example()
{
    var obj = new MyClass();  // 堆上分配
    // 使用 obj
}  // ← obj 引用释放，但堆对象等 GC
   //    不知道什么时候回收
```

**优点**：开发者完全不用管释放，写代码最省心  
**代价**：GC 触发时的 STW（Stop The World）暂停

### C# 到底能不能"手动释放"？

```
┌─────────────────────────────────────────────┐
│ C# 内存分两种：                              │
│                                              │
│ 1. 托管堆内存（GC 管理）                       │
│    → 不能手动 free。GC 是唯一的回收者          │
│    → 唯一"手动"方式：GC.Collect()（不推荐）    │
│                                              │
│ 2. 非托管资源（OS 句柄、网络连接、OpenGL 纹理）│
│    → 通过 IDisposable + using 手动释放        │
│    → using 编译为 try/finally + Dispose()     │
└─────────────────────────────────────────────┘
```

```csharp
// IDisposable 只释放非托管资源，不释放托管内存！
using (var file = File.OpenRead("data.bin"))
{
    // 使用文件
} // → 调用 file.Dispose() → 关闭 OS 文件句柄
  // → 但 FileStream 对象本身的托管内存还是要等 GC
```

### C# 的"半手动"手段

| 手段 | 作用 | 说明 |
|:----|:----|:----|
| `IDisposable` + `using` | 释放非托管资源 | 文件、网络、数据库连接等 |
| `GC.Collect()` | 强制触发 GC | **不推荐**，频率不当反而更卡 |
| `GC.AddMemoryPressure()` | 告诉 GC 有大量非托管内存 | 帮助 GC 更准确判断触发时机 |
| `WeakReference` | 弱引用 | 不阻止 GC 回收，可做缓存 |
| 对象池 | 复用对象，减少 new | 最推荐的性能优化手段 |

## Python — 引用计数 + GC

```python
def foo():
    a = [1, 2, 3]  # refCount = 1
    b = a          # refCount = 2
    return         # b 释放 → refCount = 1，a 释放 → refCount = 0 → 立即释放 ✅
```

**特殊问题**：循环引用导致 refCount 永远不会为 0，需要分代 GC 来检测和回收

```python
# 循环引用陷阱
class Node:
    def __init__(self):
        self.next = None

a = Node()
b = Node()
a.next = b
b.next = a  # 循环引用！refCount 永远不会归零
            # → 需要 GC 来检测和回收
```

## 对 Unity 项目的启示

既然 C# 不能手动释放托管内存，VR 项目中避免 GC 抖动的方法：

1. **对象池** — 子弹、特效、绳索节点，new 一次池化复用
2. **`List.Clear()` 复用** 而不是重新 `new List<T>()`
3. **`StringBuilder`** 代替字符串拼接
4. **避免 `foreach` on 值类型集合**（Unity 的 foreach 会装箱产生 GC Alloc）
5. **`struct` 替代 `class`** 承载小型数据（注意防装箱陷阱）
6. **定期 Profiler 检查** — 关注每帧 GC Alloc，定位热点
